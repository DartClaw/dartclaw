# Package Rules — `dartclaw_cli`

**Role**: Two AOT-compilable CLI entry points over one runtime. `bin/dartclaw_workflow.dart` dispatches to `buildDartclawWorkflowRunner`, mounting standalone workflow verbs flat alongside workflow-only `init` and `rebuild-index`. Entry point `bin/dartclaw.dart` dispatches into `buildDartclawRunner` (`lib/src/runner.dart`), which wires 19 top-level `Command<void>` subclasses (`ServeCommand`, `StatusCommand`, `ServiceCommand`, `WorkflowCommand`, `InitCommand`, `TasksCommand`, `SessionsCommand`, `RebuildIndexCommand`, …). `ServeCommand` parses flags, resolves config and assets, then boots the runtime via `DartclawRuntime.build()` from `package:dartclaw_runtime` — the service graph itself lives in `packages/dartclaw_runtime/lib/src/runtime/`, not here.

## Boundaries
- Depends directly on individual workspace packages (`dartclaw_acp`, `dartclaw_client`, `dartclaw_kernel`, `dartclaw_core`, `dartclaw_runtime`, `dartclaw_google_chat`, `dartclaw_workflow`). **Do not** add the `dartclaw` umbrella here — apps wire packages explicitly. `ServeCommand` composes `AcpHarnessRegistrar`; the server runtime deliberately carries no ACP dependency. This app is the only *shipping* workspace member above the runtime tier (`dev/package_tiers.txt`); `dartclaw_fitness` and `dartclaw_testing` outrank it so that nothing which ships can take a production dependency on them. The direction gate holds this app to declaring exactly what it imports — a dependency nothing here imports fails CI.
- External deps capped at: `args`, `logging`, `mason_logger`, `meta`, `path`, `shelf`, `yaml`/`yaml_edit`, plus `sqlite3`, which is declared but not imported so `dart build cli` classifies its native build hook (see the pubspec comment). Push business logic into packages, not new CLI deps.
- Both `bin/dartclaw.dart` and `bin/dartclaw_workflow.dart` are dispatch only. `workflowSubcommands` in `workflow_command.dart` owns the one workflow command list used by both mount points; the lean mount omits connected-only `runs`. The command registration list lives in `buildDartclawRunner` (`lib/src/runner.dart`) so the shipped command surface is reachable from a test — `runner_test.dart` pins it as an exact set. All command code lives under `lib/src/commands/`.

## Conventions
- New top-level command: subclass `Command<void>`, register in `buildDartclawRunner` (`lib/src/runner.dart`) and extend `runner_test.dart`'s exact set (the existing list is loosely alphabetical with grouped exceptions — match surrounding context, don't reorder). Subcommand groups (`config`, `tasks`, `workflow`, `service`, …) live in their own `commands/<group>/` directory with a parent `<group>_command.dart` that `addSubcommand`s children.
- Inject every `dart:io` and factory dependency via constructor with a default (see `ServeCommand`: `serveFn`, `exitFn`, `stderrLine`, `harnessFactory`). Tests pass fakes — never reach for `Process.run` / `stdout` / `exit` directly.
- Workflow commands shared with the lean runner extend client-free `CliCommand` / `WorkflowConnectedCommand`; only the full runner supplies `ApiWorkflowConnection` for connected operations. Keep client-typed fields out of the shared standalone command hierarchy, and derive hints from `command_path.dart`. The standalone health guard uses the shared `dart:io` reachability probe.
- Other server-talking commands extend `ConnectedCommand` (`connected_command_support.dart`): it supplies the DI ctor (`config`/`apiClient`/`writeLine`/`stderrLine`/`exitFn`), `runConnected((apiClient) async {...})` (resolves the client honoring `--config`/`--server`/`--token` and maps `DartclawApiException` → stderr message + `exitFn(connectedExitCode(error))`), and `requirePositionalArg(msg)` for the positional-id guard. Use `client()` directly only when a command needs custom error handling, and `injectedConfig` to honor an injected `DartclawConfig` on a standalone path. Pure helpers (`resolveCliApiClient`, `apiClientFromConfig`, `resolveServerUri`, `writePrettyJson`, `truncate`, `formatDateTime`, `formatNumber`) live in the same file. The transport itself is **not** the CLI's — `DartclawApiClient` and its `ApiTransport` seam live in `package:dartclaw_client`, which is dependency-free by contract; only the `DartclawConfig`/`TokenService`-derived construction stays here, because the client may not read a data directory. The byte renderer `formatByteSize` moved to `dartclaw_runtime` with the wiring that shares it — import it from `package:dartclaw_runtime/dartclaw_runtime.dart`; it is deliberately distinct from that package's page-side `formatBytes`.
- `serve` config precedence: injected `DartclawConfig` > `loadCliConfig(cliOverrides:)` (CLI flags > YAML > defaults). Only forward flags that were `wasParsed`.
- Exit codes: `0` success/report, `1` other failure or refusal, `2` cancelled/paused/awaiting-approval workflow, `3` unreachable transport, `4` HTTP 401/403, `5` other 4xx, `6` 5xx, `64` usage, `130` interrupted credential input. Connected failures use `connectedExitCode`; always exit through the injected `ExitFn`.
- **`commands/service/` is the one install path, in two scopes.** `ServiceScope { user, system }` threads through all five `ServiceBackend` methods; each platform backend keeps exactly **one** unit renderer that emits the scope's variant (LaunchAgent/LaunchDaemon, `systemd --user`/system). System scope refuses without effective uid 0 before any filesystem write, and derives its run-as user from `SUDO_USER` or `--service-user` rather than defaulting to root. **No generated unit carries a secret** — both scopes resolve credentials from config and the `dartclaw auth` stores. Don't reintroduce a placeholder-substitution step or a second root-daemon generator.
- Server and workflow assets are embedded in generated Dart maps. Source checkouts still win for dev/live-edit paths; compiled binaries use embedded content and materialize workflows/skills to the data dir where harnesses require files.

- **`ServeCommand` is the container posture's resolution point.** It calls `resolveContainerPosture` on the primed
  config, with its own `PlatformCapabilities`, *before* `DartclawRuntime.build` — so the runtime, the startup banner and
  every reader downstream see one settled boolean. The zero-server `workflow` lane deliberately does not resolve: a
  lifecycle-only verb must not touch the container runtime, and an undeclared posture stays disabled there.

## Gotchas
- `confirmDestructive` owns the shared deletion rule: `--yes`/`-y` proceeds, a terminal prompts on stderr, and non-terminal stdin without the flag refuses. Keep prompts and refusal messages off stdout, including JSON mode.
- **`commands/secrets/` is the only operator write path into the named credential store**, and it loads config with `loadCliConfig(resolveStoredCredentials: false)`. The default `loadCliConfig` registers the stored-credential provider (`ensureStoredCredentialProviderRegistered` in `config_loader.dart`), which merges the store into `config.credentials` — after which a shadowed name shows only as its stored entry and `secrets list`/`secrets audit` could not report the config-declared half at all. `SecretsSubcommand.loadDeclaredConfig` therefore skips that registration for the config file's **own** view (the load itself still goes through the runtime's one `loadDartclawConfig` seam); the `secrets list` shadowed-name assertion is what catches a regression here. `secrets set` reads the value from stdin only through the same `auth/secret_input.dart` seam — no option carries it — and validates `<name>` against `^[a-z0-9][a-z0-9_-]{0,63}$` **before** the store is opened or any path is joined. `secrets audit` reads the raw YAML as well as the parsed config: `search.providers.<id>.api_key` and `github.webhook_secret` are substituted at parse time, and a provider whose key resolves blank is dropped from the parsed map entirely, so neither the literal-versus-`${VAR}` question nor the unresolved-variable name survives into `DartclawConfig`.
- **`ensureStoredCredentialProviderRegistered` is the one registration site**, called from `loadCliConfig` before the load it hands to the runtime's `loadDartclawConfig`. `DartclawConfig.load` invokes the registered closure on every load, so `config_api_routes`, `guard_editor_service` and `reload_trigger_service` resolve stored credentials without a site of their own — a `dartclaw secrets set` is seen by the next reload, which reports `credentials` as a restart-tier section rather than delivering a delta. An unusable store degrades to no stored credentials, as `init/setup_checks.dart` does for the subscription store.
- **`commands/auth/` is the only operator write path into the dedicated credential stores**, and `token show|rotate` is unrelated (that is the server gateway token). `auth claude` reads the `setup-token` from stdin only — piped, or the masked `secret_input.dart` prompt — so it declares no option or positional that could carry the value into shell history or `ps`; that prompt reads **byte-at-a-time** (`stdin.readByteSync`) with the terminal in non-canonical, no-echo, **no-signal** (`-isig`) mode and writes one `*` per accepted byte, so a Ctrl-C arrives as byte `0x03` and is handled in-band: the mode is put back *before* the `onInterrupt` callback exits `130`, and nothing is stored. `-isig` is not optional — a SIGINT that still killed the process would bypass the restoring `finally` and leave the terminal with *neither* echo nor line mode. The mode is entered with `sh -c 'stty … < /dev/tty'` (`Process.runSync` gives the child no terminal on stdin), and a failed save or enter falls back to `dart:io`'s `lineMode`/`echoMode` pair rather than proceeding through a terminal that cannot be put back — that fallback is also the Windows path, where a Ctrl-C is whatever the console does with it. **Never read `stdin` as a stream here**: listening detaches the descriptor, after which the restoring calls throw `EBADF` and the prompt aborts with the terminal still in the hidden mode — the very failure the restore exists to prevent (tried, reverted, pinned by a test). It opens the store *before* the read so a collision or unwritable directory refuses while the operator still holds the token, and it re-ingests without an overwrite flag because re-running is the documented annual renewal. `auth codex` writes nothing itself: it spawns `codex login` with `ProcessStartMode.inheritStdio` on the operator's inherited environment with only `CODEX_HOME` overridden — deliberately *not* `SafeProcess.sanitize`d, since that rule exists to stop an agent's subprocess inheriting operator secrets and this is the operator's own interactive session. **`AuthSubcommand` carries `--data-dir` for the same reason `serve` does**: the store is derived from `server.data_dir`, so a `serve --data-dir` that overrides the YAML value reads a store a `--config`-only `auth` invocation cannot address — and the resulting refusal would tell the operator to re-run a command they already ran successfully. The override rides `loadCliConfig(cliOverrides:)` and is echoed back in `selfInvocation`; every refusal that names a store gets the searched path from `credentialRemediationFor(credentialsDir:)`.
- `serve` registers SIGINT, SIGTERM (skipped on Windows), and SIGUSR1 (`ReloadTriggerService`). New long-running work must wire into the `shutdown()` path in `serve_command.dart` and time out within 10 s, or `serve` will force-exit.
- After `shutdown()` the command calls `_exitFn(0)` outside the `finally` to force VM exit despite pending IO futures — preserve this pattern when editing.
- Local `dartclaw status` reads persisted corpus and index evidence without starting services or rescanning corpus members; `rebuild-index --json` reports revision, indexed rows, and resulting health.
- AOT build target: avoid `dart:mirrors`, runtime `import` strings, and reflective package APIs anywhere reachable from either `bin/dartclaw.dart` or `bin/dartclaw_workflow.dart`.
- `dartclaw init` supersedes the removed `deploy` command family. Prerequisite checks live in `init/setup_checks.dart`. `SetupChecks` is one type over three stages: pre-write `preflight`, post-write `verify`, and `diagnose` for `doctor`. The post-write helpers produce rows; `verify` projects them into its existing messages and outcomes, while `diagnose` adds config validity, storage, health, container and Windows rows. Preflight retains its nearest-existing-parent writability rule; post-write probes stop at the immediate parent. `probeBinary` returns an outcome and version from the same spawn. Doctor reads declared credentials before merged verification, using a per-load opt-out from stored resolution; both credential stores are inspected without provisioning. `--fix` creates only the three layout directories and reruns diagnosis.
- **Release binaries are built with `dart build cli`, not `dart compile exe`.** `dev/tools/build.sh` and `build_windows.ps1` compile both entry points into separate self-contained archives. They use `dart build cli` so the sqlite3 build hooks emit a bundled `libsqlite3` in a sibling `lib/` next to the binary. `dart compile exe` silently produces a sqlite-less binary here (its build-hook check classifies by the workspace-root pubspec — dart-lang/sdk#62593), which crashes at the first SQLite call on Linux. SQLite is bundled by default (no committed `hooks.user_defines.sqlite3.source: system` block). The only sanctioned local escape hatch is an *uncommitted* `source: system` edit for macOS codesign-blocked iteration — documented in `dev/guidelines/KEY_DEVELOPMENT_COMMANDS.md`; never commit it.
- **Release-pipeline verification stays out of the shipped binary.** The Windows bundled-SQLite gate is `dev/tools/build_windows.ps1#Invoke-WindowsBundledSqliteCheck`, which drives FTS5 through each artifact's own `dartclaw.exe` or `dartclaw-workflow.exe` (`rebuild-index` against a temp instance). Don't reintroduce a hidden verification command; `Assert-WindowsReleaseLayout` owns the archive's exact file set.
- **There is one workflow composition root, and the standalone lane stages it.** `--standalone` builds no service graph of its own: `workflow_run_command.dart` and `standalone_lifecycle_support.dart` call `DartclawRuntime.stageHeadless(...)` (`dartclaw_runtime`), which assembles storage, projects and the workflow registry and stops. The command resolves the definition off `staging.workflowRegistry`, derives `requiredWorkflowProviders`, calls `staging.preflightProviderAuth(set)` (friendly `WorkflowPreflightException` → printed remediation + exit 1), then `staging.completeForExecution(set)` – so a logged-out referenced provider aborts before execution setup, and an unreferenced logged-out default is never auth-probed. Lifecycle-only verbs (`cancel`, `pause`) take `completeForLifecycle()` instead, which composes **neither the security nor the harness layer**: no provider capacity, no task executor, no workflow CLI runner, no turn seam, and skill bootstrap forced off. `DartclawRuntime.executions`, `.resetService` and `.selfImprovement` are null on that build and refuse by name through `requireExecutions`/`requireResetService`/`requireSelfImprovement`. Composing them was not free: an `harness.acp.agents` config ran ACP validation subprocesses and a `container.enabled` one touched the container runtime, so a `cancel` could be slow, or fail, over a misconfiguration it has no use for. A headless completion provisions worker capacity **only** for the named providers and builds no primary harness, so it never starts an unused primary runner. Exactly one completion may run; until one does, `staging.dispose()` owns teardown, afterwards `runtime.shutdown()` does. `CredentialPreflight` (`dartclaw_runtime`, `lib/src/project/credential_preflight.dart`, reached through the package barrel) runs *before* staging, so a project credential that resolves empty aborts before any provisioning; the CLI owns only the printed remediation and the exit-1 path.
- **The executor-level preflight is a partial backstop, and it is inert unless the lane injects it.** `dartclaw_workflow`'s `workflow_skill_preflight.dart#_preflightProviderAuth` runs only `if (providerAuthPreflight != null)`; the shared root always injects one (`runtime/service_wiring.dart#_wireWorkflowService`, honoring a caller-supplied override). It probes only the providers a skill-bearing agent step references, so a step that names none is preflighted by nothing — the credential gate on `HarnessWiring`'s `ProviderExecutionInventory` is what refuses that spawn, and both lanes now share it.

## Testing
- `dart_test.yaml` defines tag `integration` (skipped by default); `reload_trigger_service_sigusr1_test.dart` is what still carries it here. The assembled-runtime integration suite now lives in `dartclaw_runtime` — run it with `dart test --run-skipped -t integration packages/dartclaw_runtime/test/runtime/server_builder_integration_test.dart`.
- Unit tests under `test/commands/**` mirror `lib/src/commands/**`. They drive commands through `DartclawRunner.run([...])` with fakes injected via constructor — see `runner_test.dart` and `serve_command_test.dart` for the pattern. Shared test doubles live under `test/helpers/`: `fake_api_transport.dart` (`FakeApiTransport` + `jsonResponse`), `fake_exit.dart` (`FakeExit` marker + `fakeExit` for `exitFn`), `capturing_stdout.dart` (`CapturingStdout` for `IOOverrides`), `log_test_helpers.dart` (`captureRootLogs`, wrapped by `log_service_capture.dart`). Reuse them, do not re-roll. Doubles for workflow-owned ports come from `package:dartclaw_workflow/testing.dart`, not the `dartclaw_testing` barrel.
- Wiring tests are no longer here: the service graph and its suites live in `dartclaw_runtime` (`lib/src/runtime/`, `test/runtime/`). Add a focused test there when introducing a new wiring step.
- **`Directory.current` is process-wide, and suites share the process.** `dart test` runs suites as concurrent isolates in one process, so a suite that sets `Directory.current` (`init_command_test`, `workflow_run_command_standalone_test`, and `dartclaw_runtime`'s `headless_runtime_test`) moves the cwd for every suite running alongside it. Never let a test depend on the cwd: `ServerConfig.templatesDir`/`staticDir` default to repo-root-relative paths, so pass absolute paths (see `serve_command_test.dart`'s `setUpAll`) rather than relying on the cwd or `Directory.current.path`.
- **Don't size a wait to just clear a threshold.** Poll until the expected state with a generous cap instead (`_pollFor` in `harness_wiring_test.dart`, `_waitForCount` in `reload_trigger_service_test.dart`). A fixed delay a few ms past a debounce or expected asynchronous transition passes locally and fails under parallel load.

## Workflow run observability
- **One renderer, two lanes.** `commands/workflow/workflow_progress_renderer.dart` is the single event → step-progress dispatch: step start times, the in-flight settle guard, live-entry retirement, token ticks and the printer calls exist once. The standalone lane feeds it from the in-process `EventBus` (`standalone_run_harness.dart`); the connected lane feeds it from `connected_progress_decoder.dart`, which decodes the per-run SSE frames into the renderer's own vocabulary — no core event is ever synthesized from a partial frame. Each lane keeps a step-context resolver (task row vs. frame `stepIndex` + definition step); transport, `--json` framing, settle rendering, exit codes and interrupts stay lane-owned. Adding a renderer case changes both lanes' output — don't.
- `commands/workflow/standalone_run_harness.dart` owns the standalone lane: renderer-authored `--json` payloads (`durationMs`, `definitionName`, conditional `displayScope`/`outcome`/`reason`, `workflow_approval_requested`), step/iteration completion with inline reasons (`failed — <reason>`, `blocked (recoverable): <reason>`, `interrupted (resumable): <reason>` for teardown-cancelled steps), and a per-story digest at settle (human + a single `workflow_run_digest` JSON object). The connected lane emits none of these: its `--json` stream is the server's frames echoed verbatim, and it prints no digest.
- `commands/workflow/workflow_run_digest.dart` is the shared digest builder (one builder, two renderers: `renderWorkflowRunDigestLines` + `WorkflowRunDigest.toJson`). Per-step status uses the workflow package's `stepStatusFromTask` plus the persisted `step.<id>.outcome`; a raw `cancelled` row under a paused run rolls up as `interrupted` (resumable teardown, not terminal). Reasons are scrubbed at the builder so both renderers emit clean values. Next-actions derive from the settle status; a cancelled run gets none (retry is failed-only).
- Agent-derived strings (step failure/blocked/interrupted reasons, pause reasons, approval messages, run `errorMessage`, display scopes, task titles) are scrubbed at the printer boundary via `commands/workflow/agent_text_scrub.dart` (`scrubAgentReportedText`: strip ANSI/CSI + C1 control chars, collapse whitespace, truncate) — apply it to any new sink that prints agent-reported text; never print such values raw.
- `commands/workflow/cli_progress_printer.dart` has `stepBlocked` for the recoverable-hold line and `stepInterrupted` for teardown-cancelled steps; on an interactive TTY it renders a live spinner via `commands/workflow/live_status_line.dart`. Live per-step token ticks come from `WorkflowCliTurnProgressEvent`; codex emits on `turn.completed`, and claude emits once per completed assistant message. The CLI and SSE transports consume the event provider-agnostically.
- **Live entries retire at task settle, not at the step barrier.** For parallel groups the engine fires `WorkflowStepCompletedEvent` only after the whole group drains, so the renderer watches `TaskStatusChangedEvent` (standalone) / the `task_status_changed` frame (connected) for terminal/`interrupted` statuses (`taskSettlesLiveEntry`) and calls `printer.stepSettled(taskProgressKey(taskId), countTokens: <accepted>)` – otherwise the live line overcounts "N steps running" and retry-replaced task ids leave stale entries. `LiveStatusLine.settleStep` folds only an `accepted` member's live-tick tokens into the run total (failed/cancelled/interrupted settles drop them: the barrier's step `tokenCount` accumulates across retry attempts, and interrupted members stay uncharged – folding would double-count); the barrier's `completeStep` reconciles against the authoritative count instead of double-adding. Permanent completion lines and `--json` framing still come from the barrier events – don't move them to settle time.

## Key files
- `bin/dartclaw_workflow.dart` – dispatch only; the flat command set is `buildDartclawWorkflowRunner`
- `bin/dartclaw.dart` — dispatch only; the command set is `buildDartclawRunner` in `lib/src/runner.dart`
- `lib/src/runner.dart` — `DartclawRunner` global args (`--config`, `--server`, `--token`)
- `lib/src/commands/serve_command.dart` — flag/config/asset resolution, the `DartclawRuntime.build` call, listener bind, banner, signal handling, shutdown sequence
- `lib/src/commands/auth/` — `dartclaw auth claude|codex`: the operator's write path into the dedicated credential stores, plus the masked `secret_input.dart` read seam
- `lib/src/commands/credential_subcommand.dart` — base shared by the `auth` and `secrets` groups: injected stdout/stderr/exit sinks, `--data-dir`, `selfInvocation`, `reasonFor`
- `lib/src/commands/secrets/` — `dartclaw secrets set|list|rm|audit`: the operator's write path into the named credential store, plus the store-versus-config inventory the last two report on
- `lib/src/commands/config_loader.dart` — CLI/YAML/defaults precedence and path resolution
- `lib/src/commands/connected_command_support.dart` — `ConnectedCommand` base + helpers for API-client commands
- `lib/src/commands/workflow/workflow_progress_renderer.dart` — the one event → step-progress renderer, plus the shared `progressStartKey` / `taskProgressKey` / `taskSettlesLiveEntry` helpers
- `lib/src/commands/workflow/connected_progress_decoder.dart` — SSE frame → renderer vocabulary for the connected lane
- `lib/src/commands/reload_trigger_service.dart` — SIGUSR1 + file-watch reload
- `lib/src/commands/service/service_backend.dart` — scoped `ServiceBackend` seam (`+ macos_launchd_backend_support.dart`, `unsupported_service_backend.dart` parts)
