# Package Rules — `dartclaw_cli`

**Role**: AOT-compilable reference CLI app. Entry point `bin/dartclaw.dart` → `DartclawRunner` (`lib/src/runner.dart`) wires ~18 top-level `Command<void>` subclasses (`ServeCommand`, `StatusCommand`, `DeployCommand`, `WorkflowCommand`, `InitCommand`, `TasksCommand`, `SessionsCommand`, `RebuildIndexCommand`, …). `ServeCommand` boots the HTTP server via `ServiceWiring.wire()` (`lib/src/commands/service_wiring.dart`).

## Boundaries
- Depends directly on individual workspace packages (`dartclaw_config`, `dartclaw_core`, `dartclaw_server`, `dartclaw_storage`, `dartclaw_workflow`, `dartclaw_security`, `dartclaw_whatsapp`, `dartclaw_signal`, `dartclaw_google_chat`). **Do not** add the `dartclaw` umbrella here — apps wire packages explicitly.
- External deps capped at: `args`, `http`, `logging`, `mason_logger`, `path`, `shelf`, `sqlite3`, `yaml`/`yaml_edit`. Push business logic into packages, not new CLI deps.
- `bin/dartclaw.dart` is registration-only — no logic. All command code lives under `lib/src/commands/`.

## Conventions
- New top-level command: subclass `Command<void>`, register in `bin/dartclaw.dart` (the existing list is loosely alphabetical with grouped exceptions — match surrounding context, don't reorder). Subcommand groups (`config`, `tasks`, `workflow`, `deploy`, …) live in their own `commands/<group>/` directory with a parent `<group>_command.dart` that `addSubcommand`s children.
- Inject every `dart:io` and factory dependency via constructor with a default (see `ServeCommand`: `serveFn`, `exitFn`, `stderrLine`, `harnessFactory`). Tests pass fakes — never reach for `Process.run` / `stdout` / `exit` directly.
- Server-talking commands extend `ConnectedCommand` (`connected_command_support.dart`): it supplies the DI ctor (`config`/`apiClient`/`writeLine`/`exitFn`), `runConnected((apiClient) async {...})` (resolves the client honoring `--config`/`--server`/`--token` and maps `DartclawApiException` → printed message + `exit(1)`), and `requirePositionalArg(msg)` for the positional-id guard. Use `client()` directly only when a command needs custom error handling, and `injectedConfig` to honor an injected `DartclawConfig` on a standalone path. Pure helpers (`resolveCliApiClient`, `writePrettyJson`, `truncate`, `formatDateTime`) live in the same file.
- `serve` config precedence: injected `DartclawConfig` > `loadCliConfig(cliOverrides:)` (CLI flags > YAML > defaults). Only forward flags that were `wasParsed`.
- Exit codes: `64` (`EX_USAGE`) for `UsageException` (set in `main`), `1` for runtime/IO failure, `0` on graceful shutdown. Always exit through the injected `ExitFn`.
- Deploy templates (`commands/deploy_templates/{launchdaemon_plist,systemd_unit,pf_rules,nftables_rules}.dart`) are Dart string-generators with `__PLACEHOLDER__` tokens — `deploy secrets` substitutes them. Do not ship template files as separate assets.
- Server and workflow assets are embedded in generated Dart maps. Source checkouts still win for dev/live-edit paths; compiled binaries use embedded content and materialize workflows/skills to the data dir where harnesses require files.

## Gotchas
- **`commands/secrets/` is the only operator write path into the named credential store**, and it deliberately does **not** call `loadCliConfig`. `loadCliConfig` registers the stored-credential provider (`ensureStoredCredentialProviderRegistered` in `config_loader.dart`), which merges the store into `config.credentials` — after which a shadowed name shows only as its stored entry and `secrets list`/`secrets audit` could not report the config-declared half at all. `SecretsSubcommand.loadDeclaredConfig` therefore calls `DartclawConfig.load` directly for the config file's **own** view; the `secrets list` shadowed-name assertion is what catches a regression here. `secrets set` reads the value from stdin only through the same `auth/secret_input.dart` seam — no option carries it — and validates `<name>` against `^[a-z0-9][a-z0-9_-]{0,63}$` **before** the store is opened or any path is joined. `secrets audit` reads the raw YAML as well as the parsed config: `search.providers.<id>.api_key` and `github.webhook_secret` are substituted at parse time, and a provider whose key resolves blank is dropped from the parsed map entirely, so neither the literal-versus-`${VAR}` question nor the unresolved-variable name survives into `DartclawConfig`.
- **`ensureStoredCredentialProviderRegistered` is the one registration site**, called from `loadCliConfig` beside `ensureCliChannelConfigsRegistered`. `DartclawConfig.load` invokes the registered closure on every load, so `config_api_routes`, `guard_editor_service` and `reload_trigger_service` resolve stored credentials without a site of their own — a `dartclaw secrets set` is live at the next reload with no restart. An unusable store degrades to no stored credentials, as `setup_verifier` does for the subscription store.
- **`commands/auth/` is the only operator write path into the dedicated credential stores**, and `token show|rotate` is unrelated (that is the server gateway token). `auth claude` reads the `setup-token` from stdin only — piped, or the masked `secret_input.dart` prompt — so it declares no option or positional that could carry the value into shell history or `ps`; that prompt reads **byte-at-a-time** (`stdin.readByteSync`) with the terminal in non-canonical, no-echo, **no-signal** (`-isig`) mode and writes one `*` per accepted byte, so a Ctrl-C arrives as byte `0x03` and is handled in-band: the mode is put back *before* the `onInterrupt` callback exits `130`, and nothing is stored. `-isig` is not optional — a SIGINT that still killed the process would bypass the restoring `finally` and leave the terminal with *neither* echo nor line mode. The mode is entered with `sh -c 'stty … < /dev/tty'` (`Process.runSync` gives the child no terminal on stdin), and a failed save or enter falls back to `dart:io`'s `lineMode`/`echoMode` pair rather than proceeding through a terminal that cannot be put back — that fallback is also the Windows path, where a Ctrl-C is whatever the console does with it. **Never read `stdin` as a stream here**: listening detaches the descriptor, after which the restoring calls throw `EBADF` and the prompt aborts with the terminal still in the hidden mode — the very failure the restore exists to prevent (tried, reverted, pinned by a test). It opens the store *before* the read so a collision or unwritable directory refuses while the operator still holds the token, and it re-ingests without an overwrite flag because re-running is the documented annual renewal. `auth codex` writes nothing itself: it spawns `codex login` with `ProcessStartMode.inheritStdio` on the operator's inherited environment with only `CODEX_HOME` overridden — deliberately *not* `SafeProcess.sanitize`d, since that rule exists to stop an agent's subprocess inheriting operator secrets and this is the operator's own interactive session. **`AuthSubcommand` carries `--data-dir` for the same reason `serve` does**: the store is derived from `server.data_dir`, so a `serve --data-dir` that overrides the YAML value reads a store a `--config`-only `auth` invocation cannot address — and the resulting refusal would tell the operator to re-run a command they already ran successfully. The override rides `loadCliConfig(cliOverrides:)` and is echoed back in `selfInvocation`; every refusal that names a store gets the searched path from `credentialRemediationFor(credentialsDir:)`.
- **Per-runner guard chains are layered.** `wiring/harness_wiring.dart` gives the primary harness and every worker a `GuardChain.layered` chain: the shared `SecurityWiring` base chain plus that runner's own `TaskToolFilterGuard` (per-task/per-turn `allowedTools` + read-only enforcement, e.g. the knowledge-inbox no-tools turn policy). Never hand `_security.guardChain` directly to a harness — the runner's filter would be inert. A guards.* hot-reload swaps only the base list and reaches all runner chains live.
- `HarnessWiring` owns one `ExecutionCoordinator`: one fixed serialized primary lane for interactive web/channel turns, plus hard per-provider worker-lease capacity for tasks, schedules, system/advisor work, and logical-agent sessions. Its runtime construction inputs are immutable; workers start lazily, healthy host workers may be reused only for the same provider/profile, and a logical-agent container may be retained only for the exact session/agent principal until discard, eviction, or shutdown. `sessions_spawn` pins `SessionType.logicalAgent` to `AgentDefinition.provider` (or the default provider when omitted) and the policy resolved by `ExecutionPolicyResolver` (execution mode plus container profile); `sessions_send` persists and replays history and never routes to primary. Both pass explicit persona/model/effort overrides; omitted model and effort inherit provider defaults. Logical agents are not serialized into provider-native initialization payloads.
- `SecurityWiring` builds one `ContainerManager` per live authority, giving it a per-authority generated-state directory under `<dataDir>/containers/<containerName>`, the execution's host artifacts directory (mounted read-write at `/artifacts`, so a workflow step's `DARTCLAW_STEP_ARTIFACTS_DIR` — a `<dataDir>/workflows/…` path in no profile's mount set — translates instead of throwing), and whether an MCP bridge exists (`hasMcpBridge`, derived from the granted tool set). It registers each authority container with `ContainerHealthMonitor` under the leasing principal's `taskId`, so a crash fails that execution alone. `ContainerAuthorityCleanupOwner` retains every lease until destruction is confirmed, coalesces concurrent releases, retries failed destruction, and sweeps active/pending authorities at shutdown. `HarnessWiring` captures the primary authority's container name on acquisition and listens for its `ContainerCrashedEvent`, emitting a distinct severe operator signal (restart-to-recover) — the containerized primary has no auto-recovery (deliberately deferred), so its loss must not read as an ordinary per-task crash. It mounts **no** host provider home: containerized Claude is mediated host-side on whichever credential the host resolves — a stored `setup-token` presented as a Bearer, or an `ANTHROPIC_API_KEY` — and a host holding neither is a startup warning plus an admission-time rejection at `HostGateway.register`, never a `~/.claude.json` mount.
- `HarnessWiring` warns when optional security guards are disabled and when configured agent tool policy cannot be fully host-mediated: Codex approval omitted/invalid/other than `on-request`, or ACP operations outside reverse-call/permission coverage.
- **`HarnessWiring` composes the one `ProviderExecutionInventory` and emits every execution-boundary diagnostic from one block.** ACP registrations with `container_isolation_required: true` are startup-fatal (`acpContainerRequirementError`) before any probe or registration; the inventory is then built from the configured provider IDs plus the ACP set, and the same block logs `hostOverrideWarnings()`, `failClosedWarnings()`, `providerCompatibilityWarnings()` and the `ProviderValidator` warnings through one deduping `warn` closure (the compatibility pass and the startup gate word an unpresentable credential identically, so the line is logged once). Both admission paths (`_primaryContainerManager` and the coordinator's `createWorker`) reject on that inventory's verdict — don't add a second emitter or a local compatibility check.
- **The inventory carries the host boundary's credential gate, and it is the only thing that refuses a host worker *on credential grounds*.** `createWorker` refuses first and independently — an unknown provider, or a container profile outside that provider's allowlist, throws `WorkerCreationException` before the verdict is consulted — so the inventory is the credential authority, not the only gate. `ProviderExecutionInventory.of(credentialGate:)` takes `HarnessWiring._credentialRefusalFor`, consulted per verdict rather than snapshotted — a store is re-read per spawn. Not injecting a credential is **not** a refusal: both vendor CLIs self-authenticate behind an empty environment (`claude auth status`, `~/.codex`), so a forced `providers.<id>.auth` that cannot be satisfied has to be rejected before `_harnessFactory.create`. The gate refuses every `CredentialUnavailableReason` **except** `noneConfigured` — that one exclusion is what keeps "nothing selected, so the vendor CLI's own login is admissible" alive, and removing it breaks 0.24 parity. It also skips a provider declaring `credentials_required: false` and any ACP registration, matching `ProviderValidator`. A provider *alias* has no support record (`ProviderIdentity.family` does not resolve aliases), so the gate is consulted even when the inventory holds no entry — that is precisely the shape the aliased-provider fall-through took.
- `serve` registers SIGINT, SIGTERM (skipped on Windows), and SIGUSR1 (`ReloadTriggerService`). New long-running work must wire into the `shutdown()` path in `serve_command.dart` and time out within 10 s, or `serve` will force-exit.
- After `shutdown()` the command calls `_exitFn(0)` outside the `finally` to force VM exit despite pending IO futures — preserve this pattern when editing.
- **`HarnessWiring` owns every containerized execution's bridged-MCP grant.** Deny-by-default for scoped identities: a logical agent's `allowed_tools`, or — for background work, which has no agent definition — the tool policy already on the execution request (`ExecutionRequest.allowedTools`, set by `TaskExecutor` from the task's own policy). The primary lane is the exception: it is the deployment itself, so it is granted the registered *semantic* MCP tools minus `agent.disallowed_tools`, never the session-spawning ones. Every grant is intersected with the tools this deployment actually registers (`_ownMcpToolCanonicals`), warning once per unservable entry — a `web_search` grant with no `search.providers` is reported at startup, not at the agent's first turn. Warnings about a container reaching *no* host tool are narrowed to the cases where that is real capability loss (the `restricted` profile, or a configured grant that turned out entirely unservable); an ordinary workspace task with no tool policy is the intended default and stays silent. **The workflow one-shot lane is no exception:** it derives its grant from the same owner via `HarnessWiring.workflowBridgedMcpTools` (background work carries no agent definition, so its grant comes from the step's own tool policy), injected into `WorkflowCliRunner` through `TaskWiring.bridgedMcpToolsResolver`. Don't re-add a local grant derivation in `workflow_cli_runner.dart`; the runner fails closed without the injected resolver.
- **Native provider web tools are suppressed for every container profile, not just `restricted`.** `WebSearch`/`WebFetch` execute at the provider rather than in the container, so `network:none` cannot contain them and `ProviderAdapter` 403s any request declaring one — from any profile. `workerDisallowedTools` therefore adds both to every container execution regardless of what the bridge serves (the harnesses do the same independently: `ClaudeCodeHarness._deniedNativeWebTools`, and `nativeWebSearch: false` on every `CodexEnvironment.containerAuthClean`). Bridged MCP is a container's only web path; re-adding a "keep native search when nothing bridged is granted" fallback puts the harness back in contradiction with the gateway and 403s every turn.
- `HarnessWiring` owns MCP disallowed-tool derivation, using `mcpDisallowedTools` from `serve_command.dart` to suppress `WebFetch` and (conditionally) `WebSearch` when MCP is active. The standard MCP endpoint is active with gateway authentication or on an authentication-disabled loopback deployment; non-loopback authentication-disabled deployments never advertise or mount it. Mirror any new built-in tool overlap there.
- `StorageWiring` owns the shared `MemoryCorpusService`; startup and offline rebuild stream independently bounded member projections, prove exact FTS5 row parity, and re-authenticate the complete canonical union before publishing healthy. Incremental projection advances healthy evidence only from an exactly healthy base. Derived-index failure boots degraded with canonical memory available; only unreadable canonical memory aborts startup.
- `HarnessWiring` registers the four-tool memory contract in endpoint and direct-SDK modes: `memory_apply` and `memory_observe` are writes; `memory_search` and `memory_read` are read-only. Write provenance comes only from host-owned context – the active turn for direct SDK calls, or the authenticated principal plus a unique host-generated call event for a container bridge.
- `HarnessWiring` composes the primary static prompt from the shared corpus authority. Human channel/web turns use `PromptScope.primary`; scheduled, workflow, extraction, and logical-agent turns pass `PromptScope.task` explicitly.
- `HarnessWiring` handles Claude `PreCompact` by persisting a redacted, UTF-8-bounded conversation-tail observation with host session provenance before the harness acknowledges the hook.
- `SchedulingWiring` owns built-in job and immutable system-action registration plus reserved-ID collision checks. The opt-in `memory-journal` job is prompt-based; `memory-curation` is always registered as explicit run-only work with no schedule. The hourly `credential-health` job comes from the top-level `buildCredentialHealthJob`, and `wire()` probes once during wiring so a `serve` started with an already-degraded credential reports it immediately; `service_wiring.dart#_wireCredentialHealth` builds the per-probe resolution closure over the live `ProviderStatusService` the API reads, rebuilding the registry from the context-held `SubscriptionCredentialStore` each run so a renewed credential is seen without a restart.
- **The credential-health monitor is late-bound into `SecurityWiring`, `HarnessWiring` *and* `TaskWiring`.** All three are constructed before the monitor, which needs the built `ProviderStatusService` at step 8, so `service_wiring` assigns `security.credentialHealth`, `harness.credentialHealth` and `task.credentialHealth` there rather than passing a constructor argument — never construct a second monitor, and never reorder the steps to avoid the setters. `HarnessWiring` is the **host** boundary's producer: `_reportHostCredentialHealth` is fed by the `createWorker` credential refusal and by `prepareCodexSubscriptionHome`'s `onCredentialHealth` sink, because a host-execution deployment builds no gateway and would otherwise get no FR6 event at all — only the hourly probe, which cannot see a refresh failure. Its refusals report `reauth-required`; a transient Codex refresh failure reports `refresh-failure`. The **primary** lane is outside that producer entirely: `_primaryContainerManager` throws `StateError(verdict.message)` on an unsupported verdict, reporting nothing and logging nothing — its spawn precedes step 8, so the operator meets the refusal as a failed startup carrying the gate's own message, not as a credential-health transition or a severe log line. `TaskWiring` is the same producer for the in-`serve` workflow one-shot lane, which spawns on the host too — its own `_reportHostCredentialHealth` carries the identical no-monitor degradation, and its spawns all happen well after step 8. The **standalone** `dartclaw workflow` lane (`CliWorkflowWiring`) deliberately has no sink: it is its own process, builds no `ProviderStatusService`, and installs no root-logger listener (`LogService.install()` runs only in `serve_command.dart`), so both a monitor and its severe-log degradation would be inert there — its refusal reaches the operator as the step failure, which is why threading `credentialsDir` still matters. `SecurityWiring` has exactly two report sites, both single call sites: `_reportCredentialRefusal` (the gateway's `onCredentialRefused` sink, admission and mid-turn, reporting `reauth-required`) and `_reportCodexCredentialHealth` (fed by `CodexCredentialSource.onRefreshOutcome` and `OpenAiResponsesAdapter.onRejection`; a spent refresh token and a 401 report `reauth-required`, a transient refresh failure `refresh-failure`, a scheme rejection `contract-break`). A rotated-away credential, a 429 usage limit and a rejected model are **not** credential conditions and must not report — paging for a re-login there is a false alarm. Both sites keep their log line as the no-monitor degradation FR6 requires; do not write it alongside a report, since the monitor logs its own transition.
- Local `dartclaw status` reads persisted corpus and index evidence without starting services or rescanning corpus members; `rebuild-index --json` reports revision, indexed rows, and resulting health.
- AOT build target: avoid `dart:mirrors`, runtime `import` strings, and reflective package APIs anywhere reachable from `bin/dartclaw.dart`.
- `dartclaw init` supersedes the removed `deploy setup` command. Prerequisite checks live in `init/setup_preflight.dart` — extend that, don't reintroduce a `deploy setup` subcommand.
- **Release binaries are built with `dart build cli`, not `dart compile exe`.** `dev/tools/build.sh` runs `dart build cli` so the sqlite3 build hooks emit a bundled `libsqlite3` in a sibling `lib/` next to the binary. `dart compile exe` silently produces a sqlite-less binary here (its build-hook check classifies by the workspace-root pubspec — dart-lang/sdk#62593), which crashes at the first SQLite call on Linux. SQLite is bundled by default (no committed `hooks.user_defines.sqlite3.source: system` block). The only sanctioned local escape hatch is an *uncommitted* `source: system` edit for macOS codesign-blocked iteration — documented in `dev/guidelines/KEY_DEVELOPMENT_COMMANDS.md`; never commit it.
- `ReleaseSqliteCheckCommand` is hidden release-pipeline infrastructure. On Windows it maps `package:sqlite3`'s bound `sqlite3_libversion` symbol to its loaded DLL and verifies the expected module path plus FTS5 behavior; keep it registered in the AOT entry point.
- **Every host spawn-env builder overlays the credential through one helper.** `overlayProviderCredential` (`commands/provider_credential_environment.dart`) runs *after* `SafeProcess.sanitize` in all three: `wiring/harness_wiring.dart#_providerEnvironment` (primary + workers), `wiring/task_wiring.dart#_providerEnvironmentForWorkflow` (in-`serve` workflow one-shots), and `workflow/workflow_provider_environment.dart#buildWorkflowProviderEnvironment` (the standalone workflow lane *and* every probe). Adding a fourth builder without it is how a lane silently spawns uncredentialed. **A Codex subscription is a credential too, and it is presented as `CODEX_HOME`, not as a variable the resolution can hand over.** The execution lanes get that home from the harness or the one-shot provider driver, resolved per spawn (`prepareCodexSubscriptionHome`); a **probe** — skill introspection and the CLI auth preflight — runs the vendor binary with nothing downstream, so it must resolve the home itself and pass it into the same helper: that is `buildWorkflowProbeEnvironment`, used by all three probe lanes (`service_wiring.dart#_providerProbeEnvironment`, `CliWorkflowWiring.providerProbeEnvironment`, `workflow/workflow_validate_command.dart`). The probe env builders are therefore `async`, and so are `SkillProbeEnvironmentBuilder`/`AuthProbeEnvironmentBuilder`. A probe lane that overlays nothing for a Codex subscription is *not* harmless: the vendor CLI falls back to the operator's own `~/.codex`, or fails the turn and reports it as a skill-introspection error long after auth was declared fine. Every one of them derives its family with `ProviderIdentity.resolveFamily` (executable-aware) — `ProviderIdentity.family` is plain normalization and misclassifies a provider alias as its own family, which is exactly how an aliased Claude provider ends up spawning with no credential. A claude-family spawn presents exactly what the resolution names — `CLAUDE_CODE_OAUTH_TOKEN` for a stored `setup-token`, the API-key variables for a key, **nothing** when `providers.<id>.auth` rules both out; other families keep the plain API-key overlay. The order matters: sanitize strips every inherited `*_TOKEN`, which is what makes the dedicated store authoritative over an operator's own exported value — never weaken that pattern list to "fix" it.
- **An ACP registration is credential-isolated, and that is the whole rule.** For a provider id under `harness.acp.agents`, `_providerEnvironment` takes the `overlayAcpCredential` branch instead of `overlayProviderCredential`: no `providers.<any>.auth` or `credentials.anthropic|openai` is consulted, `_subscriptionHomeFor` answers `null` before it resolves a family (a dedicated `CODEX_HOME` *is* the subscription presentation), and `_credentialRefusalFor` keeps its ACP skip. `model_provider` routes and validates; it selects no credential — the mapping that turned `anthropic`→`claude` and `openai`→`codex` was removed in 0.24.2, so do not reintroduce a credential-provider-id translation anywhere. The one injection path is `harness.acp.agents.<id>.credential`, a `credentials.<name>` **API-key** reference; config load drops and warns about every other shape (unknown name, `github-token`, empty value, literal key with no `${VAR}` name), and the overlay fails closed on the same rule. Sanitize still strips the agent's own inherited `*_API_KEY`/`*_TOKEN` — intended: the agent reads its own config or keyring.
- **One `CodexRefreshAuthority` per process, constructed beside the store it rotates.** `ServiceWiring.wire` builds it on the `_WiringContext` and threads the same instance into `SecurityWiring` (the gateway's `CodexCredentialSource`), `HarnessWiring` (long-lived host spawns) and `TaskWiring` (workflow one-shots). The standalone workflow lane is its own process, so `CliWorkflowWiring._wirePrelude` builds its own single instance beside the store it opens there and injects it as `WorkflowCliRunner.subscriptionHomeResolver` — without it a `dartclaw workflow` run spawns Codex against the operator's `~/.codex`. `workflow validate --skills` is a third process with a third store open, so `_buildIntrospector` builds one there too, beside that store. Single-flight is a property of the instance, so a second authority is a second refresher — never construct one inside a wiring class or a per-request closure. Host Codex spawns reach it through `prepareCodexSubscriptionHome` (`commands/codex_subscription_home.dart`), which answers `null` only when a credential is genuinely presentable another way — a resolved API key, or nothing selected at all (`noneConfigured`) — and **throws** for every other unavailability reason and for a terminal refresh outcome: returning `null` there would spawn against the operator's own `~/.codex` login, which this deployment must never read. `apiKeyAbsent` is a throw for exactly that reason; it reads as the mildest case and is the one where the fall-through hurts most. Refusal text comes from `credentialRemediationFor` — never hand-author one here — and travels with `credentialsDir` so the operator learns which store was searched.
- **`SubscriptionCredentialStore.open` belongs in a lane's composition root only.** Five sites, one per lane: `ServiceWiring.wire` (`serve` — held on the wiring context and shared with security/harness/task wiring), `CliWorkflowWiring` (standalone workflow lane), `workflow_validate_command` (one-shot validate), `commands/auth/auth_subcommand.dart#AuthSubcommand.openStore` (the `dartclaw auth` group, opened once per invocation), and `commands/service/setup_verifier.dart` (`dartclaw init` verification, opened once per verification). Never open it inside a per-request or per-provider closure; opening creates and chmods directories and runs the login-collision guard. `ServiceWiring` takes an `environment` argument (defaulting to `Platform.environment`) purely so that guard is testable: the collision is resolved from `CODEX_HOME`/`CLAUDE_CONFIG_DIR`/`HOME`, and without the seam the only way to provoke one is to write into the developer's real `~/.codex`. In `serve`, every consumer that resolves a credential *after* wiring rebuilds its registry per use, so a re-issued token is picked up without a restart: `security_wiring`'s gateway adapters, `harness_wiring`'s worker spawn env, `service_wiring`'s probe lane, its workflow auth preflight (a supplier, not a snapshot, so a credential stored after startup passes the gate — but for Claude the gate then outruns the spawn behind it, whose env is the startup snapshot named below, so a token stored after `serve` started is not *presented* until restart; only the Codex home is re-resolved per spawn, via `subscriptionHomeResolver`) and its hourly credential-health probe, and `task_wiring`'s per-spawn Codex dedicated-home resolver. What still snapshots at wiring time is the in-`serve` workflow one-shot spawn env, frozen into `WorkflowCliProviderConfig` at startup, and the standalone lanes, which are their own processes and spawn from the snapshot they gate on.
- **`CredentialRegistry`'s `providers:`/`subscriptions:` arguments default to empty, and every construction site must decide.** A site that omits them silently resolves as if no subscription credential and no `providers.<id>.auth` existed — the analyzer says nothing. Pass both at any site feeding a spawn env, a mediation adapter, or an auth decision (`service_wiring`, `harness_wiring`, `security_wiring`, `task_wiring`, `cli_workflow_wiring`, `workflow_validate_command`, `setup_verifier`). `setup_verifier` resolves the full picture — an unusable store degrades to "no subscription stored" rather than failing the verification — and falls through to the vendor `probeAuthStatus` only on `noneConfigured`, mirroring `ProviderValidator`.
- **Workflow provider spawn env must keep `USER`.** `buildWorkflowProviderEnvironment` (`commands/workflow/workflow_provider_environment.dart`, the seam behind `_providerEnvironment`) sanitizes with no allowlist, so `USER` survives — the standalone `claude` CLI reads its keychain subscription OAuth only when `USER` is present (`HOME`+`PATH` alone → "not logged in"). Never add an allowlist that drops it; a regression test pins this.
- **Standalone workflow wiring runs the CLI auth preflight *before execution setup*.** `CliWorkflowWiring` is two-phase: `wireBaseServices()` completes the prelude/storage/task-layer/registry (registry `continuityProviders` come from `HarnessFactory.probeContinuityProviders()` capability probes, `cwd:'/'`, no spawn); `wireExecutionServices(providers)` configures capacity and dependent services for the referenced providers. Workflow one-shots acquire capacity-only leases, so capacity is bounded without an unused streaming harness. The standalone run/resume/retry paths resolve the definition, derive `requiredWorkflowProviders`, call `preflightProviderAuth(set)` (friendly `WorkflowPreflightException` → printed remediation + exit 1), then `wireExecutionServices(set)` – so a logged-out referenced provider aborts before execution setup, and an unreferenced logged-out default is never auth-probed. The prelude opens DartClaw's dedicated credential stores for this process, so a provider whose only credential is a stored subscription token preflights as authenticated without spawning the vendor CLI probe. The `wire()` facade combines both phases for tests and callers that do not gate auth. The executor-level preflight (`dartclaw_workflow` `workflow_skill_preflight.dart#_preflightProviderAuth`) is the in-engine backstop, but **it is inert unless a lane injects `WorkflowServiceOptions.providerAuthPreflight`** (`if (providerAuthPreflight != null)`) — both lanes must, and both do: `CliWorkflowWiring._wireWorkflowService` for the standalone lane and `service_wiring.dart#_wireWorkflowService` for the in-`serve` one-shot lane. It is a **partial** backstop even where injected: it probes only the providers a skill-bearing agent step references, so a step that names none is preflighted by nothing. What a lane omitting it falls back to differs by lane, because `WorkflowCliRunner._requireSupported` is only as strong as the inventory injected into it: the in-`serve` lane gets `HarnessWiring`'s, which carries the credential gate, so the spawn is still refused (in the inventory's words, not the preflight's); the standalone lane builds its own with **no** `credentialGate`, so there the preflight is the only credential gate and omitting it spawns the step's host CLI ungated.

## Testing
- `dart_test.yaml` defines tag `integration` (skipped by default). Run live e2e with `dart test --run-skipped -t integration apps/dartclaw_cli/test/e2e/server_builder_integration_test.dart`.
- Unit tests under `test/commands/**` mirror `lib/src/commands/**`. They drive commands through `DartclawRunner.run([...])` with fakes injected via constructor — see `runner_test.dart` and `serve_command_test.dart` for the pattern. Shared test doubles live under `test/helpers/`: `fake_api_transport.dart` (`FakeApiTransport` + `jsonResponse`), `fake_exit.dart` (`FakeExit` marker + `fakeExit` for `exitFn`), `capturing_stdout.dart` (`CapturingStdout` for `IOOverrides`). Reuse them, do not re-roll.
- Wiring split-out tests live under `test/commands/wiring/` matching `lib/src/commands/wiring/`. Add a focused test there when introducing a new wiring step.
- **`Directory.current` is process-wide, and suites share the process.** `dart test` runs suites as concurrent isolates in one process, so a suite that sets `Directory.current` (`cli_workflow_wiring_test`, `init_command_test`, `workflow_run_command_standalone_test`) moves the cwd for every suite running alongside it. Never let a test depend on the cwd: `ServerConfig.templatesDir`/`staticDir` default to repo-root-relative paths, so pass absolute paths (see `serve_command_test.dart`'s `setUpAll`) rather than relying on the cwd or `Directory.current.path`.
- **Don't size a wait to just clear a threshold.** Poll until the expected state with a generous cap instead (`_pollFor` in `harness_wiring_test.dart`, `_waitForCount` in `reload_trigger_service_test.dart`). A fixed delay a few ms past a debounce or turn-monitor threshold passes locally and fails under parallel load.

## Workflow standalone-run observability
- `commands/workflow/standalone_run_harness.dart` renders step/iteration completion with inline reasons (`failed — <reason>`, `blocked (recoverable): <reason>`, `interrupted (resumable): <reason>` for teardown-cancelled steps) and forwards additive `outcome`/`reason` keys in `--json`. At settle it prints a per-story digest (human + a single `workflow_run_digest` JSON object).
- `commands/workflow/workflow_run_digest.dart` is the shared digest builder (one builder, two renderers: `renderWorkflowRunDigestLines` + `WorkflowRunDigest.toJson`). Per-step status uses the workflow package's `stepStatusFromTask` plus the persisted `step.<id>.outcome`; a raw `cancelled` row under a paused run rolls up as `interrupted` (resumable teardown, not terminal). Reasons are scrubbed at the builder so both renderers emit clean values. Next-actions derive from the settle status; a cancelled run gets none (retry is failed-only).
- Agent-derived strings (step failure/blocked/interrupted reasons, pause reasons, approval messages, run `errorMessage`, display scopes, task titles) are scrubbed at the printer boundary via `commands/workflow/agent_text_scrub.dart` (`scrubAgentReportedText`: strip ANSI/CSI + C1 control chars, collapse whitespace, truncate) — apply it to any new sink that prints agent-reported text; never print such values raw.
- `commands/workflow/cli_progress_printer.dart` has `stepBlocked` for the recoverable-hold line and `stepInterrupted` for teardown-cancelled steps; on an interactive TTY it renders a live spinner via `commands/workflow/live_status_line.dart`. Live per-step token ticks come from `WorkflowCliTurnProgressEvent`; codex emits on `turn.completed`, and claude emits once per completed assistant message. The CLI and SSE transports consume the event provider-agnostically.
- **Live entries retire at task settle, not at the step barrier.** For parallel groups the engine fires `WorkflowStepCompletedEvent` only after the whole group drains, so both drivers (standalone `standalone_run_harness.dart` and connected `workflow_run_command.dart`) watch `TaskStatusChangedEvent` for terminal/`interrupted` statuses (`taskSettlesLiveEntry`) and call `printer.stepSettled(taskProgressKey(taskId), countTokens: <accepted>)` – otherwise the live line overcounts "N steps running" and retry-replaced task ids leave stale entries. `LiveStatusLine.settleStep` folds only an `accepted` member's live-tick tokens into the run total (failed/cancelled/interrupted settles drop them: the barrier's step `tokenCount` accumulates across retry attempts, and interrupted members stay uncharged – folding would double-count); the barrier's `completeStep` reconciles against the authoritative count instead of double-adding. Permanent completion lines and `--json` framing still come from the barrier events – don't move them to settle time.
