# ADR-053: Subscription-Default Provider Authentication via Host-Mediated OAuth

**Status:** Accepted – 2026-08-14 (0.24.2 correction; owner-ratified 2026-08-14)
**Deciders:** DartClaw team (owner-ratified 2026-08-14)

**Related:** [ADR-001](001-sdk-integration-and-security-architecture.md) (security architecture, original credential-proxy pattern), [ADR-015](015-container-isolation-strategy.md) (hardened `network:none` boundary), [ADR-051](051-container-bridge-binary-packaging.md) (host gateway bridge), [ADR-052](052-native-provider-web-tools-denied-all-container-profiles.md) (host gateway as the provider-traffic enforcement point), [ADR-037](037-universal-acp-harness.md) (**amended 2026-08-17**: ACP registrations are excluded from this credential model — no subscription token, no implicit `model_provider` mapping). Supersedes the 0.24 posture "containerized Claude supports API-key mediation only; OAuth/setup-token authentication remains host-only" (`dev/architecture/security-architecture.md` § Credential Security; 0.24-execution-isolation PRD, commit `fcc3a759`).

---

## Context

0.24 replaced the credential proxy with the per-authority host gateway: a containerized execution reaches its provider only through a framed `docker exec` pipe, the container stays `network:none`, and provider credentials never enter the container. To ship that boundary on time, 0.24 restricted **containerized Claude to a host-held `ANTHROPIC_API_KEY` only** and rejected subscription logins, on the stated grounds that there was "no verified credential-free gateway contract" for them. The host `~/.claude.json` mount was removed.

The practical effect: the only way to run a containerized agent is a per-token-billed API key. That is not an acceptable **default**. Most operators hold a Claude (Max/Pro) or ChatGPT subscription, not a metered API account; forcing an API key makes the secure container path the expensive one and pushes operators to `execution: host`. The requirement for 0.24.2: subscription auth is the default on both execution boundaries, mediated by the host so the credential never enters the container, easy to set up, with clear operator visibility.

Four investigations settled the design:

- **Claude wire + refresh (spike `spike/oauth-gateway-mediation`, commit `fd39035b`).** A real `claude` CLI in a clean home with a dummy key, routed through a stand-in gateway that strips the client credential and injects a host-held `sk-ant-oat01` OAuth Bearer, completes its turn – container credential-free. Host-side token read and refresh mechanics verified. (The spike exercised the interactive OAuth token; the chosen credential is the static `setup-token`, the same `sk-ant-oat01` family per Anthropic's auth docs – a setup-token-specific wire check is a cheap spec-time confirmation.)
- **Codex container mediation (spike, scratchpad `codex-spike/`; verified against `openai/codex` `rust-v0.146.0`).** Proven **end-to-end**: a `network:none` container holding no credential received a real, subscription-billed completion. Codex's ChatGPT backend (`https://chatgpt.com/backend-api/codex`) accepts a plain `Authorization: Bearer <access_token>` + `ChatGPT-Account-ID` with a standard Responses body – no codex process need run for the credential to work, so the container can be a dumb client (refuting the earlier "requires app-server" lead). Negative control: the same token against `api.openai.com/v1/responses` returns 403 "missing scopes" – the gateway must **re-pin the upstream host**, not merely swap the credential.
- **Terms of service (current, Aug 2026).** The February 2026 restriction on subscription OAuth tokens in third-party tools was **superseded**. Anthropic's current Help Center (updated ~June 16 2026) names *"third-party apps that authenticate with your Claude subscription through the Agent SDK"* as a supported category drawing on ordinary subscription limits; the current Claude Code auth docs sanction `CLAUDE_CODE_OAUTH_TOKEN` for "CI pipelines, scripts, or other environments" with no third-party restriction; the live Consumer Terms (Oct 2025) carry no OAuth prohibition. OpenAI issued no equivalent ban and supports ChatGPT-account auth. **Residual, disclosed:** no primary source names the exact raw direct-`/v1/messages` Bearer-replay form our container gateway uses; it is the identical wire behavior the sanctioned Agent SDK produces, so it is permitted-by-equivalence, not explicitly blessed in those words. The API-key path remains for operators who want to avoid that residual ambiguity.
- **Field learnings + existing seams.** Comparable runtimes confirm the direction (static `setup-token` over mediated interactive OAuth; dedicated single-writer store over sharing the operator's login; host-mediated injection over an unfinished egress proxy) and the traps to avoid (plaintext stores, re-seeding a rotated store, sharing one store across concurrent refreshers). The credential-health surface reuses existing infrastructure: `AlertRouter`, `ProviderStatusService` + the `/settings` provider cards, scheduled-job registration, and the `secureWriteFileSync`/`chmodOwnerOnlySync` helper.

### Decision drivers

- **Secure path must be the easy path** – the container boundary should use the subscription the operator already has, not demand a metered key.
- **Credential stays on the host** – container remains `network:none` and credential-free; the host injects auth per authority (the 0.24 contract, unchanged).
- **No over-engineering** – static tokens where the provider offers them (Claude); for the one rotating credential (Codex), reuse the vendor's own refresh and exploit DartClaw's single-threaded runtime for trivial single-flight – no bespoke OAuth client.
- **No shared-store race** – DartClaw never reads or writes the operator's interactive login store; it owns dedicated stores.
- **Operator visibility** – expiry and required manual re-auth are surfaced through existing alert and status surfaces, not buried in a startup log line.
- **Baseline integrity** – reversing a documented 0.24 security posture is recorded, not left as drift.

## Decision

**Subscription authentication is the default for both Claude and Codex, on host and container execution, mediated by the host so the credential never enters the container. API key remains a supported alternative – no longer the default – and is the recommended choice for least-privilege or independent-billing deployments.**

### Credential per execution cell

| | Host mode | Container mode |
|---|---|---|
| **Claude** | `setup-token` supplied as `CLAUDE_CODE_OAUTH_TOKEN`; the real `claude` CLI makes its own calls (first-party Agent-SDK-sanctioned) | Host Anthropic adapter injects `Authorization: Bearer <setup-token>` (+ `anthropic-beta: oauth-2025-04-20`) and drops client auth; container `network:none`, dummy/no key |
| **Codex** | ChatGPT login in a DartClaw-dedicated `CODEX_HOME`; the real `codex` CLI owns refresh in that store | Host adapter re-pins upstream to `https://chatgpt.com/backend-api/codex` and injects `Authorization: Bearer <access_token>` + `ChatGPT-Account-ID`, read per request from the dedicated store |

API key (Anthropic Console / OpenAI Platform), when configured, is used where no subscription credential is present, and takes precedence only when the operator selects it explicitly (see precedence, below).

### Credential storage and refresh

- **Dedicated stores, single writer.** Claude's `setup-token` and Codex's ChatGPT `auth.json` live in DartClaw's own credential store, never the operator's `~/.claude` Keychain item or `~/.codex`. Written with the existing `secureWriteFileSync` (atomic temp+rename, `chmod 600`; `0700` dir). Contents never enter logs, `dartclaw status`, or audit – reference by name only; redaction covers both `sk-ant-*` and JWT-shaped tokens.
- **Claude: static, no refresh.** The `setup-token` is a ~1-year non-rotating token. Nothing refreshes it; the gateway injects it directly. Renewal is a re-run of `claude setup-token`.
- **Codex: one refresh authority per store, single-flight.** The ChatGPT token rotates one-time-use, so the dedicated store must have exactly one refresher. DartClaw owns the store as that authority and does not permit a second autonomous refresher – the vendor CLI's own refresh in host mode – to rotate the same store concurrently; a freshness gate keeps DartClaw's own refreshes serialized; because the vendor CLI (minutes-scale access token) may still rotate the store during a host turn, rotated-away recovery re-reads the vendor-rotated store rather than asserting an unachievable cross-process single-refresher invariant (the gate mechanism is settled in the FIS). Within DartClaw, single-flight is an explicit contract, not a free consequence of the single-threaded runtime: the in-flight refresh is a memoized `Future` inserted before the first `await`, so concurrent callers await one upstream token call rather than each starting their own. Refresh reuses the vendor's own mechanism: DartClaw drives `codex app-server` (JSON-RPC `getAuthStatus`/`account/read`) so the vendor's `AuthManager` performs and persists the refresh; DartClaw never POSTs the token grant itself (proven against `rust-v0.146.0`, spike `d6be6e61`). The inject path checks expiry, **awaits** the single-flight refresh when the token is near or at expiry, then reads and injects – re-reading the store per request alone is insufficient, since it can otherwise inject a just-expired token mid-turn. Success is confirmed by re-reading `auth.json`, not the RPC result; a terminal refresh (expired refresh token) escalates to interactive `codex login`. A concurrency test asserting that two simultaneous DartClaw-side refreshes make exactly one token-endpoint call is required; vendor-CLI rotation is covered by rotated-away recovery, not a cross-process race test.

### Fail-closed and precedence

- **Fail-closed.** An absent, expired, or refresh-failed credential (of whichever type would be presented) is refused at execution admission – container-authority registration *or* host-worker startup, before any turn runs – identical in spirit to the 0.24 missing-key gate, and covering host mode, which creates no container authority. A nearing-expiry credential warns; an unusable one refuses. No warning-only path that lets a doomed turn start. The refusal path emits the same credential-health alert event as the scheduled probe, so a credential that expires *between* probe runs still notifies the operator instead of silently refusing turns; the probe interval is set well below the Codex refresh-token lifetime so re-login is prompted before hard failure.
- **Precedence.** When both a subscription credential and an API key are configured for a provider, subscription is used by default; an explicit operator selection (config) chooses the API key. Exactly one is presented upstream per authority.

### Operator visibility (reuses existing seams)

- **Notifications.** Credential-health degradation (nearing expiry, refresh failure, re-auth required) emits a new `DartclawEvent` consumed by `AlertRouter`, delivered to configured alert targets – the same path as `container_crash`/`job_failure`. Manual action required (Claude annual re-token; Codex re-login when the refresh token fully expires) is surfaced here, not only at startup.
- **Web UI.** `ProviderStatusService`/`ProviderStatus` already models `credentialStatus`/`health`/`AuthProbe` and renders per-provider cards on `/settings`. Extend `ProviderStatus` with expiry / last-checked / reauth-required fields and render them on the existing cards – no new page.
- **Scheduled check.** A built-in `ScheduledJob('credential-health', …)` registered in `SchedulingWiring` (alongside `memory-pruner`/`session-maintenance`) probes expiry periodically and emits the alert event – so a months-long `serve` surfaces expiry without a restart.

## Consequences

**Positive**
- The secure container path uses the operator's existing subscription with a one-time setup; API keys are no longer required to run a contained agent.
- Container boundary unchanged and unweakened – still `network:none`, still credential-free; only the injected credential changes.
- Refresh is clean: Claude needs none; Codex reuses the vendor's own refresh behind a trivial single-flight; no bespoke OAuth machinery to rot.
- Dedicated stores never collide with the operator's interactive logins.
- Expiry and required re-auth are visible through channels and the `/settings` cards, not a lost log line.
- Credential-health is mostly wiring over existing seams (alerts, provider status, scheduling, atomic write).

**Negative / accepted**
- **Blast radius.** A subscription Bearer authenticates as the operator's whole account and is longer-lived and harder to revoke than a scoped API key. The container boundary prevents capture/exfiltration and short authorities bound the window, but a compromise anywhere drives calls under a broader-scope credential. Operators wanting least privilege or independent revocation configure an API key.
- **Host-mode credential exposure.** The container boundary protects only container mode. In host mode the credential is present to the agent's own subprocess – Claude via `CLAUDE_CODE_OAUTH_TOKEN` in the environment, Codex via `CODEX_HOME` – so a host-mode agent with shell access can read and exfiltrate it, and a ~1-year full-account subscription Bearer is a worse loss than the revocable scoped API key it replaces. Host mode already assumes a trusted local agent (pragmatic mode), but making subscription the default everywhere raises the stakes; an API key is recommended for host-mode deployments running less-trusted agents.
- **Raw-replay ToS residual on the default path.** Host-mode Claude uses the real CLI (fully Agent-SDK-sanctioned); only container mode uses the direct Bearer form, which is permitted-by-equivalence to the Agent SDK but not named by a primary source – and container is the default, so most operators get the one path with disclosed ambiguity. If Anthropic later distinguishes raw-replay from SDK auth, default container deployments are offside at once. The API-key "ToS-conservative" option is surfaced prominently in operator docs, not only here.
- **Codex backend contract is unpinnable.** Container-mode Codex mediation depends on the ChatGPT-backend Bearer contract, which lives server-side at `chatgpt.com` – the container image pins the codex *binary*, not this backend behavior, so a backend change (e.g. enabling `use_agent_identity`, default-off at 0.146, replacing Bearer with device-keypair assertions) would silently break every default container-Codex deployment regardless of the pinned binary. Treated as best-effort, not durable: the credential-health probe must detect a contract-break 4xx signature distinct from expiry and alert on it. The subscription model set also differs from Platform.
- **Two provider-shaped setups.** Claude is a static annual token; Codex is a dedicated device-code login whose rotating store DartClaw persists. Parity is at the mechanism level (host-mediated, container credential-free), not the credential type.
- **Subscription limits.** Subscription usage draws on plan rate/usage limits rather than metered API capacity.

## Alternatives Considered

1. **Keep API key as the default (0.24 posture / OpenClaw's recommendation)** – rejected against the requirement; makes the secure path the metered, high-friction path. Retained as an explicit alternative.
2. **Mediate the interactive login token with host-side refresh** – rejected. The interactive access token is short-lived and its refresh token rotates single-use against the operator's own store; static `setup-token` (Claude) and a dedicated store (Codex) avoid the race.
3. **Re-mount the host login into the container (pre-0.24)** – rejected; puts a reusable credential inside the boundary. Removed in 0.24, not reintroduced.
4. **Run a host-side Codex app-server the container talks to (OpenClaw's login-RPC shape)** – rejected. Bearer injection at the gateway achieves the same with no extra process; the app-server login RPC it relies on is marked "FOR OPENAI INTERNAL USE ONLY" behind an experimental capability.
5. **Build a sandbox egress proxy for subscription traffic** – rejected. DartClaw's `network:none` + `docker exec` pipe is simpler and more complete than the MITM/sentinel proxy pattern (which comparable projects have not finished wiring to sandboxes); don't regress toward it.

## Project Compliance

Smallest change that meets the requirement (reuse the host-gateway mediation shape; inject a subscription credential instead of a key), reuse before build (Claude's first-party `setup-token`, Codex's own refresh, the existing `CredentialRegistry`, `AlertRouter`, `ProviderStatusService`/`/settings`, `SchedulingWiring`, `secureWriteFileSync`), root cause over workaround (fixes the API-key-only default rather than documenting around it), and security posture preserved and stated honestly (container stays `network:none` and credential-free; the host adapter remains the enforcement point per ADR-052; the ToS residual and Codex version-pin are disclosed).

## Implementation Notes (for the spec, not blocking this decision)

- **Seams (from recon).** Credentials: `dartclaw_config/lib/src/credential_registry.dart`, `credentials_config.dart` (extend `CredentialType` with an OAuth/expiry shape). At-rest: `dartclaw_core/lib/src/storage/atomic_write.dart`. Notifications: `dartclaw_server/lib/src/alerts/` (`AlertRouter`; add a `credential_expiry`/`reauth_required` event + classification). Web UI: `dartclaw_server/lib/src/provider_status_service.dart` + `web/pages/settings_page.dart`. Scheduling: `apps/dartclaw_cli/lib/src/commands/wiring/scheduling_wiring.dart`. Codex CLI OAuth detection: `dartclaw_config/lib/src/provider_validator.dart` (`probeAuthStatus`).
- **Codex upstream re-pin** – the adapter must target `https://chatgpt.com/backend-api/codex` (not the Platform Responses API) and constrain to that host/path; the configured container model must be one of the subscription-supported models.
- **setup-token wire check (pre-ship gate)** – the spikes proved the interactive OAuth token; container-mode Claude's default credential is the `setup-token`. Its ~1-year lifetime is confirmed by Anthropic's current auth docs; its acceptance as a raw Bearer through the gateway is the residual assumption. Confirm the wire acceptance before shipping container-mode Claude as the default; cheap and mechanical.
- **Codex refresh mechanism (resolved)** – the freshness gate refreshes by driving `codex app-server` over JSON-RPC (`getAuthStatus` with no flags for the idempotent conditional refresh; `account/read {refreshToken:true}` to force), letting the vendor `AuthManager` rotate and persist `auth.json`; success is confirmed by re-reading `last_refresh`, not the RPC result. `getAuthStatus` is deprecated at `rust-v0.146.0` – re-verify on codex upgrades (fallback: scheduled `account/read`). The FIS pins the single-flight `Future` contract (synchronous insertion before first `await`, one DartClaw-side token call), the await-before-inject rule, and rotated-away recovery for concurrent vendor rotation, with a concurrency test proving one token-endpoint call under simultaneous DartClaw refresh. Evidence: spikes `spike/oauth-gateway-mediation` at `ec3071b5` (container mediation) and `d6be6e61` (refresh).
- **Linux credential store** – the host read path differs from macOS Keychain (`~/.claude/.credentials.json`, `~/.codex/auth.json`); the store abstraction covers both.
- **Breaking change** – ship in 0.24.2 but flag explicitly breaking in the CHANGELOG: the default auth changes; operators may need to run `claude setup-token` / Codex login or set an API key.
- **Evidence** – both on branch `spike/oauth-gateway-mediation`: Claude wire+refresh at commit `fd39035b` (`dev/spikes/oauth-gateway-mediation/`), Codex container end-to-end at commit `ec3071b5` (`dev/spikes/codex-container-mediation/`, verified against `openai/codex rust-v0.146.0`).
