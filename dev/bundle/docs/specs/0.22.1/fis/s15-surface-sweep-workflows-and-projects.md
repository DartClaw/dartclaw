# Surface sweep: workflows and projects

**Plan**: docs/specs/0.22.1/plan.json
**Story-ID**: S15

## Feature Overview and Goal

**Intent**: The workflow surfaces carry the release's single largest adoption debt and its only self-contradicting data – canon ships a run-board card and a pipeline spine that are used zero times while `app.css` re-implements both with far less anatomy, and the run view-model reports a Completed run as `0/0 steps` at 0 %; projects, meanwhile, hangs its entire card anatomy on six classes that have no CSS in any stylesheet.

**Expected Outcomes**:

- [OC01] The workflow list and detail render from the canonical run-board, pipeline, metric and approval families – no page-local fork of a family canon ships remains, and every class these surfaces emit resolves to a real rule.
- [OC02] Progress agrees with status and never fabricates data: an unknown step count is stated as unknown, a Completed run reports 100 %, and a Failed run's progress does not render in the success hue.
- [OC03] A project card is a composed card with a real error treatment, and a project mutation updates the list in place instead of discarding the page.
- [OC04] The workflow surfaces state what they do not know: an empty run list, an empty pipeline and a terminal run each get a designed treatment rather than a bare sentence, a floating dash, or an empty action rail.

## Architecture Decision

**Approach**: adopt, do not extend – every fork on these surfaces is deleted from `app.css` and its markup re-rendered from the canon family that already ships (`.run-card`, `.pipeline`, `.approval-card`, `.card-metric`, `.card-header` / `-footer`, `.banner-error`, `.empty-state`); the only genuinely new logic is an honest step count and status-coupled progress in the two presentation view-models.
**Why this over alternatives**: styling the six dead `.project-card-*` classes, or patching `.workflow-step-*` in place, would leave two implementations of families canon already defines – a divergence the drift check cannot see, and exactly the rot 0.22 produced.

## Constraints & Gotchas

- **Critical**: the cascade defeats markup-only container changes -- `.workflow-list-page` and `.workflow-detail-page` hardcode `max-width: 900px` in `app.css`, which loads after `design-system.css` at equal specificity, so adding the wide modifier to the markup alone changes nothing. Must handle by: deleting the two `max-width` declarations in the same task that applies the modifier, keeping the class heads (both are live `dc_workflows_controller.js` and test selectors).
- **Critical**: `.workflow-step-*` is two families under one prefix -- the spine (`-wrapper`, `-connector`, `-card`, `-active`, `-icon`, `-header`, `-name`, `-type`, `-expand-icon`, `-task-link`) is retired; the step-detail fragment (`-detail`, `-detail-loading`, `-detail-content`, `-chat`, `-no-session`, `-artifacts`, `-context-io`, `-metrics`, `-metric-value`) and the sidebar's `.workflow-step-progress` (`app.css:2929`, consumed by `sidebar_sections.js`) are not. Must handle by: enumerating the retired names explicitly in every grep and deletion; a prefix sweep breaks the sidebar and the step detail.
- **Critical**: `rg -c` exits 1 and prints nothing when there is no match -- it does not print `0`. Every "must be gone" check in this FIS is written as *exits with code exactly 1*; exit 2 means the search itself failed and is not a pass.
- **Constraint**: rendered Trellis output is not the template source -- `<span tl:text="${run.completedSteps}">3</span>/<span …>6</span> steps` renders as `<span>0</span>/<span>0</span> steps`, so no assertion may grep a response body for the literal `0/0 steps`.
