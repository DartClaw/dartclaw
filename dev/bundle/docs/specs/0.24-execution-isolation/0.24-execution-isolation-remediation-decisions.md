# 0.24 Execution Isolation — Remediation Decisions & Recommendations

**Date**: 2026-08-12 · **Author**: review orchestrator (Fable) · **Input**: the council mixed review (`…-mixed-review-claude-2026-08-12.md`), FAIL, 9 release-gating HIGH gates.

Purpose: for each open gate and Note-routed decision, the concrete choice on the table, the options with trade-offs, my recommendation, and why — plus a recommended sequence. Grounded in the code as it stands at HEAD.

A framing point that shapes several recommendations: **the root cause of this whole milestone's trouble is over-decomposition of the container lifecycle.** 0.24 correctly moved from shared per-profile persistent containers to per-*authority* isolation, but it leased an authority *per turn* rather than *per unit of trust*. Provider sessions, the primary lane, and orphan cleanup all assumed a longer-lived substrate. Most of the design gates below are really one question asked in different places: **what is the right lifetime of a container?**

**Decided model (2026-08-12): one persistent container per owner, reused across all its turns, tied to exactly one trust principal, cleaned up only when that owner ends (or on idle).** The owner is a *standing agent* (the primary; a logical-agent session) or a *one-shot job* (a task; a workflow step). Within one owner, the container is reused freely across turns — never re-created per turn. The single hard rule is **a container never crosses trust principals**: agent A's container is never handed to agent B, and there is deliberately **no "shared" scope** that pools one container across principals. "Disposed" therefore means "torn down when the owner ends," not "torn down per turn/execution."

This is the mainstream design, not a novel one. **OpenClaw** uses exactly this — scope-based persistent containers (`agent` = one long-lived container per agent reused across turns *and* sessions; `session`; `shared`), created on demand and reused, torn down only on explicit recreate or idle/age pruning; its architecture otherwise mirrors DartClaw's (host-only Gateway, default `network:none` sandbox, per-session `0600` temp-file secrets). **OpenHands** (one persistent container per conversation, reused across turns) and **Devin** (per-session env) sit on the same side; only **E2B / Modal** go ephemeral-per-task. DartClaw's current per-*turn* leasing is finer than even the ephemeral pole — an outlier no reference system runs, and the direct cause of G-HIGH-3/4. The correct fix is a **simplification** toward the persistent-per-owner model, adopting OpenClaw's `agent`/`session` scopes while **declining its `shared` scope** (the one place OpenClaw accepts a documented cross-session credential-hygiene footgun). Sources: `docs.openclaw.ai/gateway/sandboxing`, `docs.openclaw.ai/cli/sandbox`; OpenHands issues #8108/#6382.

## Release-gating gates

### G-HIGH-1 — Workflow-lane bridged-MCP grant is unguarded *(decision: where the one grant-derivation owner lives)*

**State.** `workflow_cli_runner.dart:40-47` has a package-level `bridgedMcpToolsFor(allowedTools)` that filters to canonical names only — no global-deny subtraction, no servability intersection. The canonical owner `_bridgedMcpToolsFor` lives in `harness_wiring.dart` (`dartclaw_cli`), which `dartclaw_server` cannot import. So "just call the one owner" doesn't compile.

**Options.**
- **(A) Inject the derivation from wiring.** `HarnessWiring` already injects the `containerAuthorities` acquire callback into the workflow runner. Add a sibling injected closure `Set<String> Function(List<String>? allowedTools)` (or fold the grant into the acquire call) computed by wiring, which owns both the deny set and the servable set. The package-level `bridgedMcpToolsFor` is deleted. One owner, no package inversion.
- **(B) Move the derivation down to a shared lower package** (e.g. `dartclaw_core` or `dartclaw_config`) taking deny + servable as parameters, called by both sites. Also one owner, but it relocates security-load-bearing logic into a package with no other reason to hold it, and the servable set is a runtime property of what wiring registered — unnatural to compute low.
- **(C) Duplicate the deny+servable logic inline at the workflow site.** Closes the hole but *is* the root cause (a fourth/third divergent site); the review already flagged this class three times.

**Recommendation: (A).** It makes wiring the single grant authority the package rules already claim it is ("`HarnessWiring` owns every containerized execution's bridged-MCP grant" — `apps/dartclaw_cli/CLAUDE.md`), removes the divergent site rather than adding to it, and needs no package-boundary change. Effort: small. Risk: low (a pure move of an already-tested derivation to the injection seam). Test: `disallowed_tools:['web_fetch']` empties a workflow-step grant; a `['shell','file_read']` policy yields `hasMcpBridge:false`.

### G-HIGH-3 — Workflow steps re-create their container per turn *(DECIDED: hold one container for the whole step)*

**State.** `WorkflowCliRunner.executeTurn` leases a fresh container and releases it in `finally` (`workflow_cli_runner.dart:383,431`, comment: "the container and its bridges go away with the turn"). But `WorkflowOneShotRunner.execute` calls `executeTurn` multiple times per step — main prompt, each `followUpPrompts` entry, the envelope finalizer, one retry — threading `providerSessionId` so later turns resume the same provider conversation. Codex's rollout lives in the container's `generatedStateDir` (destroyed on release); Claude's session state lives on the destroyed read-only root. So resume targets state that no longer exists, and the finalizer (which *requires* a resumable session) fails. Every multi-turn/finalizer step burns a paid main turn then fails, on the containers-enabled default. The workflow runner is the **only** place that re-creates per turn — tasks and sessions already keep their container for the whole execution.

**Decision.** Adopt the decided model: **one container per workflow step (the one-shot job), reused across that step's turns, disposed at the step's end.** Lease at `WorkflowOneShotRunner.execute` scope (or pass a caller-held lease into `executeTurn`), release after the finalizer/retry. This is a *subtraction* — it removes the workflow runner's per-turn special case so it conforms to what the rest of the system already does — not a new mount or persistence layer (rejected: a per-step provider-state mount would add its own uid/cleanup/isolation surface, compounding G-HIGH-5). Concurrent steps keep separate containers (each `execute` leases its own → one principal each, no crossing). **Robustness requirements for the implementer:** the held lease must release on **every** exit path (success, failure, cancel, timeout, and an exception before the first turn); a lease-acquire failure must fail the step closed, not fall back to host; and the change must not let two concurrent steps observe the same container. Do it **together with G-HIGH-1** (same file/seam). Test (no Docker): unit-level — one lease acquired per `execute`, reused across ≥2 `executeTurn` calls, released once on each of the exit paths above. Test (Docker, release gate): a followUp/finalizer step completes across ≥2 turns.

### G-HIGH-4 — Primary container death is a silent brick *(DECIDED: clear error now, auto-recovery deferred)*

**State.** The primary agent already *is* the decided model — one persistent container for the agent's whole life (`_primaryContainer`, acquired once in `_primaryContainerManager`, disposed at shutdown). The only defect is recovery: when that container dies (`docker rm`, OOM, daemon restart), `ContainerManager.start()`'s single-use guard throws an internal `StateError` and nothing re-acquires, so the chat is dead for the process lifetime with an operator-actionless message.

**Decision (lean).** Ship a **clear, operator-actionable error** now — "the primary agent's container was lost; restart the service to recover" — plus a distinct health alert, and accept service-restart as the 0.24 recovery. **Do not build auto-re-acquire for 0.24.** Rationale: the shipping default keeps the primary agent on the *host* (coding-on-host; containers for other agents), so a containerized primary is an opt-in posture and "restart on container death" is a defensible, documented limitation for it. Auto-re-acquire (rebuild the harness's container manager mid-conversation without racing an in-flight turn) is real work for a rare, opt-in case — deferred to a future version, added only if the need shows up. This is the non-over-engineered choice. **Requirement for the implementer:** replace the internal `StateError` at the primary path with a typed, operator-facing message naming the cause and the remediation; add the health alert; document the limitation in the security/agents guide. Test: killing the primary container surfaces the named error, not a bare `StateError`.

### G-HIGH-5 — uid≠1000 makes per-authority mounts unusable on Linux *(decision: chown host dirs vs `--user`)*

**State.** `docker create` (`container_manager.dart:180-203`) passes no `--user`; `generatedStateDir` is `chmod 700` under the host service uid (`:279`); the image runs as `dartclaw` (uid 1000). On native Linux, bind-mount ownership passes through verbatim, so unless the host service uid is exactly 1000 the container holds read-only/again-owned mounts it can't use — every containerized Codex turn (CODEX_HOME under generated-state) and the `/artifacts` write fail. Masked on Docker Desktop by its uid remapping, which is why local suites are green.

**Options.**
- **(A) `chown 1000:1000` the per-authority host dirs before mounting** (generated-state and artifacts), matching the image's runtime uid.
- **(B) Run the container as the host uid: `--user $(id -u):$(id -g)`.**

**Recommendation: (A) — chown to the image uid (1000), NOT `--user`.** `--user <host-uid>` makes the container process an arbitrary uid that (i) may not exist in the image's passwd, and (ii) cannot read the image's own `dartclaw`-owned files and installed CLIs — it trades a mount-permission failure for a broader "container can't run its own binaries" failure. Chowning the *host* side to 1000 is the standard bind-mount-uid fix and keeps the container running as the user its image was built for. Caveat: the DartClaw service must be able to `chown` to 1000 (root or `CAP_CHOWN`); if it runs as an unprivileged non-1000 systemd user without that cap, chown fails — which is exactly why this must be validated on the real Linux VM, not reasoned about. Effort: small (a `chown` alongside the existing `chmod 700`, applied to both per-authority dirs). Risk: medium *until verified on Linux* — high blast radius if wrong (bricks all container execution). **This is the top reason to get the VM conformance run working (G-HIGH-6).** Test: on Linux host uid≠1000, a containerized Codex turn and a Claude turn both read/write their state and complete.

*(This subsumes G18 and F-CC-03 — same root, same fix. Claude also needs `HOME`/`CLAUDE_CONFIG_DIR` pointed at the writable generated-state mount, per F-CC-03; fold that in here.)*

### G-HIGH-6 — No real conformance/isolation run exists *(decision: authorize + provision the Linux Docker run)*

**State.** The parity/conformance suites are `@Tags(['integration','slow'])`, skipped by `dart_test.yaml`, never wired to a real provider or process; `execution_conformance_matrix_test.dart` asserts `HarnessFactory.create()` (spawns nothing); AS S06 is checked `[x]` but unmet at its own Then. So `network:none`, the mount set, egress refusal, and placement are proven only by static reading.

**Recommendation: authorize the run and provision the Ubuntu VM for it (details in the VM section below).** This is not a code decision — it's the one piece of evidence the release actually needs, and it simultaneously confirms/refutes G-HIGH-5, G18, F-CC-01/03. Before it can run, two code prerequisites must land: (i) the suites must construct a *real* `SecurityProfile` and a *real* provider harness (G23/M11), and (ii) they must be un-skipped in the gate (a `--run-skipped -t integration` invocation, recorded per `RELEASE_PREPARATION.md:12`). My recommendation is to treat "the conformance suite runs green on real Docker (Linux uid≠1000 **and** Docker Desktop)" as the **single hard release gate** for 0.24 — the other fixes are necessary but this is the one that proves them.

### G-HIGH-9 — Native-web reversal unreconciled *(decision: accept-with-ADR vs revert)*

**State.** The code denies provider-native `WebSearch`/`WebFetch` for *every* container profile (not just `restricted`); the shipped rationale is sound (native web executes at the provider, outside `network:none`, so keeping it only relocates the failure to a gateway 403). But an operator-ratified decision note and the S03 FIS `[x]` criteria + TI05 assert the *inverse* (workspace retains native web), with no amending record.

**Recommendation: accept the reversal with an ADR; do not revert.** The engineering is correct — reverting would reintroduce a contradiction the gateway 403s on every turn. This is purely a baseline-integrity fix: write a short ADR (or amend the existing decision note via `ops update-fis design-change` + ADR) recording that native web cannot be contained under `network:none` and is therefore denied for all profiles, and update the S03 `[x]` criteria to match. Requires your sign-off because it changes an operator-facing security claim. Effort: small (doc). Risk: none to code. This is the one gate that is *only* paperwork — but it's release-gating because operators currently believe the opposite of what ships.

## Note-routed decisions (surfaced, need a call)

- **M-i — tri-state container health (recommend: implement).** `isHealthy()` conflates "daemon unreachable" with "container dead," so one daemon blip fails every in-flight containerized task. Make health three-valued (running / not-running / **unknown**); "unknown" (inspect connection error, distinct from "no such object") must **not** fire a crash event, and `stop()` must treat an unconfirmable removal as a throw, not success. Recommend implementing for 0.24 — a Docker Desktop restart failing every task is a real operability defect. Pairs with **CT-02**.
- **M-j — crash attribution should consult retries (recommend: route through `markFailedOrRetry`).** The crash subscriber transitions `failed` directly, bypassing the retry machinery and racing the executor's own settlement. Route it through the same failure handler so container crashes re-queue within `maxRetries` and there's one settlement owner. Recommend for 0.24 (bundle with M-i — same subsystem).
- **M-a — primary-lane task-policy overwrite (recommend: fix, low urgency).** `ExecutionCoordinator._routeRequest` overwrites a resolved task policy with the primary's on the primary lane — an FR1 violation, but reachable only on SDK/single-harness compositions, not the CLI default. Fix when touching the coordinator; not a 0.24 blocker on its own.
- **M22 — one YAML syntax error silently reverts the whole config to defaults (recommend: fail closed for security sections).** A duplicate key boots a container-enabled deployment fully unisolated on the host with one log line. Recommend: a parse error in (at least) `container.*`/`agent.*`/`security.*` is startup-fatal, not a silent `{}`. Broader than execution policy, so scope carefully — but "silent unisolated boot" is the worst failure mode in the set.
- **CT-09 — quarantine on failed container destroy (recommend: quarantine).** A throwing `destroyContainerAuthority` returns capacity with the container possibly still alive. Mirror the unconfirmed-termination quarantine rule. Small, bundle with M-i/M-j.
- **The recurring test-trap (recommend: graduate to a fitness check).** Third-run recurrence. Encode the five proposed rules (esp. "bound-asserting test names must use `unorderedEquals`/exact `equals`", extended to `argv|env|mounts|disallowed`) and ratchet `max_test_file_loc` (M-r/CT-11). Delete the `LEARNINGS.md:146` prose entry once the check enforces it.

1. **Paperwork + safe fixes first (no Docker needed):** G-HIGH-9 ADR (your sign-off), the two bounded boundary tests G-HIGH-7/8, the doc/glossary MED/LOW set, and the test-trap fitness check. These reduce the count and de-risk the gate without touching runtime behavior. *(Two of these — grant normalization and the codec wrap — are already applied.)*
2. **The container-lifetime cluster, together:** G-HIGH-1 + G-HIGH-3 (same file/lease seam), then G-HIGH-4, then the M-i/M-j/CT-09 health/crash bundle. This is the substantive engineering and the source of most HIGHs.
3. **The uid fix G-HIGH-5** (chown-to-1000 + Claude HOME redirect), applied but **held unverified** until step 4.
4. **The real conformance run G-HIGH-6** on the Ubuntu VM (Linux uid≠1000) **and** Docker Desktop — this validates 3 and 5 and is the single hard release gate. Nothing ships as "done" until this is green and recorded.

Steps 1 and the doc parts of 2 are autonomous. Steps 2's engineering and 4 want your decisions above first.
