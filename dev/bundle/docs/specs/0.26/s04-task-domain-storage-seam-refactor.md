# FIS: Task-Domain Storage Seam Refactor

**Plan**: dev/bundle/docs/specs/0.26/plan.json
**Story-ID**: S04

_Refreshed 2026-09-02 against released 0.25 (public HEAD `daf5125a`), replacing the 2026-07-30 authoring (then "Task-Domain Storage Async Refactor", written against 0.24 and the dissolved `dartclaw_storage` / `dartclaw_server` packages). Version labels: 0.26 is this milestone (the PRD title still carries its pre-renumber label), released 0.25 is the compatibility baseline. Premise corrections versus the prior FIS and the plan brief: `TaskType` and `Task.type` are gone (0.25), so every scenario on `list(type:)` or `Task.type` round-trips is dropped; `SqliteTaskRepository` and `TurnTraceService` were already `Future`-returning, but `TaskEventService` and `TemporalKnowledgeGraphService` are synchronous at HEAD – the brief's "already Future-returning, unchanged signatures" holds for two of the four classes only, and the seam is async, so those two change signature (PRD FR1 Outputs: "storage/service APIs become `Future`-returning")._

## Feature Overview and Goal

**Intent**: The task-domain services still talk to `sqlite3` directly, so the milestone's PostgreSQL backend cannot reach tasks, events, traces, or knowledge-graph facts – this story moves those four services onto the `DatabaseBackend` seam with zero user-visible change, so the default SQLite experience stays exactly as it is while the same code becomes portable.

**Expected Outcomes**:

- [OC01] Task and artifact persistence returns the same rows, ordering, stored formats, missing-id results, conditional-update outcomes, and artifact cascade as released 0.25.
- [OC02] Task events, turn traces, and temporal-KG facts read back identically after their callers await the storage work – ids, owners, ordering, filters, aggregates, and the `false`-for-unknown-id invalidation result are unchanged.
- [OC03] Every runtime, web, MCP, and CLI flow that uses these services produces the same response or output as before, and a supported 0.25 store opens with no operator action while an unsupported one is refused before any repository touches it.

## Architecture Decision

**Approach**: Each of the four classes takes S01's `DatabaseBackend` in its constructor (S01 #7's awaited `open()` factory is only for schema-initialising repositories, and S02 leaves none here) and issues its existing SQL through `execute`/`query`; all constructor DDL, the legacy `tasks` rewrite, and the constructor PRAGMAs are retired, S02's gate becomes the only schema precondition and is called first at both production construction sites, and the two synchronous services become `Future`-returning with their callers awaiting. See ADR: `../dartclaw-public/dev/adrs/045-pluggable-database-backend.md` (decision #7).
**Why this over alternatives**: carrying the DDL and the legacy rewrite through the seam as a transitional stub (the S01 pilot pattern) would port a `BEGIN…COMMIT` repair that S02's contract already refuses, only to delete it in S06; keeping the two services synchronous would need a synchronous door in the seam that ADR-045 rejected.


## Technical Overview

Async surface after this story (everything else keeps its 0.25 signature):

| Class | Members that change | Shape |
|---|---|---|
| `SqliteTaskRepository` | constructor (`DatabaseBackend`) | signatures of the `TaskRepository` port unchanged; `dispose()` (required by `task/task_repository.dart#TaskRepository`) closes the raw `Database` today and is production's only close of `tasks.db` (`StorageWiring.dispose()` → `TaskService.dispose()` → `_repo.dispose()`) – in this story it becomes a no-op and `StorageWiring` closes the connection it opened (TI04, TI08); S06 formalizes that ownership (S01 #6, S06 SC04) |
| `TurnTraceService` | constructor (`DatabaseBackend`) | all methods already `Future`; `dispose()` stays a no-op |
| `TaskEventService` | `insert` → `Future<void>`, `listForTask` → `Future<List<TaskEvent>>`, `countForTask` → `Future<int>` | class dartdoc rewritten: durability is "written before the returned future completes" |
| `TaskEventRecorder` (runtime) | every `record*` → `Future<void>` | `_record` awaits the insert, then fires `TaskEventCreatedEvent` (order preserved) |
| `TemporalKnowledgeGraphService` | `addFact` → `Future<int>`, `query`/`allFacts`/`timeline`/`contradictions`/`openContradictions` → `Future<List<…>>`, `invalidate`/`factExists` → `Future<bool>`, `ownerForFact` → `Future<String?>`, `factById` → `Future<KnowledgeFact?>` | `parseAsOf` and the private temporal helpers stay synchronous; `hasOwnerColumn` and `_migrateOwnerColumn` were retired by S02 before this story starts |
| `KnowledgeFact.fromRow`, row mappers | parameter `Row` → `Map<String, Object?>` | SQLite `Row` is a `Map<String, dynamic>`, so S05's raw callers compile unchanged |

Affected-row guards (`update`, `delete`, the three conditional updates, `invalidate`) consume the `int` that `execute` returns (S01 #5). `addFact` obtains its id from `query('INSERT … RETURNING id', …)`. Dynamic placeholder lists (`listByWorkflowRunIds`) and the dynamic `LIMIT`/`WHERE` assembly stay string-built exactly as today; the rewriter is identity on SQLite.

Construction order at both production sites: open the connection → wrap it in the one `SqliteBackend` (S01's instance in wiring) → `await SqliteSchemaGate.prepareTasks(backend, storeName: 'tasks.db')` → construct seam consumers and raw co-users in any order. The gate's own classification is why the order is not optional: a raw constructor's `CREATE IF NOT EXISTS` on an empty connection leaves a store that is neither empty nor current, and the gate refuses it.

## Constraints & Gotchas

- **Critical**: gate before any constructor on a fresh connection, at every site – production (TI08) and tests (TI03). The helper exists so the 72 test files follow one idiom; a test that also constructs a raw co-user (`SqliteAgentExecutionRepository(db)`, S05's files) must prepare the store through the gate on the same connection before that constructor runs.
- **Critical**: one `SqliteBackend` per connection. S01's wiring already wraps the task connection for the goal repository; the four services reuse that instance – a second wrapper on the same `Database` escapes S01's serialization and close ownership.
- **Critical**: never turn required event or KG persistence into fire-and-forget. Every production call site awaits; a synchronous enclosing function becomes `async` (`TaskExecutor._recordProviderUnavailable` is called from the async dispatch loop and simply awaits). Exactly one boundary cannot await and uses the LEARNINGS shape (`unawaited(future.catchError(log))` or an equivalent caught-and-logged wrapper): the `service_wiring.dart` binding of `recordStructuredOutputFallbackUsed` to the workflow package's `void`-returning `StructuredOutputFallbackRecorder` typedef – a `Future<void>` tear-off is assignable there and would drop the error silently. Template context builders never call storage: `templates/tasks.dart` receives events pre-fetched by its async page handler, the convention `task_detail.dart` already documents ("computed from `TaskEventService` by the page handler"). `unawaited_futures` is enabled, so `dart analyze` catches a dropped future inside an `async` body but not a call from a synchronous one – the TI05/TI07 Verify scans cover that gap.
- **Constraint**: the `TaskEventService` "writes are synchronous – no event loss on crash (NF04)" dartdoc and the `TaskEventRecorder` "inserts it synchronously" step are drift once the seam is async; rewrite them to the await contract, do not leave them.
