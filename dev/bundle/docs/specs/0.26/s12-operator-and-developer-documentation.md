## Feature Overview and Goal

**Intent**: An operator can adopt, secure, run, and leave the opt-in PostgreSQL backend from the public guide alone, and a contributor reads one storage model across the architecture docs, the generated configuration reference, and the glossary – with no document promising data transfer, an automatic schema upgrade, or a hand-edited generated reference.

**Expected Outcomes**:

- [OC01] From `docs/guide/postgresql.md` an operator configures exactly one credential reference, meets the TLS posture, provisions an administrator-owned database with a least-privilege runtime role, sizes the pool, and later switches away and decommissions the remote database without a hidden transfer.
- [OC02] The same guide tells the operator where every store lives and what to back up (storage tiers at a glance), what `rebuild-index` and a language change rebuild, and that an incompatible authoritative store is backed up and then reset, recreated, or restored – never upgraded in place.
- [OC03] The generated configuration reference lists all five `database.*` keys in its core table, and `data-model.md`, `security-architecture.md`, `configuration-architecture.md`, and the glossary describe the shipped backend, search, and compatibility contracts with current package names.
- [OC04] Private `docs/ROADMAP.md` and its public mirror record 0.26 Phase A delivered with Phase B pending and the milestone open, stating the `PostgreSQL contract` external gate's real status without inventing a date.

## Acceptance Scenarios

- **S01 [OC01] [TI01] An operator configures and provisions PostgreSQL from the guide alone**
  - **Given** an operator reads `docs/guide/postgresql.md` for a non-loopback managed PostgreSQL 14+ instance
  - **When** they follow the configuration and provisioning sections
  - **Then** the guide states that omitting `database:` keeps the SQLite default with no server; shows `database.backend: postgres` with either `url: ${DARTCLAW_DATABASE_URL}` or `credential: <name>` and says exactly one is allowed and a persisted inline password is refused; documents `pool_size` (default 5) and `fts_language` (default `english`) as restart-tier settings masked by `dartclaw config`; states the TLS posture (omitted `sslmode` connects with `verify-full` off loopback, `verify-ca` is upgraded, `sslmode=disable` is refused off loopback, a loopback server without TLS needs `?sslmode=disable` because loopback keeps the driver default `require`, platform trust store only); and separates administrator SQL (create role, database, schema owned by the runtime role) from the least-privilege runtime role, noting the one startup warning when the runtime role is a superuser.

- **S02 [OC01,OC02] [TI01] A managed deployment has an explicit data and recovery posture**
  - **Given** authoritative data moves to a managed PostgreSQL provider
  - **When** the operator reads the operations section
  - **Then** the guide names the provider a third-party data processor holding authoritative task data, recommends at-rest encryption, assigns retention, residency, and provider snapshots to the operator, points backups at the provider's tooling or `pg_dump` for PostgreSQL and at the data-model backup procedure for SQLite, and carries a storage-tiers-at-a-glance table with one row per store – `dartclaw.db` or the PostgreSQL database (authoritative, back up), `search.db` or the PostgreSQL search tables (derived, rebuildable), `turn_state.json` and `webhook_deliveries/` (transient, safe to lose), `sessions/`, `workspace/`, `dartclaw.yaml`, `projects.json`, and `credentials/named/` (file-based authoritative, back up), audit and usage logs (append-only, back up if retained) – each row saying where it lives under each backend, whether to back it up, and what is lost without it.

- **S03 [OC01,OC02] [TI01] Switching backends and decommissioning never implies a transfer**
  - **Given** `database.backend` changes in either direction
  - **When** the operator follows the switching section
  - **Then** the guide says no data is transferred (a fresh target starts empty, a compatible target reopens its own data), explains the startup notice for a non-empty abandoned store and that the PostgreSQL-side check is best effort (could not verify when the URL is unresolvable, unreachable, posture-refused, or of unknown schema) while the SQLite-side check is local, states that a lingering `url` or `credential` under `backend: sqlite` is legal and exists for that check, lists decommission steps in order (export or retain what is needed, take a provider snapshot, then drop the database and role, remove the reference from config, revoke the credential), and describes the single-writer rule: a second `dartclaw serve` on the same database fails loud, one-shot commands (`rebuild-index`, `cleanup`, `workflow status`) run with the server stopped, and an unreachable database at boot fails closed after local crash recovery has run.

- **S04 [OC02] [TI01,TI03] Language, reindex, and schema-compatibility guidance matches the shipped behaviour**
  - **Given** an operator changes `fts_language`, runs `dartclaw rebuild-index`, or meets a compatibility refusal
  - **When** they follow the guide and the PostgreSQL subsection of the search guide
  - **Then** both say one deployment-level language drives memory, conversation, and KG fact search; a language change needs a restart plus `dartclaw rebuild-index` for the stored memory and conversation vectors while KG facts use the new language on the next query after restart; the wiki is file-backed and searched live and tasks are never indexed; the limitations are listed (regular Snowball inflections only, `sprang` does not match `springa`; mixed-language content mis-stems; PostgreSQL does not fold diacritics where FTS5 does; stopword-only queries return nothing; core PostgreSQL with no extension); and the compatibility section says a fresh database is bootstrapped, a non-empty database without DartClaw's marker or with a different epoch is refused before use with the store named, and the remedy is back up, then reset or recreate the store for this release or restore a compatible one – derived search storage rebuilds automatically or refuses, and nothing upgrades data in place.

- **S05 [OC03] [TI02] The generated configuration reference carries the database section without a hand edit**
  - **Given** the core-key list gains `database.credential`, `database.pool_size`, and `database.fts_language` beside the two keys story S07 added
  - **When** `dart run dev/tools/render_config_reference.dart` runs
  - **Then** the `### Core Config` table lists all five `database.*` keys with the registry descriptions S07/S08/S09 wrote, the exhaustive table carries the `database` group, the core count stays at or under 90, and `render_config_reference.dart --check` and `generate_config_schema.dart --check` both exit 0.

- **S06 [OC03] [TI04,TI05] Contributor references describe one shipped storage model under current package names**

## Architecture Decision

**Approach**: One operator guide (`docs/guide/postgresql.md`) synthesised from the S02/S07–S11/S13–S15 contracts, the configuration reference reached only through the curated core-key list and the generator, and a verify-and-align pass over the architecture documents and glossary rows the upstream stories already touched. See ADR: `../dartclaw-public/dev/adrs/045-pluggable-database-backend.md` (#1, #2, #4–#6, § Schema Bootstrap and Compatibility).
**Why this over alternatives**: the upstream stories write each mechanism fact into the doc section they own; a second narrative copy is what drifts, so this story adds only the operator-facing synthesis (guide, tiers table, search subsection, config-section row) and reconciles.

## Technical Overview

Guide outline, in order: **When to use it** (SQLite default needs no server; PostgreSQL is opt-in, one database per deployment, never a mix, PostgreSQL 14+, core features only) · **Configuration** (the two `database:` shapes from ADR-045 § Configuration, exactly one reference, `pool_size`, `fts_language`, restart tier, masking, links to the generated reference, `deployment.md#secrets-and-the-service-unit`, and `security.md#named-credential-storage`) · **Connection security** (TLS matrix, loopback exemption and its `require` default, redaction of failures and config output, connection lifecycle audited as host-side egress) · **Provisioning** (administrator SQL: `CREATE ROLE dartclaw LOGIN PASSWORD '<password>'`, `CREATE DATABASE dartclaw OWNER dartclaw`, `CREATE SCHEMA` owned by the runtime role, `REVOKE` on `public` where the provider grants it; runtime role connects with no superuser or create-database rights; the startup superuser warning) · **First start and schema compatibility** (fresh bootstraps, non-empty unmarked or mismatched epoch refuses, remedy, single-writer interlock, one-shot commands, unreachable at boot) · **Search and language** (what each layer does on a language change; limitations) · **Operations** (backup and restore pointers, data-processor exposure, the storage-tiers table, leftover `state.db`/`webhook_deliveries.db`/`tasks.db` files) · **Switching and decommissioning** (no-transfer rule, notice, ordered steps) · **Failure reference** (lock conflict, unreachable at boot, recovery quarantine, compatibility refusal – what the message names and what to do; never a DSN).

## Constraints & Gotchas

- **Critical**: never edit between `<!-- BEGIN GENERATED CONFIG REFERENCE -->` and `<!-- END GENERATED CONFIG REFERENCE -->` in `docs/guide/configuration.md`; change `config_reference_core_keys.txt`, run `dart run dev/tools/render_config_reference.dart`, and let `--check` prove it. An unknown key in the list (a `database.*` field S07/S09 did not register) fails the generator – that is a finding for the owning story, not a prose workaround.
- **Constraint**: upstream doc sections are facts. Read the S08 security subsection, the S09/S10/S13 data-model blocks, and the S14/S15 renames at execution and write the guide against them; a contradiction between two landed sections is a `CONFUSION:` for the owner, never a third version.
- **Constraint**: the loopback default is the driver's `require`, not `disable` (S08's recorded assumption). The guide's local-development example must carry `?sslmode=disable` explicitly and say why.
- **Constraint**: two repositories, two rules – public-canonical docs change in `dartclaw-public`; the private ROADMAP changes here and is never auto-committed; the public ROADMAP mirror moves in the same change and stands alone.
- **Constraint**: no story or task IDs, no `dartclaw-private/` paths, en dashes not em dashes, version labels 0.26 / released 0.25, dates only from `date`.
- **Avoid**: describing the store files under their pre-milestone names – after S14/S15 the guide says `dartclaw.db`, `turn_state.json`, `webhook_deliveries/`; the old names appear only as adopted-or-deletable notes.
