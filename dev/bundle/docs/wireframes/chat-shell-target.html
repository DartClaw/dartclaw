The ACP handshake occasionally drops the initialize response when a provider is slow to boot. Trace where we lose it and propose a fix that does not add a retry loop.

The response is not dropped on the wire — it arrives before anything is listening. AcpSession.start() writes the initialize request and only then subscribes to the transport stream, so a provider that replies inside the same microtask wins the race.

The handshake stream is a single-subscription Stream, so the frames emitted in that window have nowhere to go and are discarded rather than buffered.

// stdio_transport.dart — subscribe first, then write.
final pending = _frames.firstWhere((f) => f.id == request.id);
_sink.add(encode(request));
return await pending.timeout(handshakeTimeout);

That reorder is the whole fix. Three things follow from it:

  • No retry loop. The race disappears instead of being papered over, so a slow provider costs latency, not a re-send.
  • The timeout stays the only failure path. handshakeTimeout already fails the session closed; nothing new has to decide when to give up.
  • One test covers it. A fake transport that replies synchronously reproduces the drop today and passes after the reorder.

The change is 6 lines in stdio_transport.dart and 2 in acp_session.dart. Want me to apply it?
