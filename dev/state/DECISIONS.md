- **LOC ceilings carry a 1500-line band, re-cut at milestone close-out**: `dev/tools/arch_check.dart`'s `_locHeadroom` is 1500 (was 400) and every per-package ceiling is re-cut to measured + band when a milestone closes, recorded in that milestone's `LOC-BASELINE`. The per-package downward-only model ([ADR-056](../adrs/056-package-topology-consolidation.md)) keeps its ratchet and slack failure between close-outs; the 400 band forced a reviewed raise every few days of the 0.25 tail and four packages sat over their ceilings after the 0.24.3 merge. Owner decision, 2026-09-01.
- **The GitHub publish plane and the model-turn credential plane are separate**: model turns authenticate through the subscription-logged-in `claude` / `codex` CLIs, while `github-pr` publishing calls the GitHub REST API with a bearer read from `credentials.<name>` (`GITHUB_TOKEN` in the workflows profile) and never shells out to `gh` – so a `gh` keyring login is invisible to the server and cannot stand in for the configured credential. `dev/testing/profiles/workflows/run.sh` resolves that token env → fixture askpass file → `gh auth token`, for the profile only. Commit `84c34cb7`. 2026-09-01.
- **The dedicated host-lane Codex home mirrors the operator's plugin capabilities, with no config knob**: a stored Codex subscription (`dartclaw auth codex`) runs in a DartClaw-generated `CODEX_HOME` that overrides any exported one, and that home is credential isolation only. On every prepare, `completeDedicatedCodexHome` (`packages/dartclaw_core/lib/src/harness/codex_environment.dart`) re-derives the operator's `~/.codex` plugin cache, `[plugins.*]` stanzas and skills into it as the single `config.toml` writer for both worker and probe lanes; removals are pruned only within the `.dartclaw-mirror.json` manifest so vendor-CLI-installed entries in the store survive, the swap stages a sibling directory rather than delete-then-recreate, and the supported TOML subset is documented and fail-closed – an input outside it refuses the whole mirror rather than guessing. Rejected: extending `providers.<name>.inherit_user_settings` to Codex – the key would then name two mechanisms, `false` on Codex would recreate the bare-home defect, and Codex already has `use_system_codex_home` on that axis. The container lane is untouched and is never seeded from `~/.codex`. Commits `98f94f10`, `d7e60dc6`. Owner decision, 2026-08-31.
- **The workflow fixture's boundary contract lives upstream in the fixture repo**: `workflow-test-todo-app` is a gitignored nested clone under `dev/testing/profiles/workflows/data/projects/`; its `CLAUDE.md` (with `AGENTS.md` symlink; `framework: fastapi`) is committed in the fixture repo (commit `96ccd84`), and `dev/testing/profiles/workflows/fixture.sh` greps for those markers, baselines its `reset` on `origin/main`, and tolerates no local overlay. Rationale: every earlier green run silently depended on an untracked overlay in this checkout. Commit `b11acd12`. 2026-08-29.
- **The per-file method-count fitness gate is retired, not repaired**: `max_method_count_per_file_test.dart` counted lines matching a two-identifier-then-paren regex rather than parsing Dart, and read roughly half the real member count — a generic return type (`Future<void> close()`, the ordinary shape in async Dart) was invisible, and getters and constructors were never counted at all. Two false-positive corrections in 0.25 brought every file under the ceiling of 40, which emptied the allowlist and left the gate green and non-binding. A count that tracks reality needs a `package:analyzer` parse; that is not worth its weight beside `max_file_loc_test.dart`, which already gates size and does bind. The gate, its allowlist and its README section are deleted; `max_file_loc` remains the size gate. Close-out, 2026-08-28.
- **0.25's unmet success metrics are recorded, not re-baselined**: three of the seven did not hold — the net LOC reduction (lib 158,179 → 156,183, a 1,996 fall against a 12,000 target, with the test surface 7,520 lines *larger*), the CLI's ≤ 8K lib LOC bar (10,491, down from 20,769), and the ≥ 40 dead-config-key removal (~29 plus 2 the plan's aggregate never counted). No target was lowered after the fact and no metric was re-scored: metric 1 depended on no descoped story, so there was nothing to re-baseline against. The three key preservations behind metric 6's shortfall (`features.thread_binding`, `automation.scheduled_tasks`, the governance knob S25 found live) are deviations under the no-regression constraint, not execution misses — a falsified dead premise means the capability stays. Figures and the one command that produced them: `LOC-BASELINE-0.25.md`; per-clause verdicts: `STATE.md`. Close-out, 2026-08-27.
- **The six orchestration and content MCP tools reach a container authority under the host lane's rule**: `workflow_run`, `workflow_list`, `schedule_upsert`, `schedule_list`, `attach_media` and `wiki_write` shipped with no `CanonicalTool` mapping, which made `_BridgeToolPolicy` refuse them for every container authority. Making container the default posture ([ADR-055](../adrs/055-container-by-default-posture.md)) turned that into a capability regression: on a default install the primary agent could no longer call the tools the milestone existed to add. All six now carry canonical entries, and exposure follows the host lane's existing rule rather than a second one — the primary agent is the deployment and reaches the servable map minus the session-spawning tools, while a task, workflow or logical-agent lane reaches only what its own `allowedTools` names. A reviewed widening, recorded in ADR-055 § *Reviewed widening*. Owner decision, 2026-08-27.
- **S63/S64 deferred to 0.30**: the workflow schema-emitting validator did not land in 0.25 and its two stories stayed `spec-ready` rather than being descoped silently. The preserved work is parked on `parked/s64-workflow-schema`; `built_in_workflow_contracts_test.dart`'s 1,345-line retention is blocked on it and is a documented deferral, not test-surface debt. Close-out, 2026-08-27.
- **No AndThen-specific filenames in production code**: AndThen artifact filenames (`prd.md`, `plan.json`, `plan.md`) and other framework-specific file-name literals must not appear in production code (`packages/*/lib/src`, `apps/*/lib/src`); built-in workflow YAML definitions and skill payloads are the sanctioned home for framework semantics, including such filenames. Completes the [ADR-041](../adrs/041-framework-agnostic-workflow-engine-generic-output-validation.md) framework-agnostic-engine direction — engine behavior must not key on one framework's artifact naming. The last such site (`filesystem_output_resolver.dart#_preferredSingularMatch`) is removed by the 0.19.1 `framework-vocabulary-neutralization-sweep` story and replaced with a generic declarative preference, guarded by a structural `rg` criterion. Owner decision, 2026-07-04.
- **Workflow git promotion/publish canonical behavior**: Connected/server and standalone workflow git paths share standalone's tested core safety semantics: promotion commits pending story-branch changes, sweeps dirty integration-worktree state into a `chore(workflow): <story-or-run> integration cleanup` commit when present, and merges from the existing integration worktree or a temporary integration worktree when none is checked out; publish commits pending branch changes before push. Connected mode keeps its project-auth push, PR creation, notes, and artifact persistence. Rationale: standalone behavior is test-pinned by the dirty-integration-worktree and temporary-integration-worktree coverage, while server-mode "neither" had no matching intent/test evidence and was duplicate-wiring drift. Owner decision, 2026-07-07.
- **Claude env-scrub hardening is per-trust, not blanket**: the v0.14.6 spawn hardening (`CLAUDE_CODE_SUBPROCESS_ENV_SCRUB=1`) reduces credential-exfiltration risk, but the Claude CLI also treats it as a signal to force `--permission-mode default`. `ClaudeCodeHarness` therefore overrides the var to `=0` when `providers.claude.approval: never` selects `bypassPermissions`; every other direct host harness spawn keeps `=1`. Containerized spawns also use `=0` because their minimal environment carries no host credential and bubblewrap cannot start under the container hardening. Real tool enforcement remains the guard chain plus host gateway. Owner decision, 2026-07-07; amended 2026-08-13 and 2026-08-23.
- **Cloud services are acceptable as explicit opt-in; "local-first" is not a product principle**: [ADR-004](../adrs/004-vector-search-approach.md)'s rejection clause ("violates local-first principle", "a system designed to run locally") was that decision's era-specific framing (0.2, single-user Mac-local), not a codified principle — it appears nowhere in PRODUCT.md or the security architecture, DartClaw's core function already sends prompt-injected memory content to cloud LLM providers on every turn, and [ADR-045](../adrs/045-pluggable-database-backend.md) committed the authoritative task corpus to optional cloud-hosted PostgreSQL. The enforced posture is narrower: credentials reference-based, agent-initiated egress guarded + audited, and any data-moving service an explicit operator opt-in. Apply by evaluating cloud APIs (e.g. embedding APIs for the hybrid-search track) on merits — quality, cost, offline-degradation contract — without a local-first penalty; a future hybrid-search ADR should explicitly supersede the ADR-004 clause. Owner decision, 2026-07-24.
- **Process termination confirmation ownership**: `killWithEscalation` returns a typed `ProcessTerminationResult` and logs unconfirmed termination locally through its existing label and Logger; lifecycle methods remain `Future<void>`, while the harness exposes whether its managed root termination is confirmed. The execution coordinator must confirm that state before replacement; otherwise it quarantines the capacity slot.
- **Windows bash qualification ownership**: The committed scenario at `dev/testing/scenarios/windows-bash-step.md` owns
  the repeatable acceptance contract; run reports are ephemeral local or CI output. S09 remains the core runtime smoke
  path and does not absorb bash qualification. Owner decision, 2026-07-19.
- **Design-system gap resolution**: When implementation discovers a gap in the canonical design system (a missing primitive, layout affordance, or token), close it upstream in `dev/design-system/` first and sync down — never with page-specific workarounds in app CSS; compose canonical primitives wherever they exist. Ratified during 0.22 preflight (owner, 2026-07-20): drove extending canonical `.content-inner` with the stack gap (rather than per-page spacing rules) and the canonical dot+badge status-hero treatment; the fallback for any canon-adoption visual regression is an upstream canon fix, not a local override.
- **Built-in `search` agent keeps its name (no `web_search` rename)**: Field-feedback proposal to reduce web-search bias; declined – the observed misses were the main agent calling `WebSearch` directly, and recipe 00's memory-before-web rule (0.23) is the causal fix. A rename needs an agent-name alias/migration mechanism the codebase lacks, plus wide docs/tests churn – permanent cost, speculative benefit. If bias recurs, sharpen the built-in description/prompt first. Owner-delegated, 2026-08-05.
- **Logical-agent orchestration and execution allocation are host-owned and provider-independent**: `sessions_spawn` and `sessions_send` are the only logical-agent conversation tools. After global governance, one execution coordinator owns the serialized primary-interactive lane and all per-provider worker leases. Main user/channel turns use the fixed primary lane; cron/system jobs, tasks, logical agents, and workflow steps use worker capacity. `providers.<id>.pool_size` is the hard worker-execution ceiling and excludes the primary lane. Harness reuse is knob-free: prefer the exact compatible session, then a healthy host worker with the same provider and effective policy, otherwise create fresh. A logical-agent container may persist only for its exact session/agent owner until discard, eviction, or shutdown; task containers end with the turn and workflow containers with the step. Replacement requires confirmed teardown or quarantine. Observability derives from leases. Provider branching stays inside adapters and composition/wiring. The SDK single-harness fallback is compatibility-only, requires the same provider/policy, and is not a server logical-agent path. This supersedes the earlier idle-runner pool interpretation, the capacity-only workflow allocation, and the per-turn-container interpretation of the 2026-08-11 ADR-012 amendment.
- **ACP runs on the host only (0.24)**: Container execution is available to a provider only where DartClaw can mediate its provider credential and host capabilities. The host gateway's provider adapters are verified for the Claude and Codex clients, so no ACP registration has a mediated container execution: `harness.acp.agents.<id>` entries setting `container_isolation_required: true` – which relay and unverified topologies must – are startup-fatal with their exact configuration path, and every other ACP registration is refused before admission when its resolved policy is container execution rather than being downgraded to host. Compatibility is computed from the existing registration fields intersected with the resolved execution policy (`ProviderExecutionInventory` in `dartclaw_core`); no declaration axis grants container support. ADR-037's topology classification is unchanged. Decided via andthen:preflight, 2026-08-12; launch-surface wording retired 2026-08-23.
- **Codex host guard enforcement is approval-routed (partial under granular, inactive under never)**: The Codex harness's only beforeToolCall guard site is the approval handler. `approval: on-request` provides the broadest available host interception; `unless-allow-listed`/granular omits provider-safe operations; under the recommended deadlock workaround (`approval: never` + full sandbox, control-protocol.md), no Codex tool call reaches the host guards – enforcement there is provider/sandbox-side only. Consequences accepted 2026-08-05 and clarified 2026-08-09: OC-level guard-block claims are unconditional only on Claude; serve warns whenever configured tool policy uses disabled guards or a Codex posture other than `on-request`. Revisit if the upstream Codex approval deadlock (codex#11816) is fixed or Codex exposes a stronger stable interception surface.
- **~~LOC fitness ceilings get headroom, not allowlist churn~~ (superseded 0.25)**: the 2026-07-05 owner decision — bump a tripped size ceiling with a dated rationale rather than churn allowlists — is superseded by the per-package downward-only ceiling model ([ADR-056](../adrs/056-package-topology-consolidation.md), 2026-08-22). Every workspace member with a `lib/` now carries one recorded ceiling and a single repo-wide headroom constant; a ceiling that sits more than that headroom above actual **fails** until it is lowered, so a package that shrinks cannot bank the space it freed. Raising a ceiling remains possible and still needs a CHANGELOG note saying what justified the growth. Barrel export-count ceilings were retired in 0.25 (ADR-008, 2026-08-20); `barrel_show_clauses_test.dart` keeps the hygiene rule, and every allowlist-backed gate now also fails on an entry that has stopped matching anything.
- **"Security-conscious", never "security-hardened"**: DartClaw copy (docs, marketing, READMEs) must not claim "security-hardened", "battle-tested", or "audited" – frame by design intent: "security-conscious" / "secure by design". Owner correction, standing.
- **Own-MCP semantic mapping is cross-harness**: Exact DartClaw MCP tools map to semantic canonicals from Claude's raw MCP name and Codex's existing `server`/`tool` payload fields; third-party tools retain generic `mcp_call`. This supersedes only the Claude-scoped mapping and Codex+MCP semantic-identity limitation in the preceding decision – Codex host guard enforcement remains approval-routed. The shared mapping supports exact `memory_apply` and `memory_observe` persistent-write policy without a new guard and removes a needless provider inconsistency. Owner-decided via andthen:preflight, 2026-08-05.
- **`providers.<id>.auth` is scoped per provider id, with alias inheritance**: the effective `auth` for a provider is its own entry's value when set; a provider alias with none inherits its resolved family's, so a vendor-level `api_key`/`subscription` binds the aliases that resolve to it; an explicit per-alias value, including `auto`, always wins. Every credential decision – container admission and mediation, host spawn overlays, the workflow subscription-home (`CODEX_HOME`) resolver, provider status, `init` verification – resolves through `CredentialRegistry.resolve(providerId, family:)` so the rule holds uniformly; a family-keyed shortcut re-introduces the aliased-provider fall-through. Recorded as FIS DECISION NOTE provider-auth-alias-inheritance (0.24.2 S01); the last family-keyed site (workflow lanes) closed 2026-08-16. Owner decision, 2026-08-15.
- **Container-mode Claude ships subscription-default behind a caveat, not a runtime `x-api-key` downgrade (0.24.2)**: the Anthropic adapter selects its header from the resolved credential mode alone; a raw-Bearer refusal fails the turn rather than degrading to a key. The PRD's API-key fallback stays prose-only; `CHANGELOG.md` and `docs/guide/security.md` state there is no runtime fallback and host mode is unaffected. Reverting to x-api-key mediation is a code change gated on the manual raw-Bearer wire check in `dev/tools/release_check.sh`. Owner decision, 2026-08-16.
- **Vendor-login health exemption is Claude-only**: a Claude provider whose binary reports a live interactive login while DartClaw holds no credential classifies `unknown` and raises no alert; Codex is excluded because its probe proves `~/.codex/auth.json` exists rather than that the sign-in is live, so exempting it turns a false alarm into a missed alarm. Health-only – admission still fails closed in a container. FIS DECISION NOTE ambient-vendor-login-health-classification (0.24.2 S05). Owner ruling with orchestrator narrowing, 2026-08-15.
- **ACP agents are credential-isolated from first-party provider auth**: a `harness.acp.agents.<id>` registration receives no DartClaw-managed provider credential – never a Claude/Codex subscription token (vendor terms forbid routing subscription credentials through third-party clients), and no `credentials.anthropic|openai` via `model_provider` – and `providers.<any>.auth` does not apply to it; it is never refused on credential grounds and authenticates itself, as with other ACP clients (Zed, claude-agent-acp, Goose ACP mode). The one injection path is explicit and API-key-only: `harness.acp.agents.<id>.credential: <credentials.<name>>`, mirroring `mcp_servers.<id>.credential`. `model_provider` keeps its validation/routing meaning only. Owner decision, 2026-08-17; recorded as the 2026-08-17 amendment to [ADR-037](../adrs/037-universal-acp-harness.md), which owns the third-party-client boundary this rests on.
