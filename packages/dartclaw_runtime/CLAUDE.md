# Package Rules — `dartclaw_runtime`

**Role**: HTTP API + HTMX web UI + task runtime + container orchestration — the composition layer that wires `dartclaw_core` services behind shelf routers and Trellis-rendered pages. Entry points: `DartclawRuntime` (`lib/src/runtime/service_wiring.dart`) — the composition root that assembles the whole runtime — plus `DartclawServer` (`lib/src/server.dart`), `TurnManager`, `TurnRunner`, `ExecutionCoordinator`, `TaskExecutor`, `TaskService`.

## Architecture
- **HTTP layer** — `DartclawServer`, assembled by `composeServer` (`server_composition.dart`) from its `Server*Deps` groups; shelf middleware (auth, security headers); `lib/src/api/*_routes.dart` (one router per domain); `sse_broadcast.dart` + `stream_handler.dart` for streaming.
- **Web UI** — `PageRegistry` (registration with reserved-prefix guard) + `lib/src/web/pages/`; Trellis templates under `lib/src/templates/` (paired `.html` + `.dart`, manifest in `expectedTemplates`); vendored static assets in `lib/src/static/`.
- **Turn orchestration** — `TurnManager` (routing, reservation, status/cancel ownership, `BusyTurnException`, provider-side continuity reset), `TurnRunner` (scoped prompt/persona resolution + harness drive + guard wiring + wait-state event emission), `turn_wait_status.dart` (server API/UI status model + `TurnCancelReason`; the `TurnWaitState`/`TurnWaitReason` enums now live in `dartclaw_core` and are re-exported here), `ExecutionCoordinator` (post-governance session admission, one serialized primary lane plus per-provider worker leases, lazy construction, reuse, and capacity snapshots), `TurnGovernanceEnforcer` (turn-level limits).
- **Step-turn seam** – `lib/src/task/step_turn_runner.dart` runs every workflow step turn on the `TurnRunner` leased by `TaskExecutor`. It carries directory/model/effort, provider-session resume, structured schema, max turns, the per-turn timeout override, tool policy and read-only posture into `reserveAdmittedTurn`; `TurnRunner` alone owns guard evaluation, both turn budgets, cancellation, stall telemetry, assistant persistence and session usage. `WorkflowOneShotRunner` owns prompt sequencing, user rows, aggregate step usage and envelope validation over this seam. It stays package-private and is tested through `package:dartclaw_runtime/src/...`.
- **Task runtime** — `TaskService` (CRUD), `TaskCreationService` (shared JSON API and web-form validation/persistence), `TaskExecutor` (queue consumer), `WorktreeManager`, `MergeExecutor` / `RemotePushService` / `PrCreator` (git ops; injected into `WorkflowGitPort`), `runtime/workflow_git_support.dart` (the workflow lanes' branch promotion, publish, retry capture and cleanup — `lib/src/`-internal, reached by the workflow package's component suites through a `src/` import, not the barrel), `task_*_subscriber.dart` (`EventBus` side effects).
- **Container orchestration** — `ContainerManager`, `SecurityProfile`, `BridgeBinaryProvisioner`, `container_posture.dart` (`resolveContainerPosture` — the one startup seam that settles an unset `container.enabled` by probing `ContainerManager.detectRuntime`, and re-runs the deferred `validateExecutionPolicySelections`), plus the host gateway under `lib/src/container/gateway/` (`HostGateway`, `GatewayPipe`, `ProviderAdapter`, `McpBridgeSurface`) — host-mediated provider and MCP access for `network:none` containers.
- **Workflow glue** — `lib/src/task/workflow_*.dart` injects `WorkflowGitPort` + `WorkflowTurnAdapter` impls into `dartclaw_workflow`; reads workflow runtime state from the hydrated `WorkflowStepExecution` row.
- **Channel wiring + MCP** — `webhook_routes.dart` (synchronous inbound + JWT verification; channel impls themselves live in their own packages); `lib/src/mcp/` (Dart-side MCP endpoint at `/mcp`). The endpoint authenticates its own callers — it is a `publicPaths` entry in `authMiddleware`, on the webhook precedent, because the middleware knows only the gateway token — and `mcpRoute` carries the server's `AuthRateLimiter` so a failed `/mcp` attempt is throttled on the same window as a failed API attempt. It compares the bearer constant-time against the gateway token and then every `gateway.mcp_clients` token: the gateway token reaches the unscoped handler, a client token reaches a `scopedTo` handler carrying `ContextEngineCallerPolicy` (`mcp/context_engine_profile.dart`: deny-by-default over the five context-engine read tools, auditing each refusal itself since the dispatch seam never sees a policy denial) and an `McpCallerIdentity` of `mcp-client:<name>`. A client token grants `/mcp` alone — never `TokenService`, no session cookie, no `?token=` bootstrap. Client tokens are read at mount, so removal takes effect at restart. Without auth the endpoint is mounted only on a configured loopback host, accepts no clients, and the request Host must remain exact loopback. Web-search MCP tools share `search_mcp_tool.dart`'s `SearchMcpTool` base (schema/validation/clamp/ContentGuard scan/result formatting); `BraveSearchTool`/`TavilySearchTool` supply provider metadata to that base, each paired with its own `SearchProvider` (HTTP shape differs per API).
- **Channel config** — `lib/src/config/channel_config_resolver.dart` owns the `switch` from `ChannelType` to `GoogleChatConfig`/`SignalConfig`/`WhatsAppConfig`; this is the lowest package depending on all three. `resolveChannelConfig` parses lazily per `DartclawConfig` instance (the serializer and settings page read off `const DartclawConfig.defaults()`) and caches the result. `loadDartclawConfig` (`config_load.dart`) is the **only** production caller of `DartclawConfig.load` in the workspace — it primes every channel section so parse warnings reach `config.warnings` and keep blocking hot reloads. A new production load path must go through it.
- **Security wiring** — `SecurityWiring` translates `GuardChain` verdicts to `EventBus` events (the seam `dartclaw_kernel` deliberately doesn't cross). It also builds the one `ContentScan` from `guards.content.*` (`contentScan`, null when no classifier is configured — never an implicit block) and hands that same instance to `ContentGuard`, `WebFetchTool` and `OutboundMcpPool`, which classifies successful `tools/call` results from `network_class: public` servers and denies an over-cap result rather than prefix-scanning it.
- **Runtime self-improvement** — `SelfImprovementService` writes both `errors.md` (canonical `error` role) and `learnings.md` (canonical `learning` role) through core's shared `MemoryCorpusService`, which owns their serialization, locking, queueing, and shutdown. `appendError` runs on failure paths, so its CAS retry loop swallows and logs instead of throwing, unlike `appendLearning`, which propagates deliberately. The `error` role is not index-eligible; `learning` is indexed as before.
- **Memory tools** — `MemoryApplyService` stages closed personal-memory add/revise/merge/remove sets from exact record-owner/prospective paths under the shared corpus CAS authority, then projects only their derived-index delta. `memory_observe` selects only the current observation partition or learning document. Heartbeat never curates memory; the only schedule path that does is the opt-in `memory-curation` job, and it is bounded to the entries its own run snapshot showed it.
- **Prompt memory** — `BehaviorFileService` renders only the canonical bounded index for `PromptScope.primary`, framed as untrusted data and carrying its coherent collection revision. `## Recent Errors` is a second bounded projection over the canonical error role under the same `memory.max_bytes` budget — never a whole-file read — and names how many records it dropped. Other scopes get retrieval guidance only; malformed, unreadable, or budget-omitted indexes degrade as a whole block.
- **Knowledge inbox** – `WikiPageStore.writePage` **performs a settled merge; it never infers one**. A slug that already holds a page requires a `WikiPageMerge` (`integrated` replaces the stored body under the stored title heading, `unchanged` writes only the `sources` union, `supplement` appends a dated section); a collision with no decision throws `ArgumentError` rather than guessing. Substring containment (`_carriesBody`) and supplement counting are gone – a second authority on what a merge means is the defect class this seam exists to remove. The one thing the store can check about a merge it cannot read is size: an `integrated` body under `mergeShrinkFloor` (0.8) of the stored body's UTF-8 bytes with an empty `removedContent` throws `WikiPageMergeRefused`. That floor is a compile-time constant reachable by no config key or constructor parameter – a floor an operator can lower is a floor a bad merge can be configured past. Every other rule is unchanged by which mode arrives: `sources` are unioned; frontmatter keys the store does not own are carried through; `confidence` takes the weaker of stored and incoming, and a stored confidence outside the vocabulary is written back untouched (same rule as provenance – lint reports it as invalid). Provenance: a stored `human-authored`/`hybrid` page becomes `hybrid`; a value the store does not recognise is written back **untouched**; a page whose frontmatter records **no** provenance keeps none (only a page with no frontmatter at all is classified, as `hybrid`). `hybrid` is what `wiki_search_source.dart` ranks as trusted, so recording it for a page the store cannot classify launders trust. An `unchanged` merge moves no authorship field and records only a source that is new to the page. Every emitted scalar and preserved key goes through `_yamlScalar`/`_yamlString`, which emits plain **only** a letter-led bare word – a stored value can hold a newline, a trailing colon, or a keyword like `null`, and emitting it raw splits the block, breaks the reader, or changes the value's type. A page the store cannot **parse** throws `WikiPageUnreadable`; frontmatter it merely does not recognise is merged normally. Writes go through `core.secureWriteFile(..., restrictPermissions: false)`: the page is the only copy of every prior batch, and the `true` default would take `wiki/` away from the operator.
- **Wiki lint** – `lintWikiPages` (`wiki_lint.dart`) reports **structural checks only**: links, orphan reachability, frontmatter validity, degradation and KG contradictions. `consolidationDebt`/`stalePages` and their `staleAfterDays`/`consolidationAfterSupplements` parameters are retired – growth is the merge contract's problem, and a category naming a chore no code can do is debt that only ever accrues. It reads pages only through the format members on `WikiPageStore`; don't reimplement frontmatter parsing there. It reports, never rewrites, so a lint finding and an ingestion refusal always name the same pages. `WikiSearchSource` (`dartclaw_core`) shares the fence splitter (`core.splitFrontmatter`) but keeps its own value extraction, because core has no `yaml` dependency – that half must stay tolerant of the same shapes (CRLF, flow and scalar `sources`) or it demotes pages the writer reads fine, and it reads an unterminated fence as no frontmatter where the store refuses the page. `orphan` means **no inbound link**, so it is computed after the scan from the link targets every scanned page named (self-links excluded, `README.md` exempt) – never from a page's own outbound links, which inverts it and names every leaf the inbox writes. Only pages the bounded scan actually read can be judged, so an omitted page is never named. It is off by default (`knowledge.wiki_lint.enabled`), so don't make it the only surface for a signal an inbox-only deployment needs.
- **Inbox two-turn flow** – per file: read → extraction turn → resolve slug → **if a page is stored there**, a page-scoped merge turn → validate the declaration → memory observations → KG facts → wiki write. Both turns go through `_runKnowledgeTurn` (toolless, `readOnly`, `maxTurns: 1`) on `SessionKey.cronSession` keys separated by a `stage` segment, so neither reads the other's context, and the stored page – itself model-authored from earlier untrusted sources – is framed as `jsonEncode`d data exactly like the inbox source. `_settleMerge` returns `null` when no page is stored; `_MergeDeclaration.fromAssistantText` is where the host decides admissibility (unknown `merge`, an `integrated_from` naming another page, a bodyless `integrated`), and `removed_content` reuses the entry-count/rune-cap/newline-collapse bounding that `dropped_topics` used to carry.
- **Inbox retries** – both model turns are retried, along with the collision's stored-page read that feeds the merge turn; nothing durable runs inside the retry, so a page the store cannot parse costs `retryAttempts + 1` extraction turns before it quarantines. They are nondeterministic and write nothing; everything after them is durable, and replaying that duplicated memory findings, KG facts, and supplement sections. `_processFile` runs exactly once and a failure inside it quarantines the file. The wiki write is the **last** durable step, so a failure leaves the stored page untouched and a `wiki-merges=0` report is always true. A source that ingests but cannot reach `processed/` is quarantined, and is deliberately counted in **both** `processed` and `quarantined` – its durable writes landed and the file is in `quarantine/`, and an operator needs both halves before re-dropping it by hand; if that move fails too the failure is recorded in the quarantine entry and the source does stay in `inbox/`. `KnowledgeInboxRunReport.summary` is one line per category by contract and collapses each assembled detail line, because a provider turn error, a filename, or an OS error string can carry a line break the pipeline never authored.
- **Inbound MCP guard/audit is dispatch-level, not per-tool** — `McpProtocolHandler._handleToolsCall` is the only site that invokes `McpTool.call` / `ContextualMcpTool.callWithContext`, and the guard-and-audit step sits there: after caller-policy authorization and schema validation, before invocation. It evaluates the composition root's *base* `GuardChain` (`ServerCoreDeps.guardChain`) and writes one `AuditEntry` per dispatch on both verdicts, principal = the scoped caller's `authorityId`, else `mcpStewardPrincipal` (the fallback for a transport that authenticates the *deployment* — loopback or the shared gateway token — not a claim the caller was local). It evaluates the **canonical** tool name, resolved from the `toolCanonicals` map a scoped view is built with, so an agent allowlist written in canonical names matches the tool serving it (`brave_search` → `web_search`); the registered name stays on `rawProviderToolName` and on the audit entry. Fails closed on a block, an evaluator throw and an audit-write throw; `scopedTo` shares the chain and sink by reference. Both must reach `DartclawServer.fromDeps` — `registerTool` refuses after the handler starts. Don't add guard plumbing to a tool, and don't claim MCP dispatch enforces session read-only mode or per-task allowlists: `TaskToolFilterGuard` is per-runner and layered *above* the base chain, and dispatch has no runner. Every `McpTool` declares a required `access` (`McpToolAccess.read`/`.write`); outbound adapters are always `write`. The task surface (`mcp/task_tools.dart`: `task_create`/`task_review`/`task_bind`/`task_unbind` write, `task_list`/`review_list` read) follows the same rule — `task_bind` narrows its `channel_type` enum through core's `supportsThreadBinding`, so a channel the inbound router could never resolve fails the schema instead of storing a dead binding — the tools are adapters over `TaskService`/`TaskReviewService`/`ThreadBindingStore` and evaluate no guard and write no audit entry of their own. The seam validates only that an argument is *named* by a closed schema, so each tool runs one schema-driven pass over its own declared `required`/type/`enum`/bounds and fails closed; `review_list`'s oldest-first order is applied in the tool, because `TaskRepository.list` orders newest-first and is shared. The orchestration and content surface (`mcp/workflow_tools.dart`, `mcp/schedule_tools.dart`, `mcp/attach_media_tool.dart`, `mcp/wiki_write_tool.dart`: `workflow_run`/`schedule_upsert`/`attach_media`/`wiki_write` write, `workflow_list`/`schedule_list` read) follows the same rule, and all six carry a `CanonicalTool` mapping, so a container authority reaches exactly what the host lane of the same kind reaches: the primary is the deployment and gets all six, while a task or workflow lane gets only what its own `allowedTools` names (an `mcp_call`-only lane still gets none). That widening is deliberate — container is the default posture, and withholding them there would make the default a capability regression. They are adapters over `WorkflowService.start`, `ScheduleMutationService`, `DeliveryService.deliverMedia` and `WikiPageStore.writePage`, and none re-derives a rule its service owns. The per-tool schema pass is one shared authority now, `mcp/tool_schema.dart` (`toolSchema`/`toolJson`/`toolError`/`validateToolArguments`), consumed by both the task surface and this one; it covers `required`, declared type, `enum`, integer bounds and the declared element type of an array or free-keyed object, and its default arm refuses a type it cannot check. Extend that pass rather than adding a second validator to a tool.
- **Host tool-result cap** — `ResultTrimmer` (`lib/src/context/`) is applied at exactly one place: `McpProtocolHandler`'s `tools/call` dispatch, to a `ToolResultText` only (a tool's error result passes through, which S04-style tests pin). `scopedTo` shares the instance by reference so a containerized caller cannot bypass it, and `dartclaw serve` threads the `ConfigNotifier`-registered instance through `ServerCoreDeps.resultTrimmer` — construct a second one and `context.max_result_bytes` stops hot-reloading. The cap is the *outer* bound: a tool with its own smaller-looking envelope (`memory_read`'s 64KB) or a larger declared allowance (`max_response_bytes`) is still cut here. Nothing on the turn path reshapes an assistant reply.
- **Search consumers** — MCP memory search, Knowledge Hub, and Context Research consume the same configured `SearchBackend` outcome. The backend is already request-composed with wiki; consumers must not scan wiki again. `LiveCitationSourceResolver` reopens canonical corpus and native layer owners rather than trusting result membership.

## Shape
- **Request lifecycle**: shelf pipeline (auth middleware → security headers → router) → `*_routes.dart` handler → one-shot response or SSE via `sse_broadcast.dart`.
- **Turn lifecycle**: route handler → `TurnManager.reserveTurn(sessionId)` (per-session reservation chain, then session lock – see Conventions; returns turn token or `BusyTurnException`) → `TurnRunner.execute` (composes prompt, drives `AgentHarness`, applies guards, fires events) → outcome → lock released.
- **Task lifecycle** runs in parallel: `TaskExecutor` consumes the queue, manages worktrees + git ops, emits `TaskEvent`s — workflow-spawned tasks auto-accept, manual tasks park for review.
- **Container orchestration** wraps containerized harness execution: `ContainerManager` applies `SecurityProfile`, delivers the bridge binary read-only, bind-mounts one per-authority generated-state directory (created empty on `start`, destroyed on `stop`), and bind-mounts the execution's `artifactsDir` read-write at `containerArtifactsPath` when it has one — that is what lets a workflow step's host-owned `<dataDir>/workflows/…` artifacts path translate into the container instead of being refused as unmounted. Every runtime call issues `config.runtimeBinary` — the CLI the startup probe answered with (`docker` or `podman`), never a hardcoded literal; `isRuntimeAvailable()` checks that one. `SecurityWiring._wireContainers` **answers a refusal string instead of exiting**: it exits non-zero only when `declaredEnabled == true`, and otherwise hands the reason back to `wire()` for the advisory warning. That asymmetry lives there and nowhere else — replicating it per probe is how one branch drifts. `start()` is single-use: it adopts a healthy container but never recreates a dead one, because the bridges died with it (see the Gotchas note); `HostGateway` binds each `docker exec -i` pipe to one authority, one surface, one upstream, and one tool policy, and refuses registration when the provider's adapter resolves no host credential – so an unmediatable auth configuration is rejected before any container exists, with refusal text from `dartclaw_kernel`'s single `credentialRemediationFor` author. Adapters are keyed by the **provider id an execution names**, not by family: one is built per configured provider plus the two canonical ids, so an alias resolves its own `providers.<alias>.auth` and a per-alias opt-out binds the container boundary exactly as it binds a host spawn. An adapter's credential comes from an injected `ProviderCredentialSource`: `resolve()` answers that admission check synchronously, `present()` is awaited in `ProviderAdapter.handle` immediately before injection so a rotating token can refresh there, and the resolved mode picks the scheme (Anthropic subscription → `authorization: Bearer` plus the `oauth-2025-04-20` beta; API key → `x-api-key`). A credential that turns terminally unusable *after* admission is raised as `GatewayCredentialUnusable`; `GatewayPipe` answers the container with that remediation **before** invoking the gateway's teardown, because a revoked pipe stops writing and a silent close would read as a crash rather than an actionable credential failure. **Exactly two production paths raise it**, and each is the terminal half of a pair whose transient half stays a `GatewayDenied`: `CodexCredentialSource` runs the core refresh authority's freshness gate in `present()` and raises it for a spent refresh lineage while a merely-failed refresh answers `503`; `AnthropicMessagesAdapter.inspectRejection` raises it for a *subscription* turn the upstream answered with a 401, or with a 403 whose body names `authentication_error` — the derived `setup-token` expiry is best-effort, so that live refusal is the only thing that makes a hard expiry fail closed, and forwarding it would leave the container with a bare 401 and the authority mediating on a dead token. A 403 that names no authentication error is forwarded: Anthropic answers `permission_error` for a plan or organization restriction on a token that authenticated fine, and tearing the authority down over one would page the operator to re-run `claude setup-token` for a credential that works. Status-then-marker, the same discipline `codex_rejection.dart` applies. An API-key deployment keeps forwarding the upstream's answer: DartClaw tracks no lifetime for an operator-managed key. Both refusal paths report through `HostGateway`'s `onCredentialRefused` sink — the single announcement point — and never fire an event themselves; the sink's one bind point (`runtime/security_wiring.dart#_reportCredentialRefusal`) reports `reauth-required` to `CredentialHealthMonitor`, falling back to a severe log line only while no monitor is bound. Scoped memory writes receive only that authenticated principal plus a unique host-generated call event; model arguments never supply provenance.

## Runtime composition (`lib/src/runtime/`)

`DartclawRuntime.build(config, {headless, harnessRegistrars, …})` (`runtime/service_wiring.dart`) is the one entry
point that assembles a runtime — storage, security/guards, harness and provider execution, the execution coordinator,
tasks, channels, scheduling, the workflow registry/service, and the `DartclawServer` itself. `headless: true` omits
every inbound and scheduled surface (no server, channel manager, heartbeat, schedule service or token service) and
keeps the rest identically; `runtime.server` is non-null exactly when `headless` is false. `runtime.shutdown()` owns
the teardown, ending with the search database. `dartclaw_cli`'s `ServeCommand` is a caller, not the composition root:
it parses flags, resolves config and assets, calls `build`, binds the listener, and calls `shutdown()`.

`DartclawRuntime.stageHeadless(...)` is the **same** assembly, paused after its base phase (storage, projects and the
workflow registry) and returned as a `HeadlessRuntimeStaging`. It exists because the zero-server `dartclaw workflow`
lane has to gate provider auth *between* base-service assembly and execution assembly, and only knows the provider set
once its definition resolves: read `staging.workflowRegistry` / `loadWorkflowRun`, call `preflightProviderAuth`, then
`completeForExecution(providers)` — or `completeForLifecycle()` for `cancel`/`pause`, which composes neither the security nor the harness layer, so `executions`, `resetService` and `selfImprovement` are null there and are read through the `require*` accessors that refuse by name. Exactly one completion may run;
until one does the staging owns teardown (`dispose()`), afterwards the returned runtime does. It composes **no** second
service graph, and the standalone-only behaviours are parameters of the one root, not a fork:

- The registry is built in the **base** phase, so a caller can resolve a definition before any execution capacity
  exists. Its `continuityProviders` therefore come from `HarnessFactory.probeContinuityProviders()` capability probes
  (`cwd: '/'`, no spawn) rather than from a wired harness — that is what makes a registry available before one exists.
- `runtimeCwd` (default `Directory.current.path`) is the repository the runtime operates on — `MergeExecutor`,
  `WorktreeManager.projectDir`, `DiffGenerator` and, for `serve`, the artifact workspace.
- `localFallbackDir` is non-null **exactly when the composition came through `stageHeadless`** — `build(headless: true)`
  leaves it null and keeps the managed-workspace posture, because the flag also arms a destructive sweep and no SDK
  embedder asked for that against its process cwd. It is the single arm selecting the
  local-repository posture: a run may resolve no project (absent or `_local` id) and falls back to it; worktrees root
  at `<localFallbackDir>/.dartclaw/worktrees` instead of `<workspaceDir>/…`; it is the workflow output-validation root
  (`WorkflowGitContext.defaultWorkspaceRoot`); it selects the local/remote-push publish arm over the project-auth + PR
  one; it enables source-tree discovery for skills and workflow YAML; and it turns on the teardown sweep
  (`cleanupTrackedWorkflowGit`) that returns the invocation repository to a clean state.
- `workflowProviderScope` (`HarnessWiring`) provisions coordinator-worker capacity for the named providers **only**
  and builds no primary harness, no primary runner and no `ProviderValidator` pass — a workflow-only build must not
  spawn a primary vendor CLI it never uses, and an unreferenced logged-out provider must not block a run that does not touch it. A scoped id
  naming no configured provider raises rather than exiting, because that process installs no log listener.
  `runtime.harness`, `HarnessWiring.healthService`, and `HarnessWiring.sseBroadcast` are therefore nullable; the server-composed surfaces read
  `primaryHarness` / `primaryHealthService`, which refuse by name.
- `HarnessWiring` receives a turn-manager getter that answers `null` in a headless build. Logical-agent dispatch and
  continuity reset retain their named refusal. Task-feedback dispatch reads the shared turn manager directly;
  channels and the MCP handler alone resolve `composedServerGetter`. The SSE field is ordinary nullable, not `late`,
  so an absent broadcaster does not retain API type metadata in the workflow-only AOT binary.

`HarnessRegistrar` / `HarnessRegistration` (core's `harness/harness_registrar.dart` — the contract sits below this
package so an adapter can implement it without depending on the runtime) let whoever composes the runtime
contribute provider families this package does not name — owned provider entries, a declared container profile, a
credential overlay, and startup warnings — while harness registration itself goes through core's
`HarnessFactory.registerFirstClaim`. **A registrar reaches the runtime only as a `DartclawRuntime.build` argument**: no static
field, top-level mutable, `Expando` or `ensure…Registered()` import-time side effect, because a registration nothing
in a pubspec or import records is exactly the service-locator pattern ADR-034 rejects. The empty default composes
what a build with no registrar composes: a profile lookup that owns nothing, an empty owned set, the first-party credential arm,
`config.providers` alone.

The wiring is split by domain — `storage_wiring`, `security_wiring`, `harness_wiring`, `channel_wiring`,
`task_wiring`, `scheduling_wiring`, `project_wiring` — with `service_wiring.dart` (plus its five `part` files)
threading cross-domain dependencies. `composeServerTurns` / `composeServer` (`server_composition.dart`) are the
package-local seam that builds the `TurnManager` and assembles `DartclawServer` from its `Server*Deps` groups;
tests construct sparse compositions through the same two functions.

- `HarnessWiring` warns when optional security guards are disabled and when configured agent tool policy cannot be fully host-mediated: Codex approval omitted/invalid/other than `on-request`, or ACP operations outside reverse-call/permission coverage. Beside those, `_warnUnhardenedPrimaryOnChannelIngress` warns once for the unhardened-primary posture — container isolation available, `agent.execution` not `container`, `agent.disallowed_tools` empty, and some channel resolving `enabled: true` through `anyChannelEnabled` (`config/channel_config_resolver.dart`, the one channel parse). It is gated on `SecurityWiring.containersEnabled` because `_warnHostAccess` already owns the isolation-off posture; never widen it to fire there too.
- **`HarnessWiring` composes the one `ProviderExecutionInventory` and emits every execution-boundary diagnostic from one block.** ACP registrations with `container_isolation_required: true` are startup-fatal (`acpContainerRequirementError`) before any probe or registration; the inventory is then built from the configured provider IDs plus the ACP set, and the same block logs `hostOverrideWarnings()`, `failClosedWarnings()`, `providerCompatibilityWarnings()` and the `ProviderValidator` warnings through one deduping `warn` closure (the compatibility pass and the startup gate word an unpresentable credential identically, so the line is logged once). Both admission paths (`_primaryContainerManager` and the coordinator's `createWorker`) reject on that inventory's verdict — don't add a second emitter or a local compatibility check.
- **The inventory carries the host boundary's credential gate, and it is the only thing that refuses a host worker *on credential grounds*.** `createWorker` refuses first and independently — an unknown provider, or a container profile outside that provider's allowlist, throws `WorkerCreationException` before the verdict is consulted — so the inventory is the credential authority, not the only gate. `ProviderExecutionInventory.of(credentialGate:)` takes `HarnessWiring._credentialRefusalFor`, consulted per verdict rather than snapshotted — a store is re-read per spawn. Not injecting a credential is **not** a refusal: both vendor CLIs self-authenticate behind an empty environment (`claude auth status`, `~/.codex`), so a forced `providers.<id>.auth` that cannot be satisfied has to be rejected before `_harnessFactory.create`. The gate refuses every `CredentialUnavailableReason` **except** `noneConfigured` — that one exclusion is what keeps "nothing selected, so the vendor CLI's own login is admissible" alive, and removing it breaks 0.24 parity. It also skips a provider declaring `credentials_required: false` and any ACP registration, matching `ProviderValidator`. A provider *alias* has no support record (`ProviderIdentity.family` does not resolve aliases), so the gate is consulted even when the inventory holds no entry — that is precisely the shape the aliased-provider fall-through took.
- **`HarnessWiring` owns every containerized execution's bridged-MCP grant.** Deny-by-default for scoped identities: a logical agent's `allowed_tools`, or — for background work, which has no agent definition — the tool policy already on the execution request (`ExecutionRequest.allowedTools`, set by `TaskExecutor` from the task's own policy). The primary lane is the exception: it is the deployment itself, so it is granted the servable map (`_ownMcpToolCanonicals`) minus the session-spawning tools and minus `agent.disallowed_tools` — deriving from that map rather than from `_semanticMcpTools` is what keeps tools registered elsewhere (the task/review/binding tools, registered from `_registerMcpTools`) in the primary grant without a second list to keep in sync. Every grant is intersected with the tools this deployment actually registers (`_ownMcpToolCanonicals`), warning once per unservable entry — a `web_search` grant with no `search.providers` is reported at startup, not at the agent's first turn. Warnings about a container reaching *no* host tool are narrowed to the cases where that is real capability loss (the `restricted` profile, or a configured grant that turned out entirely unservable); an ordinary workspace task with no tool policy is the intended default and stays silent. **A workflow step is no exception:** its leased coordinator worker derives the grant from this owner and runs every step turn on that worker's `TurnRunner`.
- **Native provider web tools are suppressed for every container profile, not just `restricted`.** `WebSearch`/`WebFetch` execute at the provider rather than in the container, so `network:none` cannot contain them and `ProviderAdapter` 403s any request declaring one — from any profile. `workerDisallowedTools` therefore adds both to every container execution regardless of what the bridge serves (the harnesses do the same independently: `ClaudeCodeHarness._deniedNativeWebTools`, and `nativeWebSearch: false` on every `CodexEnvironment.containerAuthClean`). Bridged MCP is a container's only web path; re-adding a "keep native search when nothing bridged is granted" fallback puts the harness back in contradiction with the gateway and 403s every turn.
- `HarnessWiring` owns MCP disallowed-tool derivation, using `mcpDisallowedTools`, declared beside it in `runtime/harness_wiring.dart`, to suppress `WebFetch` and (conditionally) `WebSearch` when MCP is active. The standard MCP endpoint is active with gateway authentication or on an authentication-disabled loopback deployment; non-loopback authentication-disabled deployments never advertise or mount it. Mirror any new built-in tool overlap there.
- `StorageWiring` owns the shared `MemoryCorpusService`; startup and offline rebuild stream independently bounded member projections, prove exact FTS5 row parity, and re-authenticate the complete canonical union before publishing healthy. Incremental projection advances healthy evidence only from an exactly healthy base. Derived-index failure boots degraded with canonical memory available; only unreadable canonical memory aborts startup.
- `HarnessWiring` registers the four-tool memory contract in endpoint and direct-SDK modes: `memory_apply` and `memory_observe` are writes; `memory_search` and `memory_read` are read-only. Write provenance comes only from host-owned context – the active turn for direct SDK calls, or the authenticated principal plus a unique host-generated call event for a container bridge.
- `HarnessWiring` composes the primary static prompt from the shared corpus authority. Human channel/web turns use `PromptScope.primary`; scheduled, workflow, extraction, and logical-agent turns pass `PromptScope.task` explicitly.
- `HarnessWiring` handles Claude `PreCompact` by persisting a redacted, UTF-8-bounded conversation-tail observation with host session provenance before the harness acknowledges the hook.
- `SchedulingWiring` owns built-in job registration plus its duplicate-ID checks. The opt-in `memory-journal` and `memory-curation` jobs are prompt-based; both are refused at load when a `scheduling.jobs` entry claims their ID (`validateMemoryJournalConfig` / `validateMemoryCurationConfig`). That is a **config-load** rule, not a mutation rule: `memory-curation` is an ordinary job ID at the HTTP surface (create, edit and delete all succeed) since the reserved-system-action 409 was removed with `SystemAction`, and `ScheduleMutationService` deliberately does not reintroduce it — a refusal there would fork a rule the web API does not enforce. `SchedulingWiring` also owns the one `DeliveryService` (`deliveryService`, constructed unconditionally so `attach_media` can reuse announce delivery's DM-target resolution), which it hands `MessageService`, `MemoryFileService`, the deployment `MessageRedactor` and `TurnManager.resetSessionContinuity`: an announce writes the result into every DM session it reached and resets that session's continuity so the next turn replays it, plus one daily-log record per fire — the record shape and its caps are the shared `memory/daily_log_record.dart` helper that human-facing turn capture uses, never a second copy and `ScheduleService.entries`, the projection `schedule_list` joins against `ConfigWriter.readSchedulingJobs()` to tell a loaded job from one the composer could not build. `ScheduleService` itself is constructed unconditionally too (heartbeat and credential health are always registered, and a live write needs a scheduler to reach). Config-declared jobs — prompt entries and `type: task` entries alike — come from the one `composeConfigJobs` (`scheduling/scheduled_task_runner.dart`) that `SchedulingJobsApplier` also uses; don't reintroduce a second `ScheduledJob.fromConfig` loop in the wiring. The hourly `credential-health` job comes from the top-level `buildCredentialHealthJob`, and `wire()` probes once during wiring so a `serve` started with an already-degraded credential reports it immediately; `runtime/service_wiring.dart#_wireCredentialHealth` builds the per-probe resolution closure over the live `ProviderStatusService` the API reads, rebuilding the registry from the context-held `SubscriptionCredentialStore` each run so a renewed credential is seen without a restart.
- **The credential-health monitor is late-bound into `SecurityWiring`, and `HarnessWiring`.** All three are constructed before the monitor, which needs the built `ProviderStatusService` at step 8, so the composition root assigns `security.credentialHealth` and `harness.credentialHealth` there rather than passing a constructor argument — never construct a second monitor, and never reorder the steps to avoid the setters. `HarnessWiring` is the **host** boundary's producer: `_reportHostCredentialHealth` is fed by the `createWorker` credential refusal and by `prepareCodexSubscriptionHome`'s `onCredentialHealth` sink. Active in-`serve` and standalone workflow steps both acquire that coordinator worker, so their refusals and Codex refresh failures report through `HarnessWiring` too. Its refusals report `reauth-required`; a transient Codex refresh failure reports `refresh-failure`. The **primary** lane is outside that producer entirely: `_primaryContainerManager` throws `StateError(verdict.message)` on an unsupported verdict, reporting nothing and logging nothing — its spawn precedes step 8, so the operator meets the refusal as a failed startup carrying the gate's own message, not as a credential-health transition or a severe log line. `SecurityWiring` has exactly two report sites, both single call sites: `_reportCredentialRefusal` (the gateway's `onCredentialRefused` sink, admission and mid-turn, reporting `reauth-required`) and `_reportCodexCredentialHealth` (fed by `CodexCredentialSource.onRefreshOutcome` and `OpenAiResponsesAdapter.onRejection`; a spent refresh token and a 401 report `reauth-required`, a transient refresh failure `refresh-failure`, a scheme rejection `contract-break`). A rotated-away credential, a 429 usage limit and a rejected model are **not** credential conditions and must not report — paging for a re-login there is a false alarm. Both sites keep their log line as the no-monitor degradation FR6 requires; do not write it alongside a report, since the monitor logs its own transition.
- **Per-runner guard chains are layered.** `runtime/harness_wiring.dart` gives the primary harness and every worker a `GuardChain.layered` chain: the shared `SecurityWiring` base chain plus that runner's own `TaskToolFilterGuard` (per-task/per-turn `allowedTools` + read-only enforcement, e.g. the knowledge-inbox no-tools turn policy). Never hand `_security.guardChain` directly to a harness — the runner's filter would be inert. A guards.* hot-reload swaps only the base list and reaches all runner chains live.
- `HarnessWiring` owns one `ExecutionCoordinator`: one fixed serialized primary lane for interactive web/channel turns, plus hard per-provider worker-lease capacity for tasks, schedules, system work, workflow steps, and logical-agent sessions. Deployment construction inputs are immutable; workflow workers additionally carry request-scoped artifacts and sanitized spawn-environment inputs and are always single-use. Other workers start lazily, healthy host workers may be reused only for the same provider/profile, and a logical-agent container may be retained only for the exact session/agent principal until discard, eviction, or shutdown. `sessions_spawn` pins `SessionType.logicalAgent` to `AgentDefinition.provider` (or the default provider when omitted) and the policy resolved by `ExecutionPolicyResolver` (execution mode plus container profile); `sessions_send` persists and replays history and never routes to primary. Both pass explicit persona/model/effort overrides; omitted model and effort inherit provider defaults. Logical agents are not serialized into provider-native initialization payloads.
- `SecurityWiring` builds one `ContainerManager` per live authority, giving it a per-authority generated-state directory under `<dataDir>/containers/<containerName>`, the execution's host artifacts directory (mounted read-write at `/artifacts`, so a workflow step's `DARTCLAW_STEP_ARTIFACTS_DIR` — a `<dataDir>/workflows/…` path in no profile's mount set — translates instead of throwing), and whether an MCP bridge exists (`hasMcpBridge`, derived from the granted tool set). It registers each authority container with `ContainerHealthMonitor` under the leasing principal's `taskId`, so a crash fails that execution alone. `ContainerAuthorityCleanupOwner` retains every lease until destruction is confirmed, coalesces concurrent releases, retries failed destruction, and sweeps active/pending authorities at shutdown. Every manager carries the `dartclaw.data-dir` owner label with the data-dir string verbatim; `ContainerManager.reclaimOwnedContainers` sweeps that label after the boot runtime probe and after lease cleanup at shutdown. No periodic sweep, no prefix sweep. `HarnessWiring.wire` constructs the primary harness; runtime assembly starts it only after MCP registration, so startup discovery sees the complete tool surface. Task polling and scheduling activate only after primary startup and the post-MCP startup hook succeed. Failed startup uses the assembled runtime shutdown. `HarnessWiring` captures the primary authority's container name on acquisition and listens for its `ContainerCrashedEvent`, emitting a distinct severe operator signal (restart-to-recover) — the containerized primary has no auto-recovery (deliberately deferred), so its loss must not read as an ordinary per-task crash. It mounts **no** host provider home: containerized Claude is mediated host-side on whichever credential the host resolves — a stored `setup-token` presented as a Bearer, or an `ANTHROPIC_API_KEY` — and a host holding neither is a startup warning plus an admission-time rejection at `HostGateway.register`, never a `~/.claude.json` mount.
- **There is one spawn resolution and one spawn-env builder, and every active lane uses them through `HarnessWiring`.** `runtime/provider_resolution.dart` answers which binary a provider id runs (`resolveProviderTarget` → `ResolvedProviderTarget`: executable, options, executable-aware family, ACP registration) and builds the environment for it (`buildProviderSpawnEnvironment`, plus the probe variant below). The primary harness and every coordinator worker, including the single-use workers leased by in-`serve` and standalone workflow steps, resolve at worker creation in `runtime/harness_wiring.dart`; each step then runs on that worker's `TurnRunner`. The Codex refresh authority's `codex app-server` drive is *not* a provider spawn and resolves through `resolveCodexVendorExecutable`, which is blind to `harness.acp.agents` on purpose — that drive carries the dedicated `CODEX_HOME`. `SafeProcess.sanitize` runs inside the builder and the credential overlay strictly after it (the overlay functions are private to the module, so no caller can hand it a pre-sanitized map); a claude-family target additionally gets `claudeHardeningEnvVars`. **A Codex subscription is a credential too, and it is presented as `CODEX_HOME`, not as a variable the resolution can hand over.** Active host spawns get that home from `HarnessWiring` per worker through `prepareCodexSubscriptionHome`; a **probe** — skill introspection and the CLI auth preflight — runs the vendor binary with nothing downstream, so it must resolve the home itself through `buildProviderProbeEnvironment`. `prepareCodexSubscriptionHome` is where the home is *completed*, not merely named: it calls core's `completeDedicatedCodexHome`, which mirrors the operator's plugin tables, plugin cache and skills into the store. That call belongs there and nowhere else — a probe reaches the home before any worker has built one, so completing it at worker setup alone would leave the first preflight on a freshly logged-in store reporting every `andthen:*` ref unresolvable. Completion is idempotent, not additive: core's single writer re-derives the operator's plugin tables on every call and rewrites them around whatever generated half is already in the file, so a probe never clobbers a worker's developer instructions and a worker never re-adds a plugin the operator uninstalled. That builder is used by both probe lanes (`runtime/service_wiring.dart#_providerProbeEnvironment`, surfaced as `DartclawRuntime.providerProbeEnvironment`, and `dartclaw_cli`'s `workflow/workflow_validate_command.dart`). The probe env builder is therefore `async`, and so are `SkillProbeEnvironmentBuilder`/`AuthProbeEnvironmentBuilder`. A probe lane that overlays nothing for a Codex subscription is *not* harmless: the vendor CLI falls back to the operator's own `~/.codex`, or fails the turn and reports it as a skill-introspection error long after auth was declared fine. The family is always `ProviderIdentity.resolveFamily` (executable-aware) — `ProviderIdentity.family` is plain normalization and misclassifies a provider alias as its own family, which is exactly how an aliased Claude provider ends up spawning with no credential. A claude-family spawn presents exactly what the resolution names — `CLAUDE_CODE_OAUTH_TOKEN` for a stored `setup-token`, the API-key variables for a key, **nothing** when `providers.<id>.auth` rules both out; other families keep the plain API-key overlay. The order matters: sanitize strips every inherited `*_TOKEN`, which is what makes the dedicated store authoritative over an operator's own exported value — never weaken that pattern list to "fix" it.
- **An ACP registration is credential-isolated, and that is the whole rule.** The registration travels on the `ResolvedProviderTarget`, not with the lane, so no lane can resolve its binary and then overlay DartClaw's own credential: `buildProviderSpawnEnvironment` takes the ACP branch whenever `target.acpAgent` is set, and no `providers.<any>.auth` or `credentials.anthropic|openai` is consulted, `_subscriptionHomeFor` answers `null` before it resolves a family (a dedicated `CODEX_HOME` *is* the subscription presentation), `buildProviderProbeEnvironment` skips the Codex store gate for one, and `_credentialRefusalFor` keeps its ACP skip. `HarnessWiring` owns active workflow provider resolution and passes its registrar overlay while creating the coordinator worker, so a registration owning a step's provider presents its own overlay (or the bare environment) rather than the first-party arm. The retained `TaskWiring.workflowProviderConfig` compatibility path receives the same overlay but is active-step-unreachable. `model_provider` routes and validates; it selects no credential — the mapping that turned `anthropic`→`claude` and `openai`→`codex` was removed in 0.24.2, so do not reintroduce a credential-provider-id translation anywhere. The one injection path is `harness.acp.agents.<id>.credential`, a `credentials.<name>` **API-key** reference; config load drops and warns about every other shape (unknown name, `github-token`, empty value, literal key with no `${VAR}` name), and the overlay fails closed on the same rule. Sanitize still strips the agent's own inherited `*_API_KEY`/`*_TOKEN` — intended: the agent reads its own config or keyring.
- **One `CodexRefreshAuthority` per process, constructed beside the store it rotates.** `DartclawRuntime.build` builds it on the `_WiringContext` and threads the same instance into `SecurityWiring` (the gateway's `CodexCredentialSource`) and `HarnessWiring` (primary and coordinator-worker host spawns). Active in-`serve` and standalone workflow steps therefore refresh through `HarnessWiring` before the coordinator worker starts, then execute on that worker's leased `TurnRunner`. `workflow validate --skills` is a separate process with its own store open, so `_buildIntrospector` builds one there, beside that store. Single-flight is a property of the instance, so a second authority is a second refresher — never construct one inside a wiring class or a per-request closure. Host Codex spawns reach it through `prepareCodexSubscriptionHome` (`runtime/provider_resolution.dart`), which answers `null` only when a credential is genuinely presentable another way — a resolved API key, or nothing selected at all (`noneConfigured`) — and **throws** for every other unavailability reason and for a terminal refresh outcome: returning `null` there would spawn against the operator's own `~/.codex` login, which this deployment must never read. `apiKeyAbsent` is a throw for exactly that reason; it reads as the mildest case and is the one where the fall-through hurts most. Refusal text comes from `credentialRemediationFor` — never hand-author one here — and travels with `credentialsDir` so the operator learns which store was searched.
- **`SubscriptionCredentialStore.open` belongs in a lane's composition root only.** Four sites, one per lane: `_RuntimeAssembly` (both `DartclawRuntime.build` and `DartclawRuntime.stageHeadless` — held on the wiring context and shared with security/harness wiring), `workflow_validate_command` (one-shot validate), `dartclaw_cli`'s `commands/auth/auth_subcommand.dart#AuthSubcommand.openStore` (the `dartclaw auth` group, opened once per invocation), and `dartclaw_cli`'s `commands/init/setup_checks.dart` (`dartclaw init` verification, opened once per verification). Never open it inside a per-request or per-provider closure; opening creates and chmods directories and runs the login-collision guard. `DartclawRuntime.build` takes an `environment` argument (defaulting to `Platform.environment`) purely so that guard is testable: the collision is resolved from `CODEX_HOME`/`CLAUDE_CONFIG_DIR`/`HOME`, and without that seam the only way to provoke one is to write into the developer's real `~/.codex`. In `serve`, every active consumer that resolves a credential after wiring rebuilds its registry per use, so a re-issued token is picked up without a restart: `security_wiring`'s gateway adapters, `HarnessWiring`'s coordinator-worker spawn environment and per-worker Codex home, `service_wiring`'s probe lane, its workflow auth preflight and its hourly credential-health probe. Standalone workflow execution composes the same root headlessly; `stageHeadless` passes the invocation environment as an ordinary production input, while `HarnessWiring` resolves each active step worker from the current store state in that process.
- **`CredentialRegistry`'s `providers:`/`subscriptions:` arguments default to empty, and every construction site must decide.** A site that omits them silently resolves as if no subscription credential and no `providers.<id>.auth` existed — the analyzer says nothing. Pass both at any site feeding a spawn env, a mediation adapter, or an auth decision (`runtime/service_wiring`, `runtime/harness_wiring`, `runtime/security_wiring`, `runtime/task_wiring`, `dartclaw_cli`'s `cli_workflow_wiring` and `workflow_validate_command`, `setup_checks`). `setup_checks` resolves the full picture — an unusable store degrades to "no subscription stored" rather than failing the verification — and falls through to the vendor `probeAuthStatus` only on `noneConfigured`, mirroring `ProviderValidator`.
- **Provider spawn env must keep `USER`.** `buildProviderSpawnEnvironment` (`runtime/provider_resolution.dart`) sanitizes with no allowlist, so `USER` survives — the standalone `claude` CLI reads its keychain subscription OAuth only when `USER` is present (`HOME`+`PATH` alone → "not logged in"). Never add an allowlist that drops it; a regression test pins this.

## Boundaries
- Allowed workspace prod deps (arch_check L1): `dartclaw_bridge`, `dartclaw_core`, `dartclaw_google_chat`, `dartclaw_kernel`, `dartclaw_signal`, `dartclaw_whatsapp`, and `dartclaw_workflow`. Plus the listed external libraries.
- This is the only package allowed to import from all channel packages. Channel-specific transport and webhook ingress stay in their own packages; this package mounts and wires them and supplies runtime-owned collaborators such as `SlashCommandHandler`.
- `OpenAiResponsesAdapter` owns two pinned upstreams, selected by the presented credential's mode and nothing else: an API key goes to the OpenAI Platform, a ChatGPT subscription credential to `https://chatgpt.com/backend-api/codex` with `Authorization: Bearer`, `ChatGPT-Account-ID`, and the `originator` header, both read per request because the token rotates one-time-use. That upstream carries a base path, which is why `ProviderAdapter.composeTarget` exists — the base implementation replaces the whole upstream path and would silently drop it. Every composed target is checked against `pinnedOriginsFor(credential)` before a connection opens — the pin is mode-scoped, so the presented credential admits exactly one origin (ChatGPT backend for a subscription, Platform otherwise) and a cross-mode target is refused rather than sent to a backend that would never accept it — and a `>= 400` answer is read rather than streamed so `inspectRejection` can classify it (`codex_rejection.dart`) into the four independent buckets S04/S05 consume — it receives the presented `CredentialResolution` and classifies **only** a subscription refusal, since every bucket names a ChatGPT-backend condition an API key never reaches. It never raises `GatewayCredentialUnusable`: an API-key answer is forwarded unchanged, and the subscription lane's terminal half lives in `CodexCredentialSource`, not here.
- **`ProviderAdapter` strips headers in both directions, and the strip is its own guarantee.** The request list drops what a container must not choose (credentials, routing, hop-by-hop, framing, and `chatgpt-account-id`, which the host sets only when its token names an account); the response list drops what must never enter the boundary (`authorization`, `x-api-key`, `proxy-authenticate`, `set-cookie`) because the pipe is the only channel into a `network:none` container and an upstream or error page reflecting a request header back would hand the host credential straight in. Both compare lowercased inside `handle` — never rely on a producer normalizing first, even though `GatewayPipe` does.
- Container orchestration (`lib/src/container/`) lives here, not in core — `ContainerManager`, `SecurityProfile`, `HostGateway`. Don't move it down. The framed wire contract itself lives in `dartclaw_bridge`, which both this package and the in-container executable compile against; nothing security-relevant may move there, since the bridge runs inside the boundary.
- Provider launch compatibility is `dartclaw_core`'s `ProviderExecutionInventory`, not a local rule. `ExecutionPolicyResolver.providerCompatibilityWarnings` checks it *after* resolution (it never selects a replacement policy).
- Workflow execution semantics belong in `dartclaw_workflow`. Active workflow-task glue (`workflow_one_shot_runner.dart`, `workflow_turn_extractor.dart`, `workflow_worktree_binder.dart`) lives under `lib/src/task/` and injects git impls (`MergeExecutor`, `RemotePushService`, `PrCreator`) into the workflow port.

## Conventions
- Add new dashboard pages by registering a `DashboardPage` with `PageRegistry` (`lib/src/web/page_registry.dart`). Routes must start with `/` and not collide with the reserved-route patterns (health, static, /login, channel pairing, etc.) — `register()` throws on conflict, applying the same checks to the page's `declaredRoutes`. Nested destinations that should remain routable without becoming top-level sidebar items implement `DashboardNavigationExclusion`; their handlers activate the parent destination when building nav items.
- Templates are paired `.html` + `.dart` files under `lib/src/templates/` (loaded by `loader.dart`; the file names are listed in `expectedTemplates` — startup fails if missing). Use Trellis with HTML-escaped placeholders; never concatenate user data into HTML strings. Follow `dev/guidelines/HTMX-GUIDELINES.md` and `dev/guidelines/TRELLIS-GUIDELINES.md` for fragments and SSE.
- Third-party static assets under `lib/src/static/` are **all** vendored — see `VENDORS.md` (highlight.js, DOMPurify, htmx-ext-sse, Stimulus, htmx, marked, JetBrains Mono). There are no CDN exceptions: every subresource loads same-origin and the CSP names no external origin. Do not add npm/CDN runtime fetches — `dev/tools/fitness/check_no_external_origins.sh` fails the build on any external subresource in the templates, the served CSS, or the CSP.
- `lib/src/generated/embedded_assets.g.dart` is generated, **not committed** (gitignored). `lib/` imports it, so a fresh checkout does not analyze until you run `dart run dev/tools/embed_assets.dart`. Re-run it after any template or static asset edit; never hand-edit it. CI, `dev/tools/build.sh`, and `dev/tools/release_check.sh` generate it automatically.
- `lib/src/static/{tokens,design-system,icons}.css` are generated by the same tool from `dev/design-system/{tokens,components,icons}.css` and are gitignored too — a fresh checkout has no served design-system CSS until the generator runs. Edit the canonical files under `dev/design-system/`; never the served copies. `app.css` and `app-tokens.css` are app-owned composition layers and stay committed.
- `AssetResolver` selects explicit/dev/source-tree files before the embedded fallback. Embedded templates load from the generated map; embedded static files use the in-memory handler. Keep filesystem serving for live-edit modes.
- **`/settings` is a projection of `ConfigMeta`, and no second field list may exist.** `lib/src/web/settings/` owns it: `settings_sections.dart` (the panel/tab taxonomy plus the registry prefixes each panel claims, and the `channels.*` / `guards.*` owned-elsewhere set), `settings_field_view.dart` (`FieldMeta` → control kind, label, hint, tier badge, and the one value-resolution chain: `ConfigSerializer` tree by `jsonKey` → persisted YAML → unset, with `credentials` / `gateway.token` / `github.webhook_secret` masked to a presence marker), `settings_form_model.dart` (panel render model + form-encoded submission decoding), `settings_surface.dart` (the object the page render and `POST /settings` share — built once in `server_deps.dart` and reached only through the registered `SettingsPage`; `webRoutes` builds none of its own). `templates/settings_form.html` is the swappable fragment; `settings.html` hand-authors no `data-field` markup. Adding a config key puts a control on the page with no template edit — `test/web/settings_form_test.dart` fails on a registered field no panel and no owner claims. `ConfigMutability` reaches the renderer as an enum; never parse a tier out of `_meta.fields`, a description or a rendered attribute. A submitted key the panel does not render is passed straight to `ConfigValidator` rather than dropped, so readonly and unknown keys meet the refusal `PATCH /api/config` returns, in the validator's own sentences. Two checks run before that pass-through, and both refuse only **writable** keys so the validator keeps its sentences for everything else: a key `settingsFieldOwners` assigns to another surface (`channels.*`, `guards.*`) is refused because `settingsPanelForField` answers null for those prefixes, and a key a *different panel* renders is refused because the response re-renders only the submitted section, so an accepted cross-panel write would leave no trace on the page. What is still not refused is a writable key no panel and no owner claims - do not read the pass-through as a guarantee that a panel can only write what it renders.
- `SettingsPage` owns channel-detail and guard-editor routes. Purpose-built channel and guard controls share `SettingsSurface`'s config-apply path; non-purpose-built `channels.*` and `guards.*` fields use its registry projection. `ChannelAccessService` is the single allowlist and pairing authority shared by the web and frozen JSON APIs. The guard pattern tester deliberately remains the only JSON interaction in `dc_settings_controller.js`.
- **`ScheduleMutationService` (`lib/src/scheduling/schedule_mutation.dart`) is the one `scheduling.jobs` mutation authority.** It owns `CronExpression.parse` validation, the `schedule`-or-`at` rule (`resolveSchedule`: exactly one, `at` an ISO-8601 instant still in the future, stored verbatim as `{type: once, at}`), the built-in-id refusal, id-or-name lookup, fresh reads, create/update/delete validation and merging, and writes. The JSON scheduling handlers and `SchedulingPage` consume its result values and map them to their own response encodings; the `schedule_upsert` tool consumes the same low-level validation and write seam for its upsert-shaped contract. Do not add a `CronExpression` reference, scheduling uniqueness decision, or direct `scheduling.jobs` write back into an HTTP route.
- **A `scheduling.jobs` write is live before it is answered, and records no restart marker.** Every seam write runs `commitAndApply`: commit, then await the injected `applyJobs`, which is `SchedulingJobsApplier` (`lib/src/config/scheduling_jobs_applier.dart`, beside `RuntimeToggleApplier`). The applier re-reads the *written file* through `loadDartclawConfig` — a seam write does not move the in-memory `DartclawConfig` — composes with `composeConfigJobs`, and hands the result to `ScheduleService.replaceConfigJobs`, which diffs by id against loaded jobs marked `ScheduledJob.isConfigDeclared` and never touches a built-in. The applier and the reserved built-in ids reach the seam's three construction sites (`api/config_api_routes.dart`, `runtime/service_wiring_mcp_tools.dart`, `web/pages/scheduling_page.dart#_mutations`) as lazily resolved closures threaded from the composition root, the way `scheduleServiceGetter` already is — never import the scheduler or the wiring into the seam. `ScheduleMutationService.commit` and `removeJobs` are the applier-less writes: they persist an unload the runtime has already performed, so they must not re-apply.
- **A one-time (`once`) job removes itself.** `ScheduleService` reports every terminal disposition of a one-time fire — completed, retries exhausted, skipped by the running guard, run on demand, or an instant already past when it is armed or resumed — through the single `onOneTimeComplete` callback the wiring binds to the seam's `removeJobs`. There is no second timer or state map for one-time jobs, and `_reschedule`/`_scheduleNext` refuse to arm a job object that is no longer the one loaded under its id, which is what stops a job deleted mid-fire from re-arming a zombie timer.
- **`ConfigApplyService` (`lib/src/api/config_apply_service.dart`) is the one config-apply authority.** Validate → partition by `ConfigMutability` → write every validated field → fire `ConfigChangedEvent` for live → `ConfigNotifier.reload()` for reloadable (pending-restart fallback) → `writeRestartPending`. `PATCH /api/config` and `POST /settings` are body-parsing plus a call; `normalizeConfigPatch` beside it is the single place the blank-to-null fold, the `provider/model` shorthand and the task-trigger spelling are applied. `restart_service.dart` holds `writeRestartPending`/`readRestartPending`/`restartPendingFields`, re-exported from the API barrel for existing importers.
- **A dashboard page owns its sub-routes and mutations by declaring them.** `DashboardPage.declaredRoutes` is a list of `(method, path)`; the `for (final page in registry.pages)` loop in `web/web_routes.dart` registers each declaration through the same `page.handler` call and the same `_htmlError` wrapping as the page `GET`, and `PageRegistry.register` refuses one that matches a reserved pattern or a method-and-path another page already claims (startup-fatal, not request-time). Path parameters arrive via `request.params`, so one handler signature serves static and parameterized paths — `lib/src/web/pages/projects_page.dart` is the mutation reference, while `tasks_page.dart` and `workflows_page.dart` declare their detail and fragment routes. Adding an owned route needs no `web_routes.dart` edit; only routes with no owning page (`POST /login`) stay registered by hand. Follow the seven-point fragment contract in `dev/guidelines/HTMX-GUIDELINES.md` § *Server-rendered fragment conventions for CRUD surfaces*.
- Routes go under `lib/src/api/*_routes.dart` (one shelf router per domain) with helpers from `api_helpers.dart`, which declares the **only** raw body read (`readRequestBody`) and JSON-object decode helper (`readJsonObject` / `decodeJsonObject`) in that directory – a new JSON route takes its cap from the call site and never re-implements the read; it decodes UTF-8 unconditionally, ignoring any `charset` parameter. The server-owned webhook routes (`webhook_routes`, `github_webhook`) instead read through `readBounded` (`lib/src/auth/auth_utils.dart`) because signature verification needs the raw bytes; Google Chat's package-owned webhook carries the same bounded-read contract in `dartclaw_google_chat`. Nothing enforces this by test, but no unbounded request-body read is left in `lib/src/`: every form post in `lib/src/web/` (`POST /settings`, `POST /login`, `POST /pairing/code`, and the projects and scheduling pages' declared mutation routes) reads through the same `readRequestBody` with its own cap and returns its `413`/`400` envelope verbatim, so a JSON envelope can reach an HTML form client on a refusal. Empty-body meaning and error messages stay at the route: the three live policies (empty form body → empty map, `PATCH /api/config` → `400`, subscription mutations → `400`) are contracts, not accidents. SSE streams use `sse_broadcast.dart` / `stream_handler.dart` — don't roll new SSE plumbing. `sseResponse` disables Shelf and proxy buffering by default; frame/header primitives in the same module provide UTF-8 framing, guarded sends, and the explicit buffering header variants. Reuse them instead of inlining `'data: …\n\n'` / response plumbing.
- Auth resolution and base-URL handling belong in middleware/`auth/`, never inline in routes. Use `AllowlistValidator` for outbound URL gating.
- Turn lifecycle: callers go through `TurnManager.reserveTurn` → coordinator lease → `TurnRunner.execute` → outcome/release. `BusyTurnException` is the public busy signal. Don't construct `TurnRunner` directly in routes — go through `TurnManager`. Same-session `TurnManager` callers are admitted in the order they reach `reserveTurn` (per-session `SessionMutationCoordinator` chain; guarantee and accepted consequences are canonical in `dev/architecture/session-state-architecture.md` § 6) – don't add per-caller serialization for that. The chain orders nothing a caller does before `reserveTurn` (session lookup, message persistence – the channel `MessageQueue` FIFO stays load-bearing for those). `TaskExecutor` leases via `_executions.acquire` + `reserveAdmittedTurn` and is outside the chain; no current `TurnManager` caller targets its sessions (the API rejects task sessions, `sessions_send` is logical-agent only) – a new caller that does would interleave with it unordered.
- Turn cancellation is accepted only while provider execution is active. After polling stops, executor shutdown awaits the current poll's worker-registration phase before it snapshots leased tasks; `_pollOnceInner` only schedules `_runLeasedTask`, so this barrier never waits for provider completion. Shutdown then requests `TaskStatus.cancelled` for every running leased task through `TaskService`; an optimistic-transition conflict is re-read and retried only while the canonical status remains running, while a settlement that already reached review or a terminal state wins without rejecting shutdown. Each workflow prompt rechecks that lifecycle authority immediately before reserving its turn, so cancellation during worker acquisition, before a turn or between turns cannot be lost. Once the provider returns or throws, one settlement owner completes guards, persistence, daily logging, and compaction without exposing a cancellable turn state.
- A nonblank `systemPromptOverride` bypasses behavior and memory composition verbatim. Logical-agent sessions acquire an `ExecutionCoordinator` worker lease for the exact provider and effective execution policy; never fall back to the primary lane. All placement resolves through `ExecutionPolicyResolver` — no caller may infer placement from a nullable container manager or re-derive precedence locally. `sessions_spawn` creates the hidden conversation; `sessions_send` requires its existing handle and continues persisted history. Coordinator construction inputs are immutable, so healthy idle *host* workers may be reused only for the same provider and identical `ExecutionPolicy`, preferring the same session. A logical-agent container is retained only for that exact session/agent principal and destroyed when continuity is reset, evicted, or the coordinator stops; task containers are destroyed at turn release. A throwing release-hook or `destroyContainerAuthority` quarantines the slot instead of returning capacity — the same rule as unconfirmed root-process termination — so a fresh authority is never admitted over a possibly-live orphan. **Every observed teardown publishes exactly one terminal event carrying the runner's ID** (ADR-058): `_tearDownWorker` does the physical teardown and emits nothing, the caller withholds capacity, then `_completeWorkerTeardown` emits `quarantined` or `disposed` and only then drops the runner bookkeeping — which is what leaves the trailing `released` notification runner-id-less so it cannot overwrite the `crashed` tombstone `RunnerObserver` retains. Emitting a terminal event inside the teardown, or keeping the bookkeeping past it, puts both defects back. A container authority also owns its bridge pipes: `SecurityWiring.acquireContainerAuthority` returns only once every required surface has handshaked and is listening, and release deregisters health monitoring, revokes the pipes, then destroys the container. Failed first turns use `resetProviderSessionContinuity` so cleanup skips the still-active primary MCP caller and clears idle workers only.
- `CredentialHealthMonitor` (`lib/src/alerts/`) is the single writer of per-provider credential health. The scheduled probe, the fail-closed admission refusal, and the upstream adapter classifications all go through its `probe`/`report` seam — never a direct `CredentialHealthChangedEvent` fire or a direct write to `ProviderStatusService`'s credential cache — so one condition yields one state, one alert, and one warning line no matter which path detected it. It is edge-triggered (unchanged state advances only last-checked), and it writes its `Logger.warning` unconditionally: `AlertRouter._onEvent` returns early when alerts are disabled, no target is configured, or routing excludes the type, and credential health must never be silent. The monitor reads an injected credential-resolution source and never opens a credential store. **It authors no remediation text of its own**: a resolvable `CredentialUnavailableReason` goes to `dartclaw_kernel`'s `credentialRemediationFor`, and the reason-less conditions (a stored credential nearing or past its deadline, or one a detecting path found dead) go to its companion `credentialRenewalFor`. Both take the injected `credentialsDir`, so the wording an operator meets on a provider card cannot name a different store than the one they meet at startup or at admission — a locally-written string is free to drift, and `data_dir` selecting the store is what makes that drift send a credential somewhere the server never reads. A **Claude** provider whose own binary reported an interactive vendor login (`ProviderStatusService.binaryAuthenticated`, the read-only view of the probe cache behind the `oauth` credential status) while DartClaw holds no credential of its own is `unknown`, not `reauth-required` — it authenticates fine, DartClaw just cannot check its lifetime. The exemption is deliberately narrow: it is health-only (admission still fails closed there, since an interactive login is unusable inside a container), it skips a forced `api_key`/unrecognized-`auth` misconfiguration, and it is **Claude-only** — Codex's auth probe merely proves `~/.codex/auth.json` exists rather than that the sign-in is live, and an unrecognized family takes the same `auth status` arm as Claude without anything guaranteeing it means the same thing, so neither is exempt. `binaryAuthenticated` is also a boot-time snapshot — `ProviderStatusService.probe()` runs once at wiring — so a logout mid-session is not seen until restart. **`ProviderStatus.health` folds the recorded credential health in** through the one `CredentialHealthState.isDegraded` predicate (the same one behind the warning line and the alert), so `/api/providers` and the `/settings` card badge cannot report `healthy` beside a `reauth-required` credential; `unknown` is excluded there, and `credentialStatus` deliberately stays a presence answer. That presence answer resolves through `CredentialRegistry.resolve` with the family the provider entry resolves to (`ProviderIdentity.resolveFamily`), exactly as the spawn and container-admission paths do — plain normalization reads an alias as its own family, resolves nothing, and reports a working aliased provider as `missing` **and**, since health folds credential presence in, `degraded`. That one resolution decides the whole surface: the vendor-login auth probe runs only for `CredentialUnavailableReason.noneConfigured` — admission's single rescue — so a forced or unrecognized `auth` reads `missing` rather than `oauth`, and its `errorMessage` credential line comes from `dartclaw_kernel`'s `credentialRemediationFor`. Never re-add an API-key fallback beside the resolution (`hasCredential`): it reported `present` for a provider admission refuses. Don't re-introduce a local "degraded" notion here — one predicate, one verdict.
- Built-in prompt jobs may carry an internal `ScheduledJob.allowedTools` policy. `ScheduleService` forwards it unchanged; user YAML cannot set it.
- `ScheduledJob.composePrompt` is the fire-time prompt seam: it builds the prompt after the cron session resolves and returns an optional release that `ScheduleService` runs after the turn's outcome, success or not. `buildMemoryCurationJob` is its consumer – it composes a bounded corpus snapshot and registers that snapshot's entry IDs as the run's apply scope. Curation keeps no durable record; it is an ordinary opt-in prompt job.
- Built-in prompt jobs may also carry `ScheduledJob.promptResolver` (resolve the prompt at fire time; returning `null` ends the fire quietly – no turn, no session, no failure event, no retry attempt) and `perFireSession` (a session key per fire instead of the shared cron one). Neither has a YAML surface. The resolver runs **before** the session is created, so a skipped fire leaves nothing behind – keep that order. `heartbeat_job.dart` is the one consumer.
- The **heartbeat** (`heartbeat_job.dart`) and **workspace git sync** (`workspace_git_sync_job.dart`) are built-in `ScheduledJob`s, always registered by `SchedulingWiring` and started *paused* when their config key is off. That is what makes `scheduling.heartbeat.enabled` and `workspace.git_sync.enabled` work as `live`-tier keys from either boot state; both toggle endpoints and the `ConfigChangeSubscriber` branches resolve to `pauseJob`/`resumeJob` through one `RuntimeToggleApplier` (`lib/src/config/runtime_toggle_applier.dart`) – put a new live scheduling side-effect there, not in either caller. The applier touches runtime state only; persistence stays with the caller, which is what keeps the toggle routes ephemeral. It is the **only** writer of `push_enabled`: `WorkspaceGitSync` no longer implements `Reconfigurable`, and a persisted `workspace.*` reload reaches it through `WorkspaceGitSyncReconfigurer`, which calls the applier. The persisted write still wins over an ephemeral toggle — that is what ephemeral means — but `RuntimeConfig` moves with it, so `GET /api/settings/runtime` cannot report a value that is not in force. Don't add a second writer back. Don't make either registration conditional – a boot-disabled install would go back to answering `404 NOT_AVAILABLE`. The git-sync toggle's own `404` arm stays on `WorkspaceGitSync == null`, which now means only "no git on PATH".
- `MemoryApplyService` owns CAS, closed change-set validation, audit, index reconciliation – and the run scope. `registerRunScope`/`releaseRunScope` bind a bounded entry-ID set to a session; while one is active `apply` refuses the whole change set if any operation's target or source falls outside it. No scope means no check, so ordinary callers are unaffected.
- `MemoryStatusService` is the single connected operator projection for collection, fresh prompt-index budgets, observation coverage, and derived-index health. UI and connected job surfaces consume it instead of rescanning producers.
- Session reset lifecycle: clear provider-side continuity through `TurnManager.resetSessionContinuity(sessionId)` before persisted messages/attachments are reset. If continuity reset reports busy, return the same `BusyTurnException`/409 path rather than clearing visible state first.
- Session send, title, lifecycle, and reusable-New-Chat decisions share the factory-owned `SessionMutationCoordinator` (`lib/src/concurrency/session_mutation_coordinator.dart`). Re-read mutable session eligibility inside its per-session critical section before acting; an earlier request snapshot is not authoritative. Each instance is its own chain – the API's outer chain nests safely around `TurnManager`'s inner reservation chain, but never re-enter the same instance for the same session.

## Gotchas
- **There is one token-budget implementation, and it must stay one.** `governance/budget_engine.dart` owns the threshold comparison, the percentage and the warn-once gating; a `BudgetScope` supplies the limit, the consumption reading and the warn-once cell. Two scopes exist — `BudgetEnforcer` (daily, `usage_daily:` aggregate) and `TaskBudgetPolicy` (per task, `session_cost:` KV) — and they diverge on exactly three axes, all deliberate: the daily marker is per-date and is consumed by reaching *either* threshold, the task cell is per-task and is left unwritten by a terminal breach (`limitConsumesWarning`); the per-task check wraps the evaluation in a catch-and-proceed while the daily one has none — never move that `try` into the engine, it would silently allow an over-budget turn on a storage failure; and the block-vs-warn mapping at 100% lives with the consumer (`TurnGovernanceEnforcer`), not the engine. Don't add a third comparison or a second outcome enum; `budget_vocabulary_test.dart` fails on either. Two closed sets of knowing exceptions survive, and neither may grow. **Truncated ladders**: `TaskConfigView.tokenBudget` stops at `configJson`, and `TaskExecutor` resolves the *post*-turn overrun limit through it, so goal-budgeted and default-budgeted tasks are checked pre-turn only; `task_progress_tracker.dart`, `server.dart` and `web/pages/tasks_page.dart` read `configJson` alone, display-only. **Display percentages**: `task_progress_tracker.dart` and `templates/task_detail.dart` compute their own clamped percentage rather than calling `budgetPercentage()`, and `alerts/alert_formatter.dart` renders `BudgetWarningEvent.consumedPercent` itself. New code uses `budgetPercentage()`.
- **`classifyAlert` is the only thing in `alerts/` that may switch on `DartclawEvent`, and its switch must stay wildcard-free.** It returns an alert's type, severity, body and detail fields together; `AlertFormatter` renders that classification into a channel shape and holds no event switch at all, so an event the classifier drops has no path to a channel. A `_ =>` arm in `alert_classifier.dart` would compile, keep every test green, and silently reclassify every future event as "not an alert" – which is precisely the compile-time gate ADR-057 keeps `DartclawEvent` sealed for. `dev/fitness/test/enum_exhaustive_consumer_test.dart` owns all three source-level gates: it names the classifier as the base type's sole consumer, fails on a `_ =>` arm in `alert_classifier.dart`, and fails on a `package:dartclaw_core` import in `alert_formatter.dart` (with no `DartclawEvent` subtype in scope, no switch over one can come back under any parameter name). The load-bearing guarantee is still Dart's sealed-switch compile error; the gates catch the wildcard that would disable it. (`AlertFormatter._title`'s `_ =>` arm switches on a `String` alert type, not an event – it is fine.)
- **A task retry is deduplicated on a typed failure kind, never on message text.** Every `TaskFailureHandler.markFailed`/`markFailedOrRetry` call site supplies a `TaskFailureKind` (`lib/src/task/task_failure_kind.dart`): a `TaskFailureReason` when the host decided the reason, or `TaskExecutionFailure(error)` whose discriminator is the exception's *runtime type* — never its message, which is what the retired prefix-stripping classifier keyed on. The previous attempt's key lives at `configJson[lastFailureKindKey]` (`_lastFailureKind`, underscore-prefixed so the create-task route refuses it as client input); `configJson['lastError']` is display only, feeding the retry prompt. Adding a call site means choosing a kind — reusing a neighbour's collapses two reasons into one retry budget. The vocabulary stays inside `task/` and is not barrel-exported.
- **A workflow one-shot step uses one coordinator worker/container for its whole lifetime.** `TaskExecutor` acquires one `ExecutionCoordinator` worker and passes its leased `TurnRunner` to `WorkflowOneShotRunner`; the main prompt, follow-ups, envelope finalizer and retry all reserve turns on that same runner. The coordinator owns release exactly once after the task settles. Provider-session resume stays on the shared worker. `check_task_executor_workflow_refs.dart` rejects any legacy CLI driver, supervisor, provider or process-starter reachability from `WorkflowOneShotRunner` and `StepTurnRunner`; its mutation test pins both a legacy type and a direct process start. Two concurrent steps each acquire their own worker authority.
- **A container authority is single-use, and crash attribution follows it.** `ContainerManager.start()` throws a typed `ContainerAuthorityLostException` once its container has died rather than recreating one: the bridges were `docker exec` processes that died with it and `HostGateway` revocation is permanent, so an in-place recreate would leave a harness idle against dead mediation. A harness restart or crash recovery therefore fails loudly with an operator-facing cause, and the released lease makes the next execution acquire a fresh authority. `ContainerCrashedEvent` carries the `taskId` the authority was leased for (recorded at `ContainerHealthMonitor.watch`), and `ContainerTaskFailureSubscriber` routes an exact non-null `taskId` through the executor's `TaskFailureHandler.markFailedOrRetry` — the same settlement owner — so a crash re-queues within `maxRetries` instead of terminally failing and racing the executor. An unattributed crash affects no task; profile matching is not an attribution fallback.
- **Container health is tri-state, and only a confirmed not-running is a crash.** `ContainerManager.health()` returns `running` / `notRunning` / `unknown`: a zero-exit `docker inspect` is authoritative, an explicit "no such object/container" is a confirmed absence, and any other non-zero exit (a daemon-connection blip) is `unknown`. `ContainerHealthMonitor` never fires `ContainerCrashedEvent` on `unknown` (it holds the last state), and `stop()` treats an unconfirmable removal as a throw — so one daemon hiccup neither fails every in-flight task nor silently leaks a still-live container while returning its capacity.
- **`composeServerTurns`'s `taskToolFilterGuard` is host-supplied, never fabricated.** Its single-harness compatibility path (SDK hosts and tests) receives an already-constructed `worker`, so it cannot retrofit that harness's guard chain. The host must create the `TaskToolFilterGuard`, layer it over the base chain (`GuardChain.layered(base:, guards: [filter])`), hand *that* chain to the harness, and pass the same instance to `composeServerTurns` — otherwise `startTurn(allowedTools:)` / `readOnly` are silently inert. Never re-introduce a composer-created filter. Coordinator-managed runners carry their own filters (see `runtime/harness_wiring.dart`).
- SQLite is bundled by default — no committed `hooks.user_defines.sqlite3.source: system` block. Release binaries build with `dart build cli` (`dev/tools/build.sh`), which emits a bundled `libsqlite3` from the sqlite3 hooks; committing a `source: system` block would make them depend on the host SQLite (Windows' `winsqlite3.dll` lacks FTS5). The only sanctioned escape hatch is an *uncommitted* `source: system` edit for macOS codesign-blocked local iteration — see `dev/guidelines/KEY_DEVELOPMENT_COMMANDS.md`.
- Workflow-spawned tasks have `reviewMode: auto-accept` (set by the workflow package); the server's review surface won't park them — assume they advance on `accepted`.
- Reserved route patterns in `page_registry.dart` are guarded — `/health`, `/static/`, `/whatsapp/`, `/signal/`, `/memory/content`, etc. Adding a page on a reserved prefix throws at startup, not at request time.
- `TaskExecutor` reads workflow runtime state from the hydrated `WorkflowStepExecution` row, not from `Task.configJson` — workflow-private blobs no longer round-trip through tasks.
- The `task_*_subscriber.dart` files attach to the `EventBus` — adding a new subscriber requires wiring it in the composition root (`runtime/service_wiring.dart`) so it's actually subscribed.
- `dartclaw_runtime.dart` barrel is large but ceiling-checked (≤110 exports) — prefer adding sub-barrels (`*_exports.dart`) over piling onto the top barrel.
- Host `ClaudeCodeHarness` spawns with `approval: never` override `CLAUDE_CODE_SUBPROCESS_ENV_SCRUB=0`; the current Claude CLI otherwise forces `--permission-mode default` and neutralizes `bypassPermissions`. Restricted profiles refuse `approval: never` before spawn. Containerized Claude starts from `claudeContainerHardeningEnvVars`, where scrub `=0` is mandatory because the container is the boundary and the CLI's bubblewrap mode cannot run under that hardening. Decision in `dev/state/DECISIONS.md` (Still Current, 2026-07-07; amended 2026-08-23); don't re-apply the scrub uniformly.

- Suites run in parallel; keep them that way. `dart test` runs suites as isolates in **one OS process**, so ports, the filesystem, and the working directory are shared. Bind port `0`, keep fixtures in per-test temp dirs, and never assign `Directory.current` — inject it (`DartclawRuntime.stageHeadless(runtimeCwd:)`, `WorktreeManager(currentDirectory:)`). `test/runtime/headless_runtime_test.dart` is the one exception: `HeadlessRuntimeFixture.withWiredCurrentDirectory` assigns it to pin the launch-cwd-vs-`runtimeCwd` distinction, and restores it in a `finally`. Do not copy that pattern elsewhere. Breaking this forces the package back to `-j 1` (≈5× wall time). See `dev/guidelines/TESTING-STRATEGY.md` Layer 2 note.
- Template-rendering correctness (HTML structure, escaping) is asserted at Layer 2/3 against rendered output strings — visual layout is covered by manual UI smoke tests, not Dart tests.

- `lib/src/codex_rejection.dart` — the four-bucket backend-refusal vocabulary used by the gateway adapter. A present status decides what it can decide *before* any body marker is read (401 → `authExpired`, 429 → `usageLimit`), because backends write one prose body for several conditions and the losing bucket there maps to no credential health at all. Body markers cover only what no status distinguishes; `modelUnsupported` additionally requires a 4xx.
- `lib/src/task/codex_refresh_authority.dart` — the only thing in DartClaw that rotates a dedicated Codex store. Single-flight is a property of the *instance*, so a deployment constructs exactly one per store and shares it across every lane; two instances are two refreshers. `present()` publishes the in-flight `Future` before its first `await` so concurrent demand joins one token call, while `prepareHostSpawn` gates from *inside* the per-store `RepoLock` and deliberately does **not** join that memo — the memo may hold a refresh still queued on the same lock, and a holder awaiting it would wait on something queued behind itself (a regression test pins the three-participant ordering). The near-expiry window (4 min) sits strictly inside the vendor's own 5-minute proactive window, so a demanded rotation lands where the vendor's conditional refresh acts instead of on its edge. It is the trigger only: after the drive, a token that still has life left is presented rather than failed, so a rotation the vendor declined never fails a turn on a credential the backend still accepts. Only a spent refresh token is terminal — a drive that *threw* leaving no readable store is retryable, since a killed vendor process explains that read as well as a spent lineage does.
- `lib/src/task/codex_vendor_refresh.dart` — drives `codex app-server` (newline-delimited JSON, no `jsonrpc` member) so the vendor's own auth manager performs the token POST; DartClaw embeds no client id, endpoint, or grant type and never reads the refresh token.
- `lib/src/static/VENDORS.md` — vendored asset versions and upgrade commands; update when bumping any of the seven entries. `lib/src/static/fonts/` holds the JetBrains Mono woff2 subsets (variable weight axis, one file per unicode-range).
