# Package Rules — `dartclaw_slack`

**Role**: Slack channel adapter — Socket Mode or the signed Events API for inbound envelopes, the Web API for replies, implementing the `Channel` contract. Entry point: `SlackChannel`; transports: `SocketModeClient`, `SlackEventsHandler`; API: `SlackWebApiClient`; single inbound entry: `SlackEnvelopeDispatch`.

## Shape
- **Inbound**: Slack → Socket Mode WebSocket → `SocketModeClient` (acknowledges the envelope ID, then queues it; a `view_submission` is answered after its handler instead) → `SlackEnvelopeDispatch` by kind → `SlackChannel._handleEvent` / `_handleSlashCommand` → `ChannelInboundGate` → `ChannelManager.handleInboundMessage` (in core) → `ChannelTaskBridge` → `MessageQueue`.
- **Inbound, events mode**: Slack POST → the runtime's Shelf route (bounded bytes, headers) → `SlackEventsHandler.handle` (verify, decode) → the same `SlackEnvelopeDispatch`. `SlackChannel(mode: 'events', signingSecret: …)` builds the handler (`eventsHandler`, null in socket mode), `connect()` only verifies the bot token, and no socket client exists.
- **Outbound**: queued turn → `SlackChannel.formatResponse` (Markdown → mrkdwn, chunks of 4,000) → `SlackChannel.sendMessage` → `SlackWebApiClient.postMessage` with `thread_ts`, or `postEphemeral` to a slash command's `response_url`.
- **Feedback**: `FeedbackObserverFactory` (runtime) asks `SlackChannel.feedbackStrategyFor(message)` for one `SlackFeedbackStrategy` per turn: `assistant.threads.setStatus` while the turn runs, and the reply streamed with `chat.startStream` / `appendStream` / `stopStream` when `channels.slack.streaming` is on and the message has a thread. Its `onTurnCompleted` returns `true` only when exactly one message holds the whole reply, which is how `MessageQueue` skips its own send; `false` leaves the one post to the queue.
- **Inbound files**: after the inbound gate, `takeSlackFiles` downloads a message's files off the envelope path (the handler returns at once, so acknowledgement and later envelopes never wait), one thread reply names every refusal, and the message is admitted with `ChannelMessage.attachments`.
- **Threads**: the adapter stamps `metadata['threadId']` (core's `threadIdMetadataKey`) with `thread_ts`, or the message's own `ts` for a top-level message. Core's `deriveSessionKey` turns it into one session per thread, and every reply carries it back.
- **Threaded notifications**: `SlackChannel.threadedNotifications` (`SlackThreadedNotifications`) is the capability declaration. Its thread identity is conversation-qualified, `'<conversationId>:<thread_ts>'` (composed and split only in that file; Slack ids and timestamps hold no `:`), read from `metadata['spaceName']` + `metadata['threadId']`, so a top-level message already names the thread it opens and a slash command names none. `render` builds Block Kit `section` blocks (`text` stays the fallback), every value through `escapeSlackMarkdown`, each section clipped to Slack's 3,000-character limit, then one `actions` block when the notification carries actions (a button per action, its `value` the `actionData` as compact JSON from `encodeRunActionValue`). Both sends post through `SlackWebApiClient.postMessage(blocks:)`, record participation like `sendMessage`, and return `null` on a `SlackApiException`; `ThreadedPost.messageId` is the message `ts`. `edit` is `SlackWebApiClient.updateMessage(blocks:)` and returns whether Slack accepted it; it always sends blocks (an empty list when the response has none), because Slack keeps a message's old blocks, buttons included, when the field is absent.
- **Run approvals**: `SlackRunApprovals` (`slack_run_approval.dart`) is the `block_actions` handler registered in the dispatch. It reads the first action, the clicker's `user.id` (the id the inbound path uses as sender) and `user.name`, the message `ts` and `response_url`, and calls the injected `ChannelRunApprovalHandler` (`SlackChannel(runApprovalHandler:)`; none bound answers "unavailable"). A refusal, a failure, an undecodable value or a throwing handler is answered privately through `postEphemeral(responseUrl)`; a resolution is acknowledged only. The adapter holds no admin check or nonce state and never edits the post; the runtime's run subscriber does through `edit`. Other action IDs are acknowledged and logged at debug.
- **Request changes**: the post's third button (`run_request_changes`, same `value` as the other two) is a `block_actions` click answered through `checkRequestChanges`. Only on `ChannelRunApprovalPermitted` does the adapter call `SlackWebApiClient.openView(trigger_id, …)` inside the click's handling (the trigger lives 3 s): a modal with `callback_id` `run_request_changes_submit`, one multiline `plain_text_input` (fixed `block_id`/`action_id`, `max_length` 3,000) and run, step, nonce and post `ts` in `private_metadata` as compact JSON. A refusal is an ephemeral answer and no modal opens, so a refused sender never loses typed text; a failed `views.open` (any code, a missing `trigger_id`) is an ephemeral pointer to the run page or the `workflow_request_changes` tool, with no URL invented. The modal's `view_submission` goes through `SlackRunApprovals.handleSubmission` with the text exactly as typed (`feedback`) and action `requestChanges`; the adapter validates nothing about the text.
- **Acknowledgement body**: `view_submission` is the one kind registered with `SlackEnvelopeDispatch.registerAnswering`; every other kind is acknowledged first and empty. Its handler returns `{"response_action":"clear"}` (the modal closes) on `Resolved`, `null` (an empty acknowledgement) for another modal's submission, or `{"response_action":"errors","errors":{"<feedback block_id>":"<text>"}}` for any refusal, failure, throw or unusable metadata. A transport asks `dispatch.answers(kind)` and sends `dispatchAnswering(envelope)`'s result after the handler, or empty at `slackAnswerDeadline` (2.5 s, Slack's limit is 3 s) while the handler runs on: the Events API as the HTTP 200 body (`application/json`), Socket Mode in the acknowledge frame's `payload`. ASSUMPTION: the Socket Mode `payload` placement is not confirmed; only a live workspace does. Socket Mode does not queue a `view_submission` behind earlier envelopes, since its deadline runs from receipt.

## Boundaries
- May depend on `dartclaw_core`, `dartclaw_kernel`, `crypto`, `http`, `logging`. Must not depend on another channel package, `dartclaw_runtime` or `shelf`; `dartclaw_core/lib` names no platform.
- `SlackEventsHandler` is framework-neutral (bytes and a header map in, `SlackEventsResponse` out) and imports no Socket Mode code. It returns a `SlackRequestRejection` for the runtime route to turn into the failed-auth event and the audit entry; oversize bodies are the route's 413, never the handler's. `slackExpectedBotScopes` is the one list of the ten manifest scopes, which doctor and the manifest test compare against.
- Every envelope kind enters `SlackEnvelopeDispatch` as a `SlackEnvelope` value. The dispatch knows no socket, so the Events API transport feeds it the same way. Do not process an envelope anywhere else.
- Runtime composition stays above the package: `runtime/channel_wiring.dart` builds `SlackChannel` from the resolved credentials, `config/slack_config_refusal.dart` refuses an unusable `channels.slack` section at load, and `GroupSessionInitializer` gets no Slack input (sessions are per thread, so a channel-level session would never receive a message).
- The adapter never writes the reserved-command refusal audit entry; the shared `ReservedCommandHandler` does, for every channel.
- `SlackConfig.fromYaml` is the only parse entry point; `dartclaw_runtime`'s `resolveChannelConfig` calls it. Tokens are `credentials` entry names (`bot_token_credential`, `app_token_credential`), never inline values.

## Conventions
- A secret never reaches an error, a log line or an audit entry: `SlackApiException` carries the method and Slack's error code only, a transport error contributes its runtime type, and neither the Socket Mode URL (its `ticket` authorises a connection) nor a `response_url` (slash command or interaction) is ever logged. A run action's button value holds the approval nonce, so it is never logged either, and a throwing approval handler is logged by type only. The kernel redactor masks `xox*-` and `xapp-` token shapes as a second line.
- Inject `delay` and `now` into `SlackWebApiClient` and `SocketModeClient` for tests instead of waiting; use `FakeSocketModeServer` (a real loopback WebSocket) and `FakeSlackWebApi` from `package:dartclaw_slack/testing.dart`. Tests need no network or credentials.
- Ids: `ownsJid` claims `[UWCGD][A-Z0-9]+`, which is how `ChannelManager` routes; do not loosen it.

## Gotchas
- Slack signs the exact bytes (`v0:<timestamp>:<raw body>`, HMAC-SHA256): nothing may decode, parse or re-encode the body before verification, and the `Digest` comparison stays `crypto`'s (no `constantTimeEquals`; that lives in runtime). The 300 s window is checked before the HMAC, an empty signing secret verifies nothing, and a malformed header counts as missing.
- The handler acknowledges before processing: dispatch is started unawaited, a failure is logged by type only, and the `event_id` stays in the 1,000-entry ledger so Slack's retry is not reprocessed. A verified `event_callback` without an `event_id` or event is a 400 and reserves nothing; slash commands and interactions are not deduplicated.
- `SlackHealthReporter.status` feeds the unauthenticated `/health`: mode, connection state, timestamps, a failure count and a reason code only. Socket keys appear in socket mode, `last_verified_at`/`last_failure_*` in events mode; an absent timestamp means never.
- `app_mention` is acknowledged and ignored. The same message also arrives as a `message` event, which alone carries `files`; processing both would run two turns. The app must therefore subscribe to the `message.*` events.
- A channel thread reply needs no mention only when the bot took part in the thread. `_participation` is an in-memory bounded record; a miss (such as after a restart) asks `conversations.replies` once per thread and remembers the answer, yes or no. A mention or a post by the bot overwrites a remembered no.
- The Socket Mode URL from `apps.connections.open` expires within seconds: connect at once, never cache it.
- Slack does not replay envelopes after a disconnect, so the acknowledgement precedes processing. Envelopes are then processed one at a time in arrival order so a slow handler delays no acknowledgement.
- `sendMessage` swallows `SlackApiException` (logs a warning and drops the chunk), so `MessageQueue`'s delivery retry never runs for Slack; the one retry is the 429 retry inside `SlackWebApiClient`.
- Posts to one channel are at least one second apart; the spacing and the 429 `Retry-After` wait both happen inside the per-channel post queue.
- A slash payload carries no thread, so the manifests register `/stop`, `/pause` and `/resume` only: `/bind` and `/unbind` could only answer "not in a thread". The adapter must never stamp `threadName` (Google Chat's binding key).
- `dm_access: pairing` creates a pairing and replies with its code; the runtime's `ChannelAccessService` confirms or rejects it through `/api/channels/slack/dm-pairing/*` and appends the sender to `dm_allowlist` (the allowlist API at `/api/config/channels/slack/dm-allowlist` takes user IDs). The settings page has no Slack surface yet, so confirmation is API-only. The default stays `allowlist`.
- Streamed text is released only through the last whitespace of the *redacted* accumulation, so a secret split across two deltas never leaves in part; the stream carries every text delta (including text written before a tool call), so completion edits the message into the redacted, mrkdwn-formatted reply with `chat.update` unless it already equals it. A failed append stops the stream and edits the message into the whole reply; a reply past 40,000 characters writes its first chunk over the stream message and posts the rest. Appends are at most 12,000 characters and a second apart, and each turn tries to stream once (no circuit breaker).
- The stream methods and `chat.update` go through the same per-channel post queue as `postMessage` (one-second spacing, one 429 retry); `assistant.threads.setStatus` does not. `SlackWebApiClient.teamId` is set by `authTest()` and is the `recipient_team_id` a channel stream needs.
- `downloadFile` sends the bot token only to an `https` host under `slack.com`, on every redirect hop (redirects are followed by hand), reads the body incrementally and abandons it past 20 MB, and treats a `text/html` answer to a non-HTML file as the missing `files:read` scope: Slack answers 200 with a sign-in page there. Failures carry a code (`slackFileTooLarge`, `slackFileScopeMissing`, `slackFileUnavailable`) and never the URL or token. A Slack Connect stub (`file_access: check_file_info`) and a file with no private URL are refused by name; `files.info` is never called.
- A message with files is admitted after its downloads finish, so a later text message from the same sender can be admitted first. File names are untrusted: replies show them one-line, bounded and escaped.
- `connect()` verifies the bot token with `auth.test` first and throws on a rejection without opening the socket; otherwise it starts Socket Mode in the background, where a transient socket failure retries and never fails `connect()`. In events mode the signed route is mounted regardless, so until `connect()` has verified the bot token `SlackEventsHandler` (its `isReady`, `_botUserId != null`) answers a verified event, slash command or interaction 503 and reserves no event ID, so Slack redelivers it; a rejected token fails closed, as Socket Mode (which never opens) does. `url_verification` is still answered, so the request URL can be saved before the server is ready. No dispatch-side guard remains.

## Testing
- `test/support/slack_harness.dart` wires a `SlackChannel` to a fake socket server, a fake Web API and a real `ChannelManager` over a recording queue; `deliver` returns once every earlier envelope has been processed.
- `slack_web_api_client_test.dart` (retry, spacing, fallback, error text, `auth.test` scopes), `socket_mode_client_test.dart` (ack, reconnect, backoff), `slack_events_handler_test.dart` (signature, window, ledger, parity with Socket Mode), `slack_channel_events_mode_test.dart`, `slack_health_reporter_test.dart`, `slack_inbound_test.dart`, `slack_outbound_test.dart`, `slack_slash_command_test.dart`, `slack_envelope_dispatch_test.dart`, `slack_config_test.dart`, `slack_web_api_stream_test.dart` (stream calls, bounded download), `slack_feedback_strategy_test.dart` (injected `now`/`delay`, no real waiting), `slack_inbound_files_test.dart`, `slack_run_approval_test.dart` (clicks over socket and Events API against a recording handler), `slack_request_changes_test.dart` (modal and submission over both transports with a handler that refuses as the runtime does; the 2.5 s deadline through an injected `SlackEnvelopeDispatch(delay:)`). `FakeSlackWebApi` records every stream, update (with blocks), status call, opened modal (`openedViews`, failures scripted with `viewError`) and ephemeral answer, and serves file bodies through `fileHost` so the real download rules run.

## Key files
- `lib/dartclaw_slack.dart` — production barrel; `lib/testing.dart` — opt-in test doubles the barrel does not re-export (`FakeSlackWebApi` scripts `auth.test` scopes and errors; `signedSlackHeaders` signs a body as Slack does).
- `lib/src/slack_channel.dart` — normalization, gating, participation, slash commands, outbound.
- `lib/src/slack_events_handler.dart`, `lib/src/slack_health_reporter.dart`, `lib/src/slack_bot_scopes.dart`.
- `lib/src/slack_threaded_notifications.dart` — the `ThreadedNotifications` capability: thread identity, Block Kit rendering, threaded posts, edit.
- `lib/src/slack_run_approval.dart` — the run-approval click handler and the button value encoding.
- `lib/src/slack_feedback_strategy.dart` (status + streamed reply), `lib/src/slack_file_intake.dart` (bounds, refusals, downloads).
- `lib/src/socket_mode_client.dart`, `lib/src/slack_envelope.dart`, `lib/src/slack_web_api_client.dart`, `lib/src/slack_markdown.dart`, `lib/src/slack_config.dart`.
